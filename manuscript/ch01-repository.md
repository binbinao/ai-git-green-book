> 《Git 的概念地图》第 1 章 · 定调稿 v1.0
> 五张地图的第一张：所有其他概念都装在这个盒子里。

## 1.1 场景引入：飞机上的四个小时

你坐在飞机的中间座位，膝盖顶着前排椅背。空乘刚刚广播完飞行时长——四小时二十分。你翻出电脑，机上没有 Wi-Fi，或者有但你不打算花那 80 块。

你打算把手上那个功能收个尾。改了半天，测试跑过，想 commit。手指悬在键盘上又停了半秒：**没有网，git 还能用吗？**

你试探性地敲下 `git add .`、`git commit -m "..."`，回车。什么都没发生——不，是**一切都发生了**：命令返回码是 0，log 里多了一行，工作区干净。没有报错，没有加载动画，没有\"正在连接服务器\"。

你有点狐疑地又提了两次。飞行中间你甚至开了个新分支，rebase 了一段乱糟糟的历史，把 message 全部重写了一遍。落地前的最后半小时，你 `git log --graph --oneline` 看了看，一切井井有条。

落地，连上 4G，敲 `git push`。三秒。

请诚实地回答一个问题：**过去这四个小时，你操作的到底是什么？** 你改的那些提交存在哪里？rebase 是找谁做的？如果全程都没有网，那份\"历史\"是从谁那儿变出来的？

如果答案含糊，那你就还没有第一张地图。这一章要摊开的，就是这张地图——**仓库**。看完你会知道：过去四个小时，你操作的不是\"GitHub 的一个项目\"，你操作的是**一个躺在你笔记本硬盘上、名字叫 `.git` 的完整数据库**。GitHub 那边有没有电，跟它一点关系都没有。

## 1.2 祛魅时刻：仓库到底\"是\"什么

先给结论。

> **一个 Git 仓库，是一个自包含的、内容寻址的、可以脱网工作的历史数据库。它的全部实体，是你项目根目录下那个 `.git/` 文件夹。**

关键词四个，每一个都戳穿一种主流的误解：

- **自包含**：所有历史、所有引用、所有配置，全部在 `.git/` 里。删掉这个文件夹，历史立刻消失；打包带走这个文件夹，历史一颗珠子不缺地跟你走。
- **内容寻址**：数据不是按\"路径\"存的，是按\"内容的哈希\"存的。同样的内容，全世界所有 Git 仓库里都是同一个身份证号。
- **可脱网**：Git 是一个**分布式**版本控制系统。它对网络的依赖是**零**——只有当你要跟另一份拷贝对话时，才需要网。
- **历史数据库**：不是文件夹，不是备份，不是云盘。是**结构化的历史**——每一次快照、每一次操作、每一张标签，都以对象的形式沉淀在里面。

如果你上一秒还在把\"仓库\"和\"GitHub 上那个项目\"划等号，这一节就是要**把这条等号砸碎**。GitHub 上那份东西是**你仓库的一个远程副本**（第 4 章专门讲这面镜子），它不是你的仓库；它甚至不是\"权威版本\"——只是被团队约定为\"大家都往那里同步\"的一份拷贝而已。Git 的世界里没有\"服务器\"这个特权角色。**每一份 `.git/`，都是完整的。**

### 打开黑盒：`.git/` 里到底有什么

不用相信我，自己看。找一个你手上的仓库，`cd` 进去，`ls .git/`：

```
.git/
├── HEAD              ← 当前站在哪里（一行文本）
├── config            ← 这个仓库的本地配置
├── description       ← 给 gitweb 显示用的（几乎没人管）
├── hooks/            ← 事件触发的脚本（第 13 章讲）
├── info/             ← 排除规则等杂项
├── objects/          ← ★ 核心数据库：所有内容都在这里
│   ├── 3f/
│   │   └── a2b7c8...   ← 一个对象文件
│   ├── 8b/
│   ├── ...
│   └── pack/           ← 打包压缩后的对象
├── refs/             ← ★ 引用表：所有\"名字\"都在这里
│   ├── heads/         ← 本地分支
│   ├── tags/          ← 标签
│   └── remotes/       ← 远程分支的本地缓存（第 4 章）
├── logs/             ← reflog：所有 HEAD 移动的记录（第 5 章救命用）
├── index             ← 暂存区快照（下一节讲）
└── packed-refs       ← 打包过的引用
```

密密麻麻看起来很吓人，其实**核心只有两个东西**：

1. **`objects/`**：一个 key-value 数据库。key 是内容的 SHA-1 哈希，value 是内容本身（压缩过）。你项目里所有版本的所有文件、所有目录快照、所有提交对象，全都在这里。
2. **`refs/`**：一张\"名字表\"。给上面那堆晦涩的哈希起人类可读的名字：这个哈希叫 `main`，那个哈希叫 `v1.0`，还有一个叫 `origin/main`。

其他的一切——HEAD、config、hooks、logs——都是围绕这两个核心转的辅助设施。

**用一个比喻**：`.git/` 是一间**档案馆**。`objects/` 是档案库里编号入柜的一箱箱资料（按内容哈希编号，永不改档、只增不删）；`refs/` 是门口的目录索引卡（这张卡叫\"main\"，指向 3 号柜第 47 箱）。索引卡可以随时改写（分支移动），也可以摘掉（分支删除），但柜子里的箱子一动不动。这就是为什么第 3 章说\"删分支不删提交\"——删的是索引卡，箱子还在。

### 内容寻址：为什么同一份内容全世界都是同一个身份证

Git 里所有东西都有一个 40 位十六进制的名字——SHA-1 哈希（新版本可选 SHA-256）。这个哈希不是随机分配的，是**根据内容算出来的**。

一个文件的内容一模一样，哈希就一模一样。你在自己电脑上算出来的哈希，和你同事在他电脑上算出来的哈希，一定相同。

这带来一个漂亮的性质：**两份仓库要同步时，只需要交换\"你有哪些哈希、我有哪些哈希\"**。相同的哈希代表相同的内容，不用传；差集才是要传的东西。这就是 `git fetch` 底层的对话逻辑——它不是在\"下载文件\"，是在**核对两家档案馆的箱子编号**，然后只搬相差的那几箱。

这也解释了为什么 Git 那么快、那么小：你 clone 一个几百 MB 的仓库回来，磁盘上就是几百 MB；再 clone 一次，还是几百 MB。中间没有\"下载重复内容\"这回事——每一份 objects 都是全量的，因为每一份 objects 都是唯一的。

## 1.3 三个直接推论

接受了\"仓库是本地的自包含数据库\"，很多日常怪事一下子讲得通：

**推论一：你可以完全脱网干活，一整天。**
飞行中的场景不是特例，是常态。commit、branch、merge、rebase、log、diff、tag、stash——所有这些操作**都不发一个字节的网络请求**。Git 会假装网络不存在，只对着本地那份数据库干活。等你想把结果同步给远端，才是 `push` 和 `fetch` 出场的时候——这三个命令（还有 `pull` 和 `clone`）是 Git 里**仅有的会碰网络的操作**。

**推论二：删了 GitHub 上的仓库，你的项目历史没死。**
只要你本地那份 `.git/` 还在，历史就完整。你可以在别的平台上开一个空仓库，`git push` 一下，全部历史一颗珠子不掉地重建过去。你的同事们各自的 `.git/` 也是完整的。Git 天然抗审查、抗单点故障——因为它压根没有\"中心\"。你叫某一份为\"权威\"，那只是团队协作层面的约定，不是 Git 层面的事实。

**推论三：`clone` 不是\"下载文件夹\"，是\"复制整个档案馆\"。**
`git clone` 做的事分两步：把远端的 `.git/` 目录一整个搬到本地，再把当前分支的最新快照展开到工作目录（就是你看到的那些文件）。**你看到的那堆代码，是从 `.git/` 里\"读档\"读出来的**，不是从服务器逐个文件下载的。所以 clone 完成后，你在飞机上就能看到所有分支、所有标签、所有历史，全部离线可用——它们全在你本地的 `objects/` 和 `refs/` 里。

推论三配一张图更清楚：

```
        远端（GitHub / GitLab / 内网 Gitea）
        ┌───────────────────────────┐
        │ 服务器上的 project.git/    │
        │  ├─ objects/  (全量对象)   │
        │  └─ refs/     (全量引用)   │
        └────────────┬──────────────┘
                     │  git clone
                     ▼
        本地磁盘  ~/work/project/
        ┌───────────────────────────┐
        │ .git/                      │← 与远端结构一致的完整拷贝
        │  ├─ objects/  (全量对象)   │
        │  └─ refs/     (全量引用)   │
        │                            │
        │ src/  README.md  ...       │← 从 .git 里\"读档\"铺出来的工作区
        └───────────────────────────┘
```

*图 1-1：clone 复制的是整个 `.git/`，工作区里那堆文件只是从中读出来的\"当前视图\"。*

## 1.4 仓库的三种形态

同样是\"仓库\"，在不同的物理位置扮演不同角色，长得也略有不同：

**形态一：本地仓库（working repository）**
你日常开发用的那种。有 `.git/` 目录，也有和它并排的工作目录（那些你能编辑的源代码文件）。工作区是给你看的，`.git/` 是给 Git 看的。

**形态二：裸仓库（bare repository）**
只有 `.git/` 内容，没有工作目录。目录名通常以 `.git` 结尾（比如 `project.git/`）。你不能在里面编辑代码——它就是纯粹的档案馆，用来给别人 push/fetch。**你在服务器上（GitHub、GitLab、公司自建 Gitea）看到的每一个仓库，本质上都是一个裸仓库。**

裸仓库存在的理由很简单：如果服务器上有工作目录，你 push 上去的更改会和\"服务器上当前铺开的那份代码\"打架——到底以谁为准？裸仓库的做法是根本不铺工作区，只留档案馆，谁需要看代码谁自己 clone。

用一个 `--bare` 参数就能创建：`git init --bare project.git`。

**形态三：远程副本（remote copy）**
严格说这不是一种\"新形态\"——它就是别人电脑上的一个仓库（本地的也好，裸的也好），你通过网络能碰到它。在你自己仓库的视角里，它是一个\"远程\"（remote），有一个别名（默认叫 `origin`）。

**关键点**：\"远程\"不是特殊的仓库类型，只是**你对另一份仓库的引用方式**。它可以是 GitHub 上的一个裸仓库，可以是同事笔记本上一个开了 SSH 的本地仓库，也可以是同一台机器上另一个路径下的仓库。**Git 不区分\"服务器\"和\"客户端\"——每一份仓库，在别人眼里都可以是\"远程\"。**

这一点在第 4 章会展开成一整章。这里先埋一个种子：既然远程不是特殊仓库，那**\"origin/main\" 这种东西也不是服务器上的东西**——它是你本地对\"上次听说远端 main 在哪里\"的一份缓存。这是很多人迷路的起点。

## 1.5 关于\"clone 的真实语义\"再说一遍

因为这个误解太常见，值得单开一小节把话说透。

大多数人对 `git clone <url>` 的直觉是：

> \"从服务器上，把项目文件下载到本地。像 wget、像浏览器下载，只是它会顺便把 .git 也带上。\"

**这个直觉是反的。** 正确的语义是：

> \"从远端把 `.git/` 数据库整个复制过来，然后**在本地**根据数据库把当前分支的快照\"读档\"铺开成一堆文件。\"

主角不是\"文件\"，主角是**数据库**。文件是数据库的一个衍生视图。

三个可以立刻验证的观察：

**观察一：clone 完立刻断网，一切都能用。**
包括 `git log --all`（看所有历史）、`git checkout <某个 3 年前的 sha>`（看历史版本）、`git branch <name>`（开分支）、`git diff <某个 tag>`（对比古董版本）。**没有一个操作需要联网**——因为它们要的东西全在本地 `.git/` 里。

**观察二：一份 clone 的大小，几乎等于服务器上仓库的大小。**
不管你的分支多少、tag 多少、历史多长，clone 会把全部搬回来。这是 Git 分布式模型的基础：**每一份 clone 都是权威。** 你 clone 完，理论上就有资格接过整个项目的历史，独立继续下去。

（如果你只想要浅历史——比如 CI 环境只 build 最新版——可以用 `--depth 1` 做浅克隆。这是**明确的例外**，需要你显式请求；默认行为永远是全量复制。）

**观察三：clone 和 fork 不是一回事。**
Fork 是 GitHub/GitLab 平台的功能，在**平台侧**给你复制一份远端仓库（第 4 章、第 11 章会讲清 Fork 工作流）。clone 是 Git 的原生动作，把\"某份远端\"复制到**你本地**。两者在不同层，很容易被混为一谈。一个粗糙的对应：Fork 是\"服务器上的 clone\"，clone 是\"本地上的 clone\"。

## 1.6 三区模型的预告

到这里，你已经掌握了\"仓库 = 一个自包含的历史数据库\"这一层。但当你开始实际 commit 时，会遇到 Git 的另一个特色：**它在你的\"工作目录\"和\"仓库\"之间，还塞了一层缓冲区。**

这层缓冲区叫\"暂存区\"（staging area，也叫 index），存在 `.git/index` 这个文件里。你熟悉的 `git add` 就是在往它里面塞东西，`git commit` 才是把它写进 `objects/` 变成一颗真正的珠子。

三区模型（工作目录 / 暂存区 / 仓库）是 Git 最容易\"顶到脸上\"的抽象。它值得单开一章讲透——那就是下一章（第 2 章）的一半内容。这里先只留一句话让你带着往下走：

> **`.git/index` 是仓库的\"入库暂存台\"。你在工作目录里的所有改动，都要先过暂存台，才有资格进档案馆。`add` 是搬上暂存台，`commit` 是入库。**

有了这一句，第 2 章会告诉你为什么这样的设计不是脱裤子放屁——它是 Git 提供的\"提交塑形工具\"，让你能对\"这一次要归档什么\"做细粒度的控制。这是 SVN、Mercurial 都不这么玩的地方，也是 Git 命令表里让新手最困惑的一层。

## 1.7 场景判断：什么时候你需要一个新仓库

概念清楚了，落到实操层面：**这堆代码，什么时候该开个 Git 仓库？什么时候不该？** 三条判断规则。

**规则一：任何值得存超过两天的东西，都开仓库。**
心理成本几乎为零（`git init` 一行命令、一毫秒完成、`.git/` 一开始只有几十 KB）。你不开仓库损失的是历史；开了仓库最坏也就是多几十 KB 磁盘占用。这个不对称让\"该不该开\"的决定几乎不需要犹豫。**AI 时代补充**：你让 AI 帮你随便造的原型代码、探索性脚本、临时试验目录，也顺手 `git init` 一下——你会庆幸的，因为 AI 会\"帮\"你改坏东西，reflog 是唯一的救生索。

**规则二：一个逻辑上独立的\"项目\"= 一个仓库。**
不要把三个不相关的项目塞进同一个仓库（除非你有意做 monorepo，那是另一个话题，见第 13 章）。判断标准：**它们是不是有独立的发布节奏、独立的贡献者、独立的生命周期？** 如果是，各开各的。

**规则三：不要把仓库嵌套。**
在一个已有仓库的目录里 `git init` 另一个仓库，会得到 Git 的皱眉——这种嵌套关系不是\"目录树的自然扩展\"，Git 需要你显式声明是 submodule（第 13 章）还是 subtree。想\"顺手管一下\"这种半路加进来的子目录，通常是麻烦的开始。

**反规则一：不要为一个五分钟就扔的脚本开仓库。**
这条不冲突——五分钟就扔的东西不属于\"值得存超过两天\"。开仓库当然可以，但那不叫 Git 用法，那叫强迫症。

## 1.8 AI 指令箱 · 仓库

以下指令模板与工具无关（Claude Code / Cursor / Copilot / Aider / Windsurf 皆适用）。**使用前先看颜色标注**——本章大多是绿色指令（探索仓库结构、了解现状），黄色出现在\"clone 到敏感位置\"和\"init 覆盖已有目录\"的极少数场景。

**🟢 探索类（只读，放心用）**

- 「打开我当前所在的仓库，告诉我这些事：它有多少个提交、多少个分支、多少个 tag、`.git/` 目录整体多大、`.git/objects/` 里有多少个对象。用一张表给我。」
- 「读 `.git/config` 文件，用中文解释一下里面每一段配置的意义。特别关注 `[remote]` 和 `[branch]` 那几段。」
- 「让我看一下 `.git/HEAD` 和 `.git/refs/heads/` 下的文件内容——不是 `git branch` 的输出，我要看那几个文本文件里到底写了什么。」
- 「用 `git rev-parse --is-bare-repository` 和 `git rev-parse --git-dir` 帮我确认：我现在在什么类型的仓库里、`.git` 目录在哪儿。用一句话总结。」

**🟢 clone/init 类（低风险）**

- 「我想 clone 这个仓库到本地：<URL>。clone 之前先告诉我这个仓库的大小估计有多大（用 GitHub API 查一下）、有哪些主要分支、上一次提交是什么时候。clone 完成后确认 `.git/` 的实际大小和对象总数。」
- 「在当前目录初始化一个新的 Git 仓库，默认分支设为 `main`。初始化后打印 `.git/` 里的目录结构（一层就行），让我看看什么都还没提交的时候仓库长什么样。」
- 「帮我做一个浅克隆（`--depth 1`）到 `/tmp/quick-look`，我只是想看看这个开源项目最新版长什么样，不需要历史。看完提醒我用 `rm -rf` 清理掉。」

**🟡 需要盯着的（涉及覆盖或敏感位置）**

- 「我想在 `~/existing-project` 目录初始化 Git，但那里已经有一堆代码了。在你执行 `git init` 之前，先扫描一下有没有明显的敏感文件（.env、id_rsa、config.json 之类），列出来，由我决定要不要先加 .gitignore 再 init。」
- 「clone 这个仓库到 `~/work/`，clone 完成后立刻检查有没有 `.env`、`credentials.json` 之类的敏感文件被 commit 进历史里。如果发现了，先别做任何清理，告诉我在哪几个 commit。」

**训练用指令（陪练模式）**

- 「假装我是一个只用过 GitHub 网页界面、从没在命令行用过 Git 的人。给我出 8 个判断题：'仓库到底在哪里''远程和本地的关系''clone 到底做了什么''删除 GitHub 上的仓库我的代码还在不在'等等。每题给四选项，我答完你批改并讲评错的那道。」

## 1.9 执行后的世界

把本章的指令交给 AI 执行后，`.git/` 里发生了什么？透视一下：

| 你说的话 | AI 大概率执行 | `.git/` 里的真实变化 |
|---|---|---|
| \"在这里 init 一个仓库\" | `git init` | 新建 `.git/` 目录，写入 HEAD、config、objects/、refs/ 骨架，占用约 100–200 KB |
| \"clone 这个仓库\" | `git clone <url>` | 把远端 `.git/` 的**全部对象和引用**打包传输到本地，然后在工作目录展开当前分支的快照 |
| \"看看 .git 里有什么\" | `ls .git/`、`cat .git/HEAD` | **零字节变化**——纯读操作 |
| \"这个仓库有多大\" | `git count-objects -vH` | 零变化 |
| \"清一下 .git\" | `git gc` | 把散落对象打包进 `objects/pack/`，可能显著缩小 `.git/` 体积（但不改变任何历史） |
| \"再 clone 一次到别的目录\" | `git clone . ../copy` | 新目录里出现一个**完整拷贝**——不是软链、不是引用，是**独立的档案馆** |

看懂这张表你会发现：本章讲的所有\"神奇\"操作，最终都落到\"读写 `.git/` 目录里的几个文件\"这件平淡无奇的事上。**Git 不是魔法。它是文件系统上一套聪明的约定。**

## 1.10 命令侧栏

```
git init                 # 在当前目录搭一个空档案馆（新建 .git/）
git init --bare          # 搭一个裸档案馆（没有工作区，服务器用）
git clone <url>          # 把远端档案馆整个复制过来 + 铺开工作区
git clone --depth 1 <url># 浅克隆：只要最新一层，不要历史（CI 常用）
git clone <local> <dst>  # 本地 clone 本地：就是复制 .git 目录
git count-objects -vH    # 统计 objects/ 里的对象数与体积
git gc                   # 打包散落对象，压缩 objects 存储
git rev-parse --git-dir  # 告诉我 .git 目录在哪里
git rev-parse --show-toplevel  # 告诉我当前仓库的根在哪里
```

不需要背。需要时回来看，或者直接说人话让 AI 翻译。

## 1.11 本章小地图

```
仓库 = 一个自包含的历史数据库 = 你项目根目录下的 .git/
  │
  ├─ objects/  内容寻址库（按 SHA 存所有版本的所有内容）
  ├─ refs/     引用表（给哈希起人类可读的名字）
  ├─ HEAD      当前站在哪里
  ├─ config    这个仓库的本地配置
  ├─ hooks/    事件触发脚本（第 13 章）
  ├─ logs/     reflog：所有 HEAD 移动的记录（第 5 章救命用）
  └─ index     暂存区快照（第 2 章讲）

三种形态：
  ├─ 本地仓库（有工作区）      —— 你每天用的
  ├─ 裸仓库（只有 .git 内容）  —— 服务器上的都是这个
  └─ 远程副本                  —— 其实就是别人的仓库 + 你的引用

三个直接推论：
  1) 完全可以脱网干活（只有 push/fetch/clone/pull 需要网络）
  2) 删了 GitHub 你的历史没死（只要本地 .git 还在）
  3) clone 是复制整个档案馆，不是下载文件
```

## 1.12 三大典型误解拆解

**误解一：\"仓库就是 GitHub 上那个东西。\"**
这是最流行、也最贻害无穷的误解，因为它把\"托管平台\"和\"版本控制系统\"混成一坨。真相是：Git 是一套本地运行的分布式版本控制系统，GitHub / GitLab / Gitea / Bitbucket 是搭在 Git 之上的**协作与托管服务**。你在 GitHub 页面上看到的\"issues\"\"PR\"\"Actions\",没有一样是 Git 原生的——它们是平台加的层。Git 原生只有：仓库、提交、分支、标签、引用。**Git 可以完全脱离 GitHub 存在；GitHub 不能脱离 Git 存在。** 分清这两层，会为你省下未来无数次\"服务出问题我是不是完蛋了\"的心跳加速。

**误解二：\"clone 是把代码下载到本地——就像下载 zip 包一样。\"**
下载 zip 包你得到的是**当前一份快照**——一层。clone 你得到的是**整个历史数据库**——所有层。差异体现在：zip 包解开后你没法 `git log`、没法看分支、没法回到 3 年前的版本、没法看谁改了什么；clone 完这些全都能干，而且离线就能干。**如果你只是想看看代码最新长什么样、不需要历史，那你要的确实是下载 zip（GitHub 页面上就有那个按钮）——不是 clone。分清楚需求，别把两件事情混着做。**

**误解三：\"我本地这份是'副本',服务器那份才是'主'。\"**
Git 不同意。**每一份 `.git/` 都是完整的、平权的。** 服务器那份被叫做\"主\"，纯粹是因为团队约定\"我们都往这里同步\"，不是 Git 层面的特权。这个平权设计有实际后果：服务器炸了，任何一个团队成员本地 push 一下，就能起一个新的\"主\"。历史不会丢，因为它同时存在于每一份 clone 里。**这也是 Git 之所以叫\"分布式\"的原因——不是命令能远程执行，是仓库本身就分布在每个人手上。**

---

**下一章预告：** 你现在知道仓库是一个装着\"历史\"的数据库。但这个\"历史\"到底是什么材料做的？是一颗颗珠子——commit。下一章你会打开一颗珠子，看看里面装着什么。你会知道：Git 存的不是\"改动\"，而是**一次次全量的快照**；\"改\" commit message 其实是造了一颗新珠子；那颗你以为\"丢掉\"的珠子，其实还在 reflog 的托管期里安睡。你还会正面遭遇第 0 章自测第 4 题的答案——**三区模型**——那是 Git 命令表里让新手最困惑的一层，也是 Git 提供给你的\"提交塑形工具\"。
