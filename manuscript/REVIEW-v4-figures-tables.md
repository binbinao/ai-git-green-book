## 0. 一句话结论

你感觉「图还能更好」，**方向对，但杠杆找错了**：

> 问题不在「图排得不够大」——14 张位图**已经全部顶满 120mm 版心宽**，没有可缩放空间。
> 真正的原因是 **archify 的图内字号是「画布设计单位」里的固定值（11px/9px/8px/7px），不随画布尺寸变化**。
> 于是画布越宽，落到纸上的字越小：`落版 pt = 画布字号 × 340.16 ÷ 画布宽`。
>
> 结果：**13/14 张图的图内正文字号在 2.5–5.7pt**，而书里两张 ASCII 图是 **8.5pt**。
> 这个 2–3 倍的落差，就是「看着累」的全部来源。

好消息：这是一个**纯几何问题，有确定的解**，而且不需要重画内容。

## 3. 根因：图内字号 = 11px × 版心宽 ÷ 画布宽

### 3.1 archify 的字号体系（源码证据）

`renderers/architecture/render-architecture.mjs` 里，图内各层字号是**写死的设计单位值**：

| 元素 | 源码 | 首选 | 下限 |
|---|---|---|---|
| 节点主标签 | `fittedNodeFontSize(c.label, brandLabelFitWidth(c, c.width), 11, 8)` | **11px** | 8px |
| 节点副标签 | `fittedNodeFontSize(c.sublabel, c.width, sublabelPreferred, sublabelMinimum)` | **9px** | 6px |
| 节点 tag | 同上，`tagPreferred / tagMinimum` | **7px** | 6px |
| 连线标签 | `<text … font-size="8">` | **8px（硬编码，永不变）** | — |
| 边界标题 | `measureBoundaryTitle()` 内 clamp | 8–9px | — |

`renderers/shared/text-fit.mjs` 的收缩公式：
`fitted = min(preferred, (width − 8) / (textUnits × 0.6))`，下限截断。

**关键**：这些是**画布单位**的 px，不是输出 px。画布多大，它们都不变。

渲染链路（`build/render_figure2.py`）：
```
spec.json → archify render → HTML → Chrome headless (DPR=3, 视口 1100×2600)
          → SVG 铺满视口宽（≈1080 CSS px）→ PIL 去底纹 + 自动裁白边 → PNG
```
因为 SVG 被**铺满视口宽**，所以 14 张 PNG **全部恰好 3253 px 宽**（3300 − 裁边），
这本身就是「画布内容宽 → 固定落版宽」这条映射的直接证据。

`meta.quality_profile` 14 张全是 `showcase`，weight 600，深字浅底 —— **渲染配置已经是最优**，
不是配置问题。

### 3.2 换算公式

```
落版 pt = 画布字号(px) × 版心宽(mm) × 2.8346 ÷ 画布宽(设计单位)
        = 画布字号(px) × 340.16 ÷ canvas_W          （满版心宽的图）
```

反解「达到 7pt 所需画布宽上限」（7pt 是图书图表内文字的经验下限）：

| 元素 | 画布字号 | 画布宽上限 |
|---|---|---|
| 节点主标签 | 11px | **≤ 534** |
| 副标签 | 9px | ≤ 437 |
| 连线标签 | 8px | ≤ 388 |
| tag | 7px | ≤ 340 |

## 5. 方向杠杆：横置整页

### 5.1 模型

- 竖版页：`s_u = min(120 / W, 196 / H)` mm/单位
- 横版页（整页旋转 90°，版心变为 196 × 120）：`s_r = min(196 / W, 120 / H)`
- **增益 = s_r / s_u**

### 5.2 结论

| 图 | 画布 | 比例 | 竖版 mm/单位 | 横版 mm/单位 | 增益 | 横置后节点 pt | 判定 |
|---|---|---|---|---|---|---|---|
| 0-2 | 370×630 | 0.59 | 0.3095 | 0.1905 | **0.62×** | 5.94（−38%） | ❌ 绝对不要 |

| 1-1 | 760×708 | 1.07 | 0.1579 | 0.1695 | 1.07× | 5.28 | ➖ 收益太小 |
| 0-1 | 790×638 | 1.24 | 0.1519 | 0.1881 | 1.24× | 5.86 | ✅ |
| 13-1 | 660×528 | 1.25 | 0.1818 | 0.2273 | 1.25× | **7.09** | ✅ 达标 |
| 4-1 | 740×558 | 1.33 | 0.1622 | 0.2151 | 1.33× | 6.71 | ✅ |
| 12-2 | 880×618 | 1.42 | 0.1364 | 0.1942 | 1.42× | 6.05 | ✅ |
| 7-1 | 920×578 | 1.59 | 0.1304 | 0.2076 | 1.59× | 6.47 | ✅ |
| 8-1 | 910×568 | 1.60 | 0.1319 | 0.2113 | 1.60× | 6.59 | ✅ |
| 2-1 | 1090×598 | 1.82 | 0.1101 | 0.1789 | **1.62×** | 5.58 | ✅ 最大收益之一 |
| 3-1 | 880×518 | 1.70 | 0.1364 | 0.2216 | **1.62×** | **6.91** | ✅ |
| 10-1 | 1030×588 | 1.75 | 0.1165 | 0.1893 | **1.62×** | 5.90 | ✅ 最大收益之一 |
| 5-1 | 840×508 | 1.65 | 0.1429 | 0.2321 | **1.63×** | **7.24** | ✅ 达标 |

**要点**

1. **横置的收益上限是 196/120 = 1.63×**，达到它的条件是「原图宽度贴边、高度还留有余量」——
   也就是**横长图**。10 张符合，实测增益 1.24×–1.63×
2. **竖长图横置是负收益**（0.62× / 0.70×），因为长轴被迫塞进 120mm 窄边
3. **横置只解决一半问题**：只有 5-1、13-1、3-1 三张能靠横置单独跨过 7pt；
   2-1、10-1 这种"超宽"图横置后仍只有 5.6–5.9pt
4. **重排（改画布比例）与横置量级相当**（1.28×–1.72× vs 1.24×–1.63×），
   且重排对 2-1 / 10-1 更有效（1.72× / 1.69×）。**建议：以重排为主，横置为辅**
5. 横置的**额外代价**：需要读者把书转 90°，且图会独占一页。本书是面向新手的教学书，
   建议只在少数几张（3-1、5-1、13-1）使用，且在图题里加"（请横置阅读）"提示

### 5.3 要牢记的设计约束（可直接写给 spec）

> **单张图的画布设计尺寸不应超过 534 × 872 单位**（比例恰为版心 0.612）——
> 此时节点主标签刚好 7pt。

| 目标 | 画布上限（宽 × 高） |
|---|---|
| 节点主标签 ≥7pt | **534 × 872** |
| 副标签 ≥7pt | 437 × 714 |
| 连线标签 ≥7pt | 388 × 634 |
| tag ≥7pt | 340 × 555 |

> 高度上限 = 宽度上限 × 1.6333（即版心高/宽），这样两个方向同时贴边、不留浪费。

现状对照：14 张里 **13 张的画布宽超过 534**（最小超 1.24×，最大超 2.05×）。
**这一条基准可以直接替代"凭感觉调"**。

既不能放大（已贴边），横置也无意义（表格的约束是**列宽**而非整体尺寸）。
`REVIEW-v3` 已把表格字号体系统一到 9pt，**这一层不建议再动**。

| 页 | 表头格宽（mm） | 实测缺陷 |
|---|---|---|
| **p129** | 24.0 ×3（实为 5 列） | `git reset --soft C` → 折成 **2 行**；<br>`git reset --mixed C (默认)` → 折成 **3 行**；均 6.19pt |
| **p177** | 26.7 / 32.0 / 34.7 | 表头 `Trunk-Based` → `Trunk-` / `Based`；<br>`特性分支怎么合` → `特性分支怎么` / `合` |
| **p244** | 26.7 / 26.7 / 32.0 / 34.7 | `add/rm/rename` → `add/rm/` / `rename` |
| p178 | 26.7 / 32.0 / 34.7 | 同 p177 体例 |
| p210 | 24.0 ×3 | `S4 试危险操作（大 rebase、reset、脚本重写历史）` 在 24mm 列里占 4–5 行 |
| p211 | 24.0 ×3 | 同上 |
| p155 | 26.7 / 26.7 / 32.0 / 34.7 | 同类 |
| p20 | 30.0 ×4 | `一个自包含的历史数据库，藏在 .git/ 里` 折 3 行 |

**为什么这是问题**：命令行被折成 2–3 行后，读者**无法一眼抄下来**，也看不出这是"一条命令"；
`Trunk-` / `Based` 则把一个专有名词劈成两半。

**处置建议（按性价比排序）**

1. **重分配列宽**（零成本，改 `columns:` 即可）。现状多为**均分**
   （如 p177 的 26.7/32/34.7、p20 的 30/30/30/30），但第一列"维度/冲突类别"内容短，
   富余宽度被浪费，应该让给内容列 → 把最窄列从 24mm 提到 32–36mm
2. **命令列禁止折行**：对含命令的单元格加 `#show table.cell` 内 `raw` 的
   `break: false`（或改用 `#h(0pt)` 断点抑制），让"一条命令"保持完整；
   若无论如何放不下，**把命令提到表外的代码块**（p129 那三条 `git reset` 尤其适合，
   因为正文已经逐条解释过）
3. **表头专有名词不折行**：`Trunk-Based` → 允许整体溢出/缩小，或缩写为 `Trunk`（正文已给全称）
4. ⚠️ 注意 1 与 2 会**互相作用**：加宽列 + 禁止折行会让表变高，可能触发更多跨页续表

#### 问题 B：表内行内代码 6.19pt（全书 9,150 字）

- 成因是**倍率相乘**：`raw` 固有 0.8em 基准 × 表格 0.86 缩放 → `9.0 × 0.8 × 0.86 = 6.19pt`
  （正文里的行内代码是 `10.5 × 0.8 × 1.07 = 8.99pt`，正常）
- **6.19pt 低于 7pt 阅读下限**，且这是"要照着敲"的代码
- **处置**：给**表格内的行内代码**单独加一条 `#show raw.where(block: false)`，
  不继承 `raw` 的 0.8 基准，直接设 ~8pt
- ⚠️ **副作用警告**：代码放大会加宽单元格 → 会让**问题 A 恶化**。
  **正确顺序是先做 A（重分配列宽），再做 B（提字号）**；若某张表因此放不下，宁可
  把该表的代码改成表外代码块

### 6.4 不建议做的事

- ❌ 不要为了"更好看"给表格加竖线（现在的横线 + 深青表头是好设计）
- ❌ 不要动表体 9.0pt（相对正文 10.5pt 的 0.86 是出版常规）
- ❌ 不要试图"放大表格"（已满版心）

## 10. 本报告的自我限定

1. **所有数字来自对最终 PDF 的实测**，不是对源文件的推断。
   中间产物（`book-body.typ`）与最终产物会不一致 —— 判据永远取最终 PDF
2. **7pt 是经验下限而非硬标准**。学术出版常在 6–7pt 之间；本书是教学书、
   读者含新手，故取 7pt 偏保守。若认为 6pt 可接受，画布上限可放宽到 625 × 1020
3. **"重排收益"（第 4.3 / 5.2 节的 ×1.xx）按"画布面积不变、比例调到 0.612"计算**，
   是理论上限。实际重排可能因 archify 的几何约束（节点宽 ≥ 副标签宽、step > 节点宽、
   名牌不重叠）而达不到 —— `build/figures/README.md` 已记录过 4 张变体因此失败
4. **未评估矢量方案**。`README.md` 提到"剩余 40 张建议先建 typst shape 模板库"；
   若走矢量路线，本报告的字号模型（11px ÷ 画布宽）**完全不适用** ——
   矢量图可以直接设 pt，反而能彻底解决这一类问题。这是比"调画布"更根本的解法，
   但工作量更大，故未列为推荐路径
5. **未做视觉抽检之外的逐图人工阅读**。p56 的"工作目录"标签已用裁图目视确认约 3.7pt，
   与公式一致；其余按公式与实测互验推断（第 3.3 节，13/13 吻合）
