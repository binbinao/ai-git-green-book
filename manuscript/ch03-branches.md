# 第 3 章　分支：只是一张会移动的名牌

> 《Git 的概念地图》第 3 章 · 定调稿 v1.0
> 本章是全书概念主干的代表章：五张地图里最反直觉、也最能"一言祛魅"的一张。

---

## 3.1 场景引入：一次 0.3 秒的犹豫

周一早上，你准备开始写一个新功能。手指已经放到了回车键上，`git checkout -b feature/user-profile` 敲了一半，忽然停住了。

犹豫只有 0.3 秒，内容却是灵魂拷问：**这个命令会不会很"重"？** 毕竟要"开一个新的开发线"了——项目里有两千多个文件、三百多 MB 的历史，复制一份是不是要等半天？是不是该先把当前的工作 commit 干净再开分支？开完之后我的文件是不是都变了？

于是你先 `git status` 确认了一下，又 `git log` 看了一眼，最后还是按下了回车。命令瞬间完成，你松了口气，没细想为什么这么快。

同样的 0.3 秒犹豫，还会出现在这些时刻：

- 要删除一个合并完的分支时——"删掉之后，那些提交还在吗？"
- 在两个分支间来回切换时——"我的代码是怎么被'搬'来'搬'去的？"
- 看到 `HEAD detached at a1b2c3d` 的红色警告时——"我是不是把仓库搞坏了？"
- 听说大厂"一天创建几十个分支"时——"这么造，仓库不会爆炸吗？"

本章把这张地图彻底摊开。读完你会发现：上面所有问题的答案，都藏在 `.git` 目录里**总共不超过几百字节**的几个文本文件里。

## 3.2 祛魅时刻：分支到底"是"什么

先给结论，再给证据。

> **分支是一个指向某次提交的、可以移动的指针。它的全部实体，是一个文件里的一行文本。**

证据就在你的项目里。打开 `.git/refs/heads/` 目录，你会看到类似这样的东西：

```
.git/refs/heads/
├── main            ← 一个文件，里面是 41 个字节
└── feature-login   ← 一个文件，里面也是 41 个字节
```

`cat` 出来看，`main` 文件里的内容是：

```
a1b2c3d4e5f6...（40 个十六进制字符 + 换行符）
```

这 40 个字符是什么？是第 2 章讲过的：一次提交的 SHA-1 哈希——**整个项目历史中某一次快照的身份证号**。

没了。这就是分支的全部。没有代码副本，没有目录快照，没有隐藏的开发线。**一个分支 = 一个文件名 + 一次提交的哈希值。**

用一个比喻：把项目历史想象成一条项链，每颗珠子是一次提交，珠子和珠子之间用 parent 指针串起来。**分支，就是挂在某颗珠子环上的名牌。** "创建分支"是挂一张新名牌，"切换分支"是把视线移到某张名牌上，"删除分支"是摘掉一张名牌——珠子一颗都不会少。

### 三个直接推论

接受了"分支 = 指针"，三件日常怪事立刻有了答案：

**推论一：创建分支是免费的。**
`git branch feature-login` 做的事：在 `.git/refs/heads/` 里新建一个文件，写入当前提交的哈希。写一行字，耗时不到一毫秒。所以大厂"一天创建几十个分支"不是奢侈，是本来就没人把分支当成本——**该把分支当成本的团队，是把"合并分支"当成本，而不是"创建分支"。**

**推论二：删除分支不会删除提交。**
`git branch -d merged-branch` 摘掉的是名牌。珠子（提交）还挂在项链上——main 的历史里就有它们。至于那些"没合并就删掉"的提交，也还在，只是暂时没有名牌指向它们，Git 会在磁盘上替你保管大约 30 天（对象在 `objects/`，记录在 `logs/`，详见第 5 章 reflog）。所以删分支时的那句警告 `error: The branch is not fully merged` 才会写成那样——Git 不是不让你删，是提醒你"名牌摘了之后，这串珠子就只能靠 reflog 找回来了"。

**推论三：切换分支不是搬运代码，是"换一张快照铺开"。**
`git checkout main` 做的事：把 HEAD 指向 main 这张名牌，然后把 main 指向的那次**全量快照**展开到工作目录。不是"把 feature 的文件搬回去"，而是"把另一个存档读出来"。这也解释了为什么切换前 Git 会拦着你——工作区里未提交的改动会和"读档"冲突，Git 不愿意它们被覆盖。

```
      ┌─────────────────────────────────────────┐
      │              提交的项链                   │
      │                                         │
      │  (C1)──▶(C2)──▶(C3)──▶(C4)──▶(C5)       │
      │                            │      │     │
      └────────────────────────────┼──────┼─────┘
                             main ──┘      │
                             （名牌挂在 C4） │
                                  feature ─┘
                             （名牌挂在 C5）
```

*图 3-1：两张名牌挂在同一条项链的不同珠子上。这就是分支的全部。*

## 3.3 HEAD：指向指针的指针

地图上还有最后一个角色：**HEAD**。

`.git/HEAD` 也是一个文本文件，大多数时候它的内容只有一行：

```
ref: refs/heads/main
```

翻译：**"当前所在位置，是 main 这张名牌。"** 它不指向某颗珠子，而是指向一张名牌——一个指向指针的指针。

这个双层设计解释了 Git 的两种"站位"：

**正常状态**：HEAD → 分支 → 提交。你在 main 上提交一次，main 名牌自动前移到新珠子，HEAD 跟着 main，一切顺理成章。

**detached 状态**：HEAD → 提交（跳过了名牌）。当你 `git checkout a1b2c3d` 直接检出一颗珠子、或是在 rebase/bisect 的中间态时，HEAD 不再挂在任何名牌上。此时你完全可以正常写代码、正常提交——但新珠子**没有名牌指向它**，只有 HEAD 这个"手指"按着它。一旦你切走，手指挪开，这颗珠子就成了无主孤珠，30 天后被垃圾回收静悄悄带走。

所以那个红色警告 `HEAD detached at a1b2c3d` 的真实含义不是"你把仓库搞坏了"，而是：**"你现在站在一颗没有名牌的珠子上。如果你打算在这里干活，先给它挂张名牌。"** 处理方式温柔得出奇：

```
git switch -c rescue-branch     ← 就地挂一张名牌，珠子得救
```

甚至可以不救——detached HEAD 本来就是"看一看、试一试"的理想姿势：看看旧版本的代码什么样、跑一跑某个历史版本、做二分排查。看完切回来，什么痕迹都不留。**会这么用的人，已经不是在"用命令"，是在地图上行走。**

## 3.4 场景判断：什么时候开分支，什么时候不用

概念清楚了，落到场景里的问题是：**这事到底该不该开分支？** 给三条判断规则：

**规则一：会"污染"主干的，开分支。**
判断标准很简单——**这批改动合不合并进主干，是一个需要评审的决定吗？**
- 新功能：是，评审后合并 → 开分支。
- 修 bug：是 → 开分支。
- 改 README 错别字、调注释：不是，没有人想评审这个 → 直接在主干提交。
分支的本质用途是**隔离风险 + 提供评审边界**，不是为了仪式感。

**规则二：实验性的、可能整体扔掉的，开分支——而且不要命名的太隆重。**
试着重构一个模块，成不成心里没底？开 `spike/kondo-rewrite` 这种一次性的名字，写崩了整支删除，主干毫发无伤。"分支是免费的"（推论一）在这里兑现成真正的勇气：**试错的成本被压到接近零，你才有资格大胆试。**

**规则三：需要并行推进两条线时，开分支是唯一正解，不要用 stash 凑合。**
"先放着这个，去修个紧急 bug"，很多人的习惯是 `git stash` 存起来就走。stash 是个好的临时容器（第 13 章细讲），但它是"压栈暂停"，不是并行——栈里堆了三个改动再想逐个恢复时，痛苦才开始。正确做法：当前半成品**先 commit 到自己的分支上**（哪怕 message 写 "WIP"），然后从主干开新分支修 bug。半成品在它的分支上安睡，随时回来续写，还能看到清晰的时间线。commit 不神圣，它只是存档。

> 💡 **AI 时代补充**：并行场景还有一件更趁手的兵器——**worktree**（第 8 章专讲）。同一个仓库同时铺开多个工作目录，每个目录站一个分支，多任务真正"左右互搏"。让 AI 代理在独立的 worktree 里干活，你的主工作区一动不动。

## 3.5 AI 指令箱 · 分支

以下指令模板与工具无关（Claude Code / Cursor / Copilot / Aider / Windsurf 皆适用）。**使用前先看颜色标注**——本章指令多为绿色，但涉及"改主干"和"删除"的几条是黄色，别跳过确认。

**🟢 导航类（只读，放心用）**

- 「看一下当前仓库的分支全景：本地分支、远程分支、每个分支最后一次提交的时间和 message，以及哪些分支已经完全合并进 main、哪些还有未合并的提交。」
- 「我和 main 的分叉点在哪？用文字画出从分叉点到现在，我这边每颗提交和 main 那边每颗提交的项链图。」
- 「解释一下我现在是不是处于 detached HEAD 状态，如果是，是哪个操作导致的，有没有我可能丢掉的提交。」

**🟢 开分支类（低风险）**

- 「我要开始一个新特性，叫 user-profile。按我们仓库的分支命名惯例给我建分支并切过去。建好之后告诉我当前 HEAD 的状态。」
- 「在当前位置建一个叫 rescue/<今天日期> 的分支，把我现在 detached HEAD 上这几颗提交挂到这张名牌上。」
- 「把 main 上最新的 3 个提交中，属于我的那个（作者是我、message 是 xxx）搬到新分支 feature/quick-fix 上，并把 main 退回它提交之前。先列出你要执行的每一步和每一步的后果，我确认后再动 main。」
（最后这条是黄色指令，见下）

**🟡 需要盯着的（涉及改写或删除）**

- 「列出所有已经合并进 main 的本地分支。我想清理它们。先只列表，不要删。」→ 看完列表再补一句「确认，删除列表里的这几个，保留 xxx」。
- 「我刚才在 main 上直接提交了两个不想进主干的 commit。帮我把它们搬到新分支上并把 main 复原。给出完整命令序列，标注哪一步之后数据就回不去了。」

**训练用指令（陪练模式）**

- 「给我 10 道'这是不是该开分支'的判断题，场景覆盖修 bug、重构实验、改文档、半成品切换、紧急 hotfix。我答完你批改并讲评。」

## 3.6 执行后的世界

把本章指令交给 AI 执行后，`.git` 里发生了什么？透视一下：

| 你说的话 | AI 大概率执行 | `.git` 里的真实变化 |
|---|---|---|
| "建个分支 user-profile" | `git branch user-profile` | 新增文件 `refs/heads/user-profile`，41 字节 |
| "切过去" | `git switch user-profile` | `HEAD` 文件内容改为 `ref: refs/heads/user-profile`，工作目录重新铺开 |
| "删掉这个合并完的分支" | `git branch -d feature-x` | 删除文件 `refs/heads/feature-x`。提交对象原封不动 |
| "看看 3 个月前的代码" | `git checkout <sha>` | `HEAD` 直接写入那个 sha（detached），没有分支被创建 |
| "把我的提交搬过去" | `git cherry-pick <sha>` | 复制提交对象、生成**新** sha，目标分支指针前移 |

看懂这张表，你就理解了本章的全部：**五句话，五个文件操作，没有一次是"搬运代码"。**

## 3.7 命令侧栏

```
git branch <name>        # 挂一张新名牌（不动 HEAD，不切换）
git branch -d <name>     # 摘名牌（-D 强制摘，含未合并警告的关闭）
git switch <name>        # 把 HEAD 挪到某名牌上（checkout 的现代马甲）
git switch -c <name>     # 挂名牌 + 挪过去，一步完成
git checkout <sha>       # detached：HEAD 直接按住某颗珠子
git branch -a            # 列出全部名牌（本地+远程）
git cherry-pick <sha>    # 把某颗珠子复制到当前项链末端
```

不需要背。需要时回来看，或者直接说人话让 AI 翻译。

## 3.8 本章小地图

```
分支 = refs/heads/ 里的一个文件 = 指向某次提交的可移动指针
  │
  ├─ 创建：写一行字（免费）        ──▶ 所以试错应该大胆
  ├─ 删除：摘名牌（提交还在）      ──▶ 所以删除不需要恐惧
  └─ 切换：HEAD 挪位 + 读档铺开    ──▶ 所以未提交改动会被拦下
  
HEAD = 指向指针的指针
  ├─ 正常：HEAD → 分支 → 提交
  └─ detached：HEAD → 提交（无名牌）
        └─ 新提交会成"无主孤珠" ──▶ 想留住就 switch -c 挂名牌

什么时候开分支：
  1) 需要评审边界（功能/修复）     2) 实验可能整体扔掉     3) 需要真并行（别用 stash 凑合）
```

**三大典型误解拆解**

1. **"分支是一份独立的代码拷贝。"** ——最常见的妄想，来自 SVN 时代肌肉记忆。其实 SVN 服务端的分支也是廉价副本（常数时间、常数空间）；真正贵的是**切换**——`svn switch` 要把整个工作副本更新一遍。Git 与 SVN 的真正差别不在复制成本，而在"分支是一个目录"和"分支是一行哈希"这两个心智模型。把 SVN 的直觉带进 Git，你会系统性地低估分支（不敢开）或高估删除（不敢删）。
2. **"删分支把我的代码删没了！"** ——删的是名牌。提交要么已在主干项链上，要么还在 30 天的托管期里（`git reflog` 可救）。真正的数据丢失只有一种途径：对象被垃圾回收，而那需要名牌消失 + 30 天 + `git gc` 三个条件同时满足。
3. **"detached HEAD 是危险状态/错误状态。"** ——它是**设计出来的**查看与试验姿势，rebase、bisect 这些高级操作全都在 detached 状态里工作。危险的从来不是状态本身，而是"在 detached 状态里提交、然后没挂名牌就切走"这个组合。见到警告，要么挂名牌，要么看完就走，两条路都安全。
