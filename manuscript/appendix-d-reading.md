# 附录 D　延伸阅读

> 《Git 的概念地图》附录 D · v1.0
> 体例：按**阅读目的**分五类；每条给出**是什么 / 为什么值得读 / 读前提醒**（含本书哪一章已铺垫基础）。
> 用法：本书结尾不是句号，是分岔口。挑对应你现在的问题类型的那一类往下走。

## 一、官方文档类：手边常备的参考

### 1. **Pro Git**（第二版，Scott Chacon & Ben Straub，中文完整版）
- **是什么**：Git 官方推荐的系统教材，覆盖从"什么是 Git"到内部对象模型的全部内容。免费在线阅读，也有印刷版。中文版由社区翻译，跟进较及时。地址：`git-scm.com/book/zh/v2`。
- **为什么值得读**：这是**唯一一本官方级别的百科全书式 Git 教材**。当你需要"某个命令的所有参数、所有场景"这种参考级信息时，Pro Git 是最全的中文资源。第 10 章"Git 内部原理"尤其经典。
- **读前提醒**：Pro Git 是**命令目录型**结构（章 = 功能模块），与本书**概念地图型**结构互补而不重合。**读它时最容易迷失在参数森林里**——建议**先读完本书第 1–5 章建立概念地图**，再用 Pro Git 作为"某具体功能怎么用"的查询手册，别当入门书从头啃。本书第 1–5 章覆盖了 Pro Git 前 3 章的所有核心概念。

### 2. **Git Reference Manual**（`git-scm.com/docs`）
- **是什么**：Git 每条命令的官方手册页（man page），逐参数解释。本地也可通过 `git help <command>` 查看。
- **为什么值得读**：**唯一权威**。SO 上一半的"神奇命令"其实是 man page 里明写的用法。你越熟悉概念，读 man page 越快。
- **读前提醒**：手册页**假设你已经理解 Git 的对象模型和三区模型**，直接翻会像读法律条文。建议**在本书附录 A 命令速查表**里先找到你要的命令、看清它属于哪张概念地图，再去 man page 深挖参数。**永远不要以 man page 为起点学新概念**。

## 二、交互学习类：手把手把概念在屏幕上"跑"一遍

### 3. **Learn Git Branching**（`learngitbranching.js.org`）
- **是什么**：一个基于浏览器的交互式 Git 沙箱，把提交、分支、rebase、cherry-pick 全部可视化为节点图。每关一个挑战，你敲命令，图实时变化。有中文界面。
- **为什么值得读**：**"分支只是指针"这句话，Learn Git Branching 用动画演给你看**。你在本书第 3 章读到的"项链-珠子-名牌"比喻，在这里能亲手拨动。特别是 rebase 和 cherry-pick 关卡，图形变化过程比任何文字都直观。
- **读前提醒**：它**只覆盖分支/合并/rebase 这一小片**，不讲远程、不讲三区、不讲事故恢复。**建议在读完本书第 3、5 章后玩**——你会发现自己已经能猜出每关的图会怎么动，那就是概念地图内化的信号。**不要当作系统学习工具**。

### 4. **Oh Shit, Git!?!**（`ohshitgit.com`，也有印刷版 *Dangit, Git!?!*，作者 Katie Sylor-Miller & Julia Evans）
- **是什么**：一本"事故→解药"式的小手册。每一页一个惨案（"我 commit 到错的分支了"、"我不小心把 secrets 推上去了"），下面直接给解救命令。有中文译版流传。
- **为什么值得读**：**心慌时的止血带**。当你已经在冒冷汗、没时间读概念时，它给你**能马上敲的、有解释的解药**。语气还很治愈（每一页开头都是 "Oh shit,"），能让你在事故里保持冷静。
- **读前提醒**：**它是急救手册，不是教材**——只讲救火，不建概念地图，只知答案不知因果。**本书第 10 章"事故恢复"的哲学正好相反：先讲 reflog + Git 几乎不扔东西的原理，再讲救援命令**。建议**把 Oh Shit Git 收藏在书签栏应急，把本书第 10 章的心智模型装进脑子**——这样即使 Oh Shit Git 上没写你这个场景，你也能自己推演出救援步骤。

### 5. **First Aid Git**（`firstaidgit.io`）
- **是什么**：一个可搜索的 Git 常见问题与命令解释的小站，社区维护。类似 Oh Shit Git，但更偏问答式索引。
- **为什么值得读**：**关键词友好**——你脑子里冒出的是 "detached HEAD"、"undo last commit" 这类词，直接搜就能定位到解答。适合手边总放一个的 tab。
- **读前提醒**：与 Oh Shit Git 一样是**索引型资源**，不建立系统模型。**本书第 10 章 + 附录 C 术语表**给你的是建模能力；First Aid Git 给你的是速查便利，两者搭配用。

### 6. **Git Immersion**（`gitimmersion.com`）
- **是什么**：一份 50+ 关的自导式实战教程，从 `git init` 一路走到 rebase 和 remote，每步给出精确命令与预期结果。
- **为什么值得读**：**如果你完全没有键盘 Git 手感**——比如一直用 GUI 或 IDE 内嵌 Git——它是把命令跑一遍建立手感的最短路径。
- **读前提醒**：**动作导向，弱概念**。跑完它你会"能敲"，但不一定"理解"。本书第 1–5 章补的正是这一课。建议**先看本书概念章 → 再用 Git Immersion 上手 → 回本书场景章**。

## 三、深度理解类：想看清 `.git/` 里到底装了什么

### 7. **Git Internals**（Scott Chacon，短小 PDF，早期免费版）
- **是什么**：GitHub 联合创始人、《Pro Git》作者 Scott Chacon 写的一本小书，专讲 Git 的对象模型、引用系统、pack 文件、传输协议。开篇那句"我看到一个又一个开发者爱用 Git 但从没真正理解它"就出自这里。
- **为什么值得读**：**如果你想彻底祛魅，这是最短的路径**。看完你会明白：`git commit` 就是往 `.git/objects/` 里塞几个新对象、改一个 ref。全书能压缩成"对象 + 引用"两个词。
- **读前提醒**：**风格偏工程手册，不是通俗读物**——但如果你已经读完本书第 1、2 章，会发现它讲的正是你已经有心理模型的东西，只是更细。**建议作为本书第 13 章"进阶概念"读完后的下一步**。

### 8. **Pro Git 第 10 章：Git 内部原理**（`git-scm.com/book/zh/v2/Git-内部原理-底层命令和高层命令`）
- **是什么**：Pro Git 里最硬核的一章，用底层命令（`hash-object`/`cat-file`/`update-ref`……）从零重建对象、tree、commit、branch，让你亲手证实 Git 的物理机制。
- **为什么值得读**：**这一章可以独立成书**。它是"Git 到底是什么"的最短官方答案。跟着敲一遍，你就再也不会怀疑本书说的"分支只是一行文本"了。
- **读前提醒**：**建议在本书第 1、2、3 章之后专门抽一晚上读它**。跟着命令敲，别只读。**如果你只想从 Pro Git 读一章，就读这一章**。它比其他 9 章加起来更能改变你看 Git 的方式。

### 9. **Git from the Bottom Up**（John Wiegley，免费小书）
- **是什么**：从对象层一路往上讲 Git 的短篇讲义，风格偏学术。
- **为什么值得读**：**结构与 Git Internals 类似，语言更简练**。作为第二本原理书交叉验证，可以帮你把对象模型这个心智模型钉得更牢。
- **读前提醒**：**内容与 Git Internals、Pro Git 第 10 章大量重叠**——三本挑一本读通即可，别为完成主义三本都啃。**推荐优先 Pro Git 第 10 章**，中文翻译最好且可交叉验证。

### 10. **Think Like (a) Git**（`think-like-a-git.net`）
- **是什么**：几页短文（作者 Sam Livingston-Gray），从图论视角讲 "commit 是有向无环图上的节点"。停更多年，但仍是网上"用一张图理解 Git"最好的短文之一。
- **为什么值得读**：**本书的理念前辈**。它是市场上（在本书之前）最接近"概念地图型 Git 教材"的尝试，只可惜篇幅太短、无 AI 时代。**读它就当读一份宣言**：确认你走在对的方向上。
- **读前提醒**：**只有几页，几十分钟能读完**，不能当教材。**本书第 3、5 章是它的完整化 + 场景化版本**。

## 四、AI × Git 类：把新分工落到具体工具上

> **通用提醒**：本类文档变化极快，一年前的写法今年可能已废弃。请以官方站点最新版本为准，本附录只对**能力形状**做描述。

### 11. **Claude Code 官方文档**（`docs.claude.com/en/docs/claude-code`）
- **是什么**：Anthropic 官方的 CLI 编码代理文档，讲如何在终端里让 Claude 直接读写文件、执行命令（含 Git）、审阅 diff。含权限模型、hook、MCP 集成。
- **为什么值得读**：**把本书第 12 章的"红黄绿分级"和"确认关卡"变成真实工具的配置项**。你会看到 Anthropic 官方推荐的权限最小化设置、审计日志、危险操作确认策略——与本书主张的框架**高度重合**（不是巧合，是同一套安全直觉）。
- **读前提醒**：**先读本书第 0、12 章建立"你出意图、AI 出语法"的分工与安全边界**，再读官方文档时就会看到"你为什么该这样配"，而不是"这个开关是干嘛的"。**不要一上来打开所有权限**。

### 12. **Aider 文档**（`aider.chat`）
- **是什么**：一个开源的 AI pair-programming CLI，深度集成 Git——每次 AI 改动自动 commit，PR-friendly 工作流。文档含 `/undo`、`/diff`、`/commit` 等命令。
- **为什么值得读**：**Aider 是把 Git 作为"AI 安全网"这一理念做得最彻底的工具**——每一次 AI 生成的改动都是一个可 revert 的提交。读它的文档就是在读"如何让 Git 反向保护你不被 AI 搞砸"的实践方案。
- **读前提醒**：**Aider 的自动 commit 会让历史很啰嗦**——理解本书第 5、6 章后，你会用 `rebase -i squash` 收拾好这些"AI 珠子"再合入主干。**别害怕历史脏，只要它属于你未推送的部分**。

### 13. **GitHub Copilot 文档**（`docs.github.com/en/copilot`）
- **是什么**：GitHub 官方 Copilot 文档，含 CLI、Chat、Workspace、PR summarization 等多个产品的 Git 相关能力。
- **为什么值得读**：**理解"平台原生 AI"如何看待 Git**——Copilot 在 PR 描述、commit message、review comment 上的自动化，与本书第 6、11 章的场景直接对上。
- **读前提醒**：**功能变化极快**，别把某个具体功能当作技能沉淀；把注意力放在**"这类能力如何提高我第 6 章的提交质量、第 11 章的评审效率"** 这一层。这一层是稳定的。

### 14. **Cursor / Windsurf / Continue / Cline 等编辑器代理的文档**（各自官网）
- **是什么**：一系列以 VS Code 风格 IDE 为载体的 AI 编码代理。Git 操作通常通过内置终端 + 权限确认对话框完成。
- **为什么值得读**：**你在实际工作中大概率会用其中一到两个**。它们的差异不在"能不能操作 Git"（都能），而在**"怎么让你确认危险操作"**——这是你选工具时应该盯着看的点。
- **读前提醒**：**盯"权限模型"和"审计日志"两栏读**。任何一个不给你**清晰的操作预演 + 事后可回溯**的工具，本书第 12 章视为红线。**别被功能演示迷惑**，回到安全底盘。

### 15. **Model Context Protocol（MCP）官方文档**（`modelcontextprotocol.io`）
- **是什么**：Anthropic 主导、行业跟进的开放协议，让 AI 助手能以受控方式接入外部工具/数据源，包括 Git 服务器。
- **为什么值得读**：**如果你想给团队的 AI 助手挂上"内部 Git 服务器只读访问"或"仅个人分支可 push"这种能力，MCP 是当前最规范的做法**。本书第 13 章会展开。
- **读前提醒**：**MCP 是协议层，不是产品**——读文档时留意"能力边界如何声明、如何审计"。**本书第 12 章的最小权限原则**是评估任何 MCP server 时的判据。

## 五、本书未展开话题的接续阅读

### 16. **Git LFS 官方文档**（`git-lfs.com`）
- **是什么**：Git 的大文件存储扩展。把媒体文件、二进制资产、模型权重存到 LFS 服务器，Git 里只留一个指针。
- **为什么值得读**：**如果你在游戏、AI、设计、视频行业**，早晚遇到"仓库炸到十几 GB"的问题。LFS 是当前主流解法。
- **读前提醒**：**本书第 13 章只做了简介**。LFS 的坑在于**"不是所有托管平台都完美支持"**——先确认你的 GitHub/GitLab/内部服务器是否有 LFS 配额与备份策略，再全面切换。**LFS 迁移历史文件是可逆但麻烦的操作**，动手前做完整备份。

### 17. **Monorepo 相关：`monorepo.tools` + Google/Meta/Uber 的工程博客**
- **是什么**：Monorepo（单体仓库）策略的资源集散地，含工具（Nx、Turborepo、Bazel、Pants）与大厂经验帖。
- **为什么值得读**：**当你的组织把 3+ 个项目塞进同一个 Git 仓库时**，Git 会开始遇到规模问题（大 checkout、稀疏克隆、CI 触发范围……）。这些帖子讲的是"人家几万工程师踩过的坑"。
- **读前提醒**：**大多数团队不需要 Monorepo**——它是复杂度换协同的权衡。先在本书第 7 章的分支策略框架里确认你的规模是否值得这份复杂度。**别为了赶时髦切 monorepo**。

### 18. **Git Hooks 相关：`githooks.com` + husky / lefthook / pre-commit 项目文档**
- **是什么**：Git 钩子的工作原理与实用工具。让 hooks 能被团队分发、跨平台跑、和包管理器集成。
- **为什么值得读**：**hooks 是让"约定"变成"墙"的最短工程手段**。commit message 校验、代码格式化、密钥泄漏检测，都能在 pre-commit / pre-push 阶段拦下来。
- **读前提醒**：**本书第 13 章只做了简介**。**hooks 是可执行脚本，本身是一个供应链攻击面**（第 12 章）——审 hooks 脚本要像审 CI 一样审。**避免让 AI 直接生成并安装 hooks**，那是本书划为红线的组合。

### 19. **《SQL Antipatterns》**（Bill Karwin，Pragmatic Bookshelf）
- **是什么**：不是 Git 书，但结构与本书最亲——"错误场景 → 为什么错 → 正确解法"。
- **为什么值得读**：**如果你觉得本书第 2 部分场景章的读法很过瘾**，你会喜欢这本书用同样的方式教 SQL。也可以让你反过来看清本书的结构选择。
- **读前提醒**：SQL 与 Git 无关，纯为阅读体验推荐。

### 20. **《Designing Data-Intensive Applications》**（Martin Kleppmann；第 2 版与 Chris Riccomini 合著，中文《数据密集型应用系统设计》）
- **是什么**：全书讲分布式系统概念地图，无代码清单，是"概念地图型技术书"的典范。英文第 2 版已于 2026 年出版（O'Reilly），中文第 2 版同年上市。
- **为什么值得读**：**如果本书让你意识到"看清概念比背命令值钱"**，DDIA 会把这个信念在另一个更大的领域里再次证明。它是许多工程师"读书方式被永久改变"的那本书。
- **读前提醒**：**厚，但每章独立**。读的时候留意作者如何用一整章展开一个概念、如何用权衡代替方案——那是本书试图学习的写作范式的更宏大版本。

## 六、如何组合使用这份书单

按你现在的痛点挑：

- **概念模糊、想彻底祛魅**：Pro Git 第 10 章 → Git Internals → Git from the Bottom Up（三选一或按顺序）。
- **想把分支/rebase 玩通**：Learn Git Branching + 本书第 3、5 章反复对照。
- **刚出事、要救火**：Oh Shit Git → First Aid Git，同时把本书第 10 章内化——**你的目标是有一天不再需要它们**。
- **要把 AI 用起来但不想被坑**：本书第 12 章 → Claude Code / Aider 官方文档 → MCP 文档；**永远保留最小权限直觉**。
- **组织层面的下一步**：Monorepo tools + LFS + Hooks，配合本书第 7 章的策略判断力。
- **想让"读技术书"这件事本身升级**：DDIA + SQL Antipatterns，看看概念地图型和场景决策型在别的领域怎么开花。

## 七、一个不列进书单的建议

**这份书单不该被你按顺序读完**。它是**面对不同问题时的分岔口**，不是**必读清单**。任何以"读完 20 本书才算真会 Git"作为里程碑的努力，都是本书开篇第 0 章说的 cargo-cult 的另一种形式——**把仪式（读书）当因果（理解）**。

真正的进步的信号，不是你读了多少，而是——

> **下一次某位同事在群里贴出一条 `git reset --hard origin/main` 求助时，你能不假思索地说出：**
> **"先别急着敲。你上一次 fetch 是什么时候？现在 reflog 里最新一条是什么？"**

那一刻，你已经不再需要这份书单，因为**你自己就是那份书单**。
