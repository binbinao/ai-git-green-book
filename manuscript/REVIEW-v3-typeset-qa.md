## 二、P0 明细（必须改）

### P0-1　中文引号全书缺失

**现象**：全书中文引号使用**零**。所有引语用的是 ASCII 直引号。

| 字符        | 码位              | 全书出现             |
| --------- | --------------- | ---------------- |
| `"`       | U+0022          | **4 653**        |
| `'`       | U+0027          | **450**          |
| `“`       | U+201C          | **0**            |
| `”`       | U+201D          | **0**            |
| `「` / `」` | U+300C / U+300D | 431 / 431（配平，正常） |

`「」`（AI 指令模板）用得非常正确且左右配平，说明模板层没问题——**问题恰恰在于围绕 `「」` 的中文散文全部退回了直引号**。

**加重情节**：相邻直引号在视觉上**坍缩**成一对空引号。例（p39，第 1 章 AI 指令箱）：

```
出 8 个判断题：'仓库到底在哪里''远程和本地的关系''clone 到底做了什么'…
```

读者看到的是 `''`，不是引语。同一页还出现 **半角逗号混入中文**：`误解三："我本地这份是'副本',服务器那份才是'主'。"`

**成因**：`build.sh` 有意关闭 pandoc 智能引号（`-f markdown-smart`），以避免中文直引号被弯成错误方向；但关闭后**没有任何一层补回正确的 `“ ”`**，于是"避免错方向"变成了"完全没有中文引号"。

**修法**：两条路，建议 A 为主。

- **A（首选，改后处理）**：在 `postprocess.py` 增加引号配对 pass——以「行内成对出现」为准，把 `"` 按奇偶位置替换为 `“` / `”`，`'` 同理；跳过「代码围栏内」与「已配平 `「」` 内」的段落，避免误伤 `git commit -m "..."` 这类真代码。文中实测代码块内的 `"` 与散文中的 `"` 可用字体（Sarasa vs Songti）区分，判定可靠。
- **B（改稿件）**：源稿 13 个正文文件 + 附录直接批量替换；工作量大但一次到位。

同时清理那 1 处半角逗号（`'副本',服务器`）。

### P0-2　42 处字面反斜杠被印进书里

**现象**：书里真的印出了反斜杠 `\`（U+005C）。

```
p29  .git/refs/ ← ★ 引用表：所有\"名字\"都在这里
p33  │← 从 .git 里\"读档\"铺出来的工作区
p53  │  的一个\"入库单\"     │
p63  ├─ 暂存区  下次 commit 会包含什么的\"入库单\"
```

**取证**（p33 精确码位）：`里` U+91CC → `\` **U+005C** → `"` U+0022 → `读` → `档` → `\` → `"` → `铺`。反斜杠是实体字符，不是提取噪声。

**分布**：**42 处 / 28 页**，全部落在代码与 ASCII 图块内（Sarasa 字体），**散文层为 0 处**。受影响页：29, 33, 53, 56, 62, 63, 92, 100, 101, 133, 180, 181, 193, 194, 195, 332, 339, 341, 350, 361, 384, 385, 387, 388, 420, 421, 431, 432。

**成因（已定位）**：源稿用 `\"` 转义引号（`grep -c '\\"'` 命中 13 个正文文件，合计 880+ 处）。

- **散文层**：pandoc 读 markdown 时把 `\"` 还原为 `"` → 反斜杠消失（所以看不见，但直接喂给了 P0-1）。
- **代码围栏内**：markdown 围栏内容不做转义还原 → `\"` **原样输出**，于是印在书上。

**修法**：在 `assemble.py` 或 `postprocess.py` 增加一步：**围栏块内的 `\"` → `"`**（同时把 P0-1 的引号配对 pass 覆盖到围栏内）；或者干脆把源稿里所有 `\"` 归一为 `"`，让两层的归因消失。

**现象**：插图下方印出的不是中文图题，而是**素材文件名 + 制作过程备注**：

```
p18   图 0 mini-map（archify 优化版，本章导航）
p18   图 0 cargo-cult（archify 优化版）
p29   图 1 clone（archify 优化版）

p392  图 13 cherry-pick（archify 优化版）
p429  图 14 knowledge-map（archify 优化版）
```

**三重问题**：

1. `（archify 优化版）` 是**内部制作备注**（"archify" 是出图工具名），不该进成品书；
2. `mini-map` / `cargo-cult` / `three-areas` / `three-gates` 是**英文素材 slug**，不是中文图题；
3. `10-decision-tree.architecture（archify 优化版，与原 ASCII 图内容相同）` —— **文件名带点号、缺「图」字前缀**，且"与原 ASCII 图内容相同"是**编辑内部说明**，读者无从理解。

**修法**：在 `build/figures/` 旁边建一份 `figures.yaml` 映射（`slug → 中文图题 + 纠错句`），注入脚本只读该映射；caption 模板去掉 `（archify 优化版…）`。图题应写成内容性说明，例：`图 0-1：Cargo-Cult 循环——遇到问题就搜命令，命令失灵后更慌。`

### P0-4　封面书名断行破损

**现象**（p1 渲染目视）：封面主标题断成

```
Git 的概念地
[ 图 ]          ← 单字成行，且被反白方块包裹
```

书名《Git 的概念地图》被拆在「地 / 图」之间，第 2 行只剩一个「图」字，视觉上像一块补丁。副标题同样断行不雅：「用自然语言驾驭版本控制 —— 一本不背命令的」/「Git 书」，第 2 行只有「Git 书」，且因两端对齐在「的」与「Git」之间拉出大空档。

### P0-5　ASCII 箱线图跨页断裂 / 内部折行

**现象 A——跨页孤儿碎片**：**22 页**的页首第一行代码就是箱线图的**中段**（`│` `├` `└` 开头，无上边框），即一张图被页断开，下一页只剩残片：

```
p30   │   ├── tags/          ← 标签
p33           │ src/  README.md  ...       │← 从 .git 里\"读档\"铺出来的工作区
p63     └─ 元信息 + SHA 身份证（改任何一点，SHA 就变，就是新珠子了）
p101    ├─ 物理上：一个文件，40 个字符（和本地分支一模一样）
p202       │ 主工作台     │  │ 工作台 A     │  │ 工作台 B     │
…（另见 p53/71/138/140/164/195/223/241/256/300/309/341/342/357/371/384/431）
```

**现象 B——图内文字被折行撕碎**：p267（第 10 章事故恢复决策树）整张图被换行拆散，框线错乱、词被劈开：

```
      │  你们有没有"多个版本同时在  │
有 → 从旧 clone        没 → 事情
变严重
                         │ 救出历史    │  （敏
感文件已扩散
                         │ 用 revert 或再 │  珠子"（第 5 章
revert|
```

p76 同类问题：小地图末行 `（别用 stash 凑合）` 被挤到框外单独成行。

**成因**：ASCII 图作为普通段落参与断行——既允许跨页，也允许在行内换行；而图内是固定宽度艺术字，一旦换行，边框与列对齐全毁。

**修法**：

1. 所有 ASCII 图块包 `block(breakable: false)`，禁止跨页；
2. 图块字号自适应：宽度超版心的图按比例缩字号（或用 `scale()`），**宁可缩小也不换行**；
3. 对放不下的长图，改排版策略（横排/拆分/重绘）而非让它挤断；
4. 重新跑 QA 复核「页首孤儿碎片 = 0」。

## 三、P1 明细

### P1-7　红黄绿安全标记的字体未嵌入

`AppleColorEmoji` 是 **Type3 字体、无 FontFile**——即 138 页上的 emoji 不是可嵌入字体，而是 Type3 字形程序。全书 emoji 实测：🟢 **229**、🟡 **186**、🔴 **29**（合计 444 个安全标记）+ ⭐26 / ✅21 / 🤖16 / ❌10 / ⚠9 / ✨2 / 🚫2 / 💡1 / 📋1 / 🚨1。

**影响**：红黄绿分级是本书核心卖点之一，却在印刷 preflight 里会被判"字体未嵌入"；不同 RIP 可能出现黑块、空框、错位，甚至丢失颜色语义。其余 17 款字体**全部正常嵌入**（`FontFile2`/`FontFile3`）。

**修法**：把 🟢🟡🔴 换成**矢量实现**——模板内联 SVG 圆点（`circle()`），或改用「●＋颜色」的中文字符方案；同时把散落的装饰 emoji 一并处理或删除。这同时能解决"emoji 风格与全书排版语言不搭"的观感问题。

### P1-8　全角收尾标点前被排入中西文间隙

**现象**（p46 逐 span 实测）：正文 `你刚才那条 \`--amend\`，到底做了什么？\`

```
x0=267.95 x1=299.45  Sarasa-Fixed-SC-Regular  '--amend'
x0=299.45 x1=304.51  DejaVuSansMono          ' '        ← 5.06pt 空格
x0=304.51 x1=388.51  STSongti-SC-Regular     '，到底做了什么？'
```

源稿该处是 `` `--amend`， ``（**无空格**，码位 `0x60, 0xff0c`）——空格是**排版引擎插入**的。视觉上如「--amend ，」、「project.git ）。」（p33 目视确认）。

**规模**：全书 **514 处**，按后随标点分布：`。`128、`，`117、`、`108、`）`95、`：`36、`；`29、`」`1。

**修法**：模板侧关掉/收窄 `cjk-latin-spacing` 在「Latin → 全角收尾标点」边界的插入（Typst 条件下可对特定标点做 lookbehind 处理，或在 `postprocess.py` 对 `[Latin] + space + [。，、；：）」]` 做清除）。这是本书**观感最脏的一类细节**，514 处散布在每一页，值得优先修。

### P1-9　DejaVuSansMono：为渲染空格而无谓嵌入

实测该字体在 **401 页**渲染了 **2 990 个空格 span**（宽度 4.58 / 4.82 / **5.06** / 5.78 / 6.98 pt），**可见字形 0 个**。也就是说它 100% 只服务于 P1-8 那类被排入的间隙空格。

**影响**：与 `build/README.md`「代码 = Sarasa Fixed SC」的规格不符（字体清单里多出一款等宽体）；PDF 资源臃肿、排版引擎的字体回退路径不可控。修掉 P1-8 后应复核该字体是否随之消失。

### P1-10　PDF 元数据全空

```
title: ''    author: ''    subject: ''    keywords: ''
creator: 'Typst 0.15.1'     producer: ''
```

**影响**：阅读器标题栏/书库/检索系统拿不到任何书目信息，属出版元数据缺失。

**修法**：模板里设置 `document(title: "Git 的概念地图——用自然语言驾驭版本控制", author: "binbinao", keywords: (...), date: ...)`。

### P1-11　表格单元格底色不一致 + 缺表头

p39「执行后的世界」三列表：**3 个单元格为深青底白字**（fill `(0.06, 0.30, 0.36)`），其余为浅灰底（`(0.91,0.94,0.94)`）——同一张表内两种底色，且分布无规律（第 1 行第 3 格、第 3 行第 1 格）。

同时**全表没有表头行**：三列语义（你说的话 / AI 执行的命令 / `.git` 里的真实变化）只写在 `STYLE-NOTES.md` 里，读者在书上看不到列义。

p352 顶部另有一处疑似被页截断的表体：只剩两行内容（`服务端扫描 / 签名者 / AI 拉的东西`、`历史清理`）、无表头、列宽错位，且其图题写的是"Git 安全的三张地图"——图题与所见内容不匹配。

**修法**：统一次行底色规则（表头深、正文浅，或全部浅底）；补表头行；长表设 `repeat-header` 并在跨页处保持表头重复。

### P1-12　章扉题字全大写 `GIT`

19 处章/附录扉页顶部印的是 **`GIT 的概念地图`**（全大写），而正文书眉印的是 **`Git 的概念地图`**（正确）。Git 官方品牌写法恒为 `Git`，`GIT` 是常见误写。全书 `GIT` 出现 20 次、`Git` 1 134 次——这 20 次全在章扉。

**修法**：模板章扉题字改为 `Git 的概念地图`，与书眉统一（或让章扉题字与偶数页书眉共用同一个字符串常量）。

### P1-13　表内代码 token 被折断

p39 第 4 行第 2 格：`git count-objects -vH` 被断成两行，`-` 留在上一行、`vH` 落到下一行——**命令行开关被从中劈开**，读者复制即错。同页 `ls .git/ 、cat .git/HEAD` 也被折行。

**修法**：表内代码单元格设 `breakable: false` / 允许溢出，或收窄字号；至少保证 `-vH` 这类 token 不被断开。

### P1-14　版本 / 日期 / 规模四处不自洽

| 位置                | 声明                                                   |
| ----------------- | ---------------------------------------------------- |
| 封面 p1             | `2026`                                               |
| 扉页 p2             | `1.1（第二轮修订版）· 2026-09-16`                            |
| 版权页 p3            | `2026 年 9 月 · 1.1（第二轮修订版）`                           |
| `README.md` 末尾    | `2026-09-15 完稿 · 15 章 + 4 附录 · 约 14.7 万字`            |
| `build/README.md` | `1.1（第二轮修订版）· 588 页 · 6.0 MB · 2026-09-16 书稿`        |
| **实际 PDF**        | **534 页 · 10.28 MB · 生成于 2026-10-04 10:52 · 元数据无日期** |

**页数差 54 页、体积差 4.3 MB**，且 `build/README.md` 的管线描述里没有"插图注入""图题生成"这两个现已存在的步骤（`inject_mini_map*.py` 连维护说明都没有）。文档已明显落后于构件。

**修法**：确立单一版本源（建议就放在 `book.typ` 的前置页块，其余文档引用它），构建时把页数/日期写回 `build/README.md`；把新增的注入步骤补进管线说明。

### P1-15　总页数非 4 的倍数

534 页，`534 mod 4 = 2`。开本 172×248mm 属常规 16 开装订体系，**配帖要求总页数为 4（胶订）或 8/16（锁线）的倍数**；当前需补 2 页空白（放在附录 D 之后）才能落版。

**修法**：模板末尾补 `pagebreak()` 至 4 的倍数，或接受自出版电子版不补（需在版权页注明"电子版"以免误导）。

## 四、P2 明细

### P2-16　章扉落页奇偶不一致

书内 19 处章/附录扉页中，**13 处落在奇数页（右页）**，**6 处落在偶数页（左页）**：


```
偶数页（左页）章扉：第 1 章 p26、第 13 章 p390、附录 A p426、附录 B p446、附录 C p476、附录 D p506
奇数页（右页）章扉：p15 / 45 / 67 / 79 / 105 / 145 / 167 / 197 / 227 / 261 / 315 / 347 / 523
```

同类页起页规则应统一。行业惯例：**章级可"另面起"，但同一本书内应一致；附录属篇级划分，宜"另页起"（必落右页）**。当前附录 A/B/C/D 有 4 处落左页，与"另页起"不符。

**修法**：模板对章扉统一 `pagebreak(to: "odd")`（或全书统一 `to: "auto"`，二选一，不可混）。

### P2-17　行首 / 行末禁则

| 违规          | 数量     | 位置                                                                                                                                                                                                                    |
| ----------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 行首全角分号 `；`  | **2**  | p253 `；把分支名牌恢复到 rebase 开始`、p435 `；纠正 message 风格`                                                                                                                                                                      |
| 行首破折号 `——`  | **54** | p17/27/35/38/42/53/57/58/73/81/95/106/141/142/155/178/183/196/199/202/223/243/244/246/247/253/258/263/268/280/281/288/289/303/311/323/330/331/338/364/367/387/394/396/399/403/405/412/422/435/443/474/478/485/487/496 |
| 行末全角前括号 `（` | **2**  | p205 ×2                                                                                                                                                                                                               |

分号与行末前括号是**硬违规**（须修）；破折号行首 54 处在部分出版社属禁则、部分允许，建议与排版方确认口径后统一处理——若按禁则修，用 `——` 前加 `no-break` 绑定前字即可。

（另核查：行首出现 `（`、`「` 共 213 行，行首坐标 x0=68pt < 版心左界 73.7pt，属**标点悬挂**，是正确的中文排版行为，**不是**问题。）

### P2-18　用全角空格做缩进

全文 U+3000（全角空格）共 538 处，其中 **537 处**是行首缩进，典型如术语表的 `　常见混淆：`。模板已对段落设 `first-line-indent: 2em`，再叠一个全角空格会形成**双重缩进**，且是"用空格排版"的非规范做法。

**修法**：删掉源稿里的行首 U+3000，改用列表项 / `hanging-indent` / 段落样式表达层级。

### P2-19　术语「标签」越界 + 附录 C 条数不同步

**术语**：全书 `标签` 21 处 / 14 页，`名牌` 200 处（主体已按 §四口径收敛）。但有两处**越出"标签 = git tag"的锁定口径**：

- p183 `给 AI 的 PR 打标签`（讲的是 GitHub **label**）
- p198 `两个 Chrome 标签页`（浏览器 **tab**）

建议分别改为「打标记 / 加标签」以外的说法（如 GitHub label → 「PR 标记」）与「选项卡」，以保持「标签」一词的唯一指向。

**条数**：

- 附录 B：实测 `B.<组>.<序>` 唯一编号 **157 条**，13 个分组 —— 与 README 声称的 **157 条 / 13 类完全一致** ✅
- 附录 C：按 `常见混淆`逐条计，实测 **82 条**（9 个一级分组）—— 与 README「91 条」**差 9 条**，需以源稿为准核对到底是少录还是声称有误。

**字数**：源稿 19 文件实测汉字 **149 245**（≈14.9 万字），其中正文去除代码围栏后 **139 656**（≈14.0 万字）；README 声称「约 14.7 万字」——量级吻合，若以"含代码块"口径则偏低约 0.2 万，可一并微调。

**其他零散**：

- 「三大典型误解」**两种版式并存**：第 1/2/4/5/9/13/14 章用「误解一/二/三：」+ 直引号；第 0/3/6/7/8/10/11/12 章用 §四规定的 `"…" ——驳斥` 格式。15 章各有 1 组、数量齐全，但版式不统一。
- 纯英文括注用**全角括号**（`（Repository）`、`（Commit / Message）`、`（Yang et al.）` 等 2 377 处全角括号中的一部分）——部分出版社要求纯拉丁内容用半角括号 + 中西文间隙。
- **数字与单位间距不一致**：`10GB` / `200 MB` / `20GB` / `8 GB` 混用（实测样本 6 种写法 3 种间距），建议统一为「数字 + 半角空格 + 单位」。
- 目录与正文**没有「第 N 部分」分部页**（README 目录分「第 0/1/2/3 部分」），但正文有 9 处引用"第 1 部分 / 第 2 部分"——引用无对应落点。
