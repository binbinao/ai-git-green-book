# 第 7 章　分支策略：Trunk、GitFlow 还是什么都不用

> 《Git 的概念地图》第 7 章 · 场景章 · v1.0
> 场景决策部分的第二章：从"分支是什么"跨到"你们团队要怎么用分支"。
> 结构：症状 → 候选方案 → 判断规则。三段式。

---

## 7.1 场景引入：一场会议室里的圣战

周四下午两点，会议室里六个人，白板上写着三个词：**Trunk-Based、GitHub Flow、GitFlow**。

事情的起因是新来的架构师老陈提议\"我们改成 Trunk-Based Development 吧\"。技术总监立刻皱眉：\"我们是做企业级软件的，客户环境有五个大版本在跑，不用 GitFlow 你告诉我 hotfix 怎么打？\" 前端的小张小声说：\"我以前那家公司就 main 分支 + PR，挺好的呀。\" 老陈补一句：\"Google 内部一个仓库上万工程师，用的就是 Trunk-Based。\" 总监立刻回：\"Google 是 Google，我们是我们。\" 小张：\"……\"

三十分钟过去，白板上多了两个 UML 图、四条决策树、一个 Google 的架构截图，还有若干句\"这是最佳实践\"和\"你这是照搬大厂\"。**没有人在讨论\"我们团队怎么发布\"这件事。** 大家在讨论\"哪个策略正确\"。

这就是分支策略讨论最常见的翻车方式：**把一个团队决策，讨论成了一个技术决策。**

同样的翻车，还会以别的姿势出现：

- \"我们要不要开个 develop 分支？\"——真实的问题其实是\"我们主干上的代码能不能随时上线\"，但没人把它挑明。
- \"这个 feature 分支活了三周了合不进去。\"——真实的问题其实是\"我们的评审人手不够\"或\"我们的 CI 太慢\"，不是分支的问题。
- \"能不能就在 main 上直接推？我们就三个人。\"——真实的问题其实是\"我们要不要保留 code review 这层\"，不是分支模型问题。
- \"AI 一天给我提了 20 个 PR，全都基于两天前的 main，冲突炸了。\"——真实的问题是\"AI 产出速度和你们合流节奏不匹配\"，不是任何一种\"策略\"能直接救的。

这一章要摊开的这张地图，不打算告诉你\"用哪个最好\"。**分支策略没有最好，只有最匹配。** 摊开之后你会看到：三种主流策略，每一种都是**对四个问题的一组回答**——发布节奏、代码所有权、工程成熟度、回滚需求。把这四个问题问清楚，五分钟能决策的事，不用开半天会。

## 7.2 祛魅时刻：分支策略不是技术决策

先给结论。

> **分支策略是一个团队决策，不是一个技术决策。它是团队对\"我们打算怎么协作、怎么发布、怎么承担风险\"的一次公开表态——分支只是这份表态的实现细节。**

拆解这句话，三个词最要紧：

**\"团队决策\"**：一个策略能不能跑起来，取决于团队有没有配套的能力（自动化测试？评审习惯？回滚机制？），而不是取决于文档写得多完整。Google 用 Trunk-Based，是因为他们有 Blaze/Bazel、有跨仓库的 presubmit、有 feature flag 基础设施——**策略是能力的下游产物**，不是上游命令。

**\"怎么发布\"**：分支模型的形状，本质上是发布节奏的镜像。每天上线 10 次的 SaaS 团队，和每季度出一版的桌面软件团队，天然长成两种形状——前者根本没时间开 release 分支，后者根本没条件\"合完就部署\"。策略是从发布节奏倒推出来的，不是从\"业界最佳实践\"顺推下来的。

**\"承担风险\"**：分支不是为了整齐好看，是为了**把不确定性关在一个可撤销的房间里**。风险大的（大重构、破坏性变更）需要长命房间加评审边界；风险小的（改文案、加个开关）短命房间甚至无房间即可。

### 一个反常识观察：\"最佳实践\"是上下文相关的

拉近看点数据：

- Google 内部 monorepo，超过 2.5 万工程师、数十亿行代码，主流分支模型是 **Trunk-Based**。
- 一家做嵌入式医疗设备的小公司，五个工程师，主流分支模型可能是 **GitFlow**——因为他们的产品会同时有 v1.2、v1.5、v2.0 三个在客户现场跑，任何一个都要能独立打补丁。
- 一个独立开发者维护的开源工具库，主流分支模型可能是 **GitHub Flow**——一个 main、每个功能一个 PR、合并即发新版本。

三个团队三种策略，都是\"正确\"的。**没有一种能搬到另外两个团队去。** 谁抄错谁翻车：

- Google 抄 GitFlow？——他们那种提交频率下，develop 和 main 一天分叉一百次，人力光顾着合分支了。
- 医疗设备小公司抄 Trunk-Based？——客户报的那个 v1.2 的 bug，你告诉我怎么在\"永远最新\"的 main 上修？
- 独立开发者抄 GitFlow？——你有必要为一个人的仓库开六种分支吗？

所以，**任何一句\"业界最佳实践是 XXX\"，如果没跟上\"在什么样的团队、什么样的发布节奏下\"，都是半句话**。而这半句话，正是所有分支策略圣战的燃料。

## 7.3 三种策略的全景图

把三种主流策略摆到同一张表上看一遍：

| 维度 | Trunk-Based | GitHub Flow | GitFlow |
|---|---|---|---|
| 主干 | 只有 `main` | 只有 `main` | `main` + `develop` 双主干 |
| 特性分支寿命 | **几小时到 1-2 天** | 几天到 1 周 | 数天到数周 |
| 特性分支怎么合 | 直接合入 main（可小 PR，也可直接 push） | PR 合入 main | PR 合入 develop |
| 发布怎么触发 | main 上任意 commit 都可发（配合 feature flag） | PR 合并即部署 | 从 develop 切 release 分支 → 稳定后合入 main + 打 tag |
| Hotfix 怎么办 | main 上直接修，flag 关掉坏功能 | main 上开 hotfix 分支 → PR → 部署 | main 上开 hotfix 分支 → 合回 main **和** develop |
| 未完成功能怎么藏 | **Feature flag**（代码合了但功能关着） | 不合到 main 就等于没上线 | 待在 feature 分支上 |
| 依赖的工程能力 | 强 CI/CD、trunk 保护测试、feature flag 基础设施 | CI + 自动部署 | 版本管理规范、release 冻结流程 |
| 典型团队 | Google/Meta/Netflix/字节等大厂主线 | GitHub 自身、绝大多数 SaaS 创业公司、开源项目 | 桌面软件、嵌入式、有 LTS 需求的企业产品 |
| 冲突频率 | **低**（短命 + 高频合流） | 中 | **高**（长命分支 + 双主干） |
| 复杂度 | 低（分支形态简单） | 低 | 高（六种分支类型） |
| 现状 | **业界主流**，DORA 报告持续背书 | SaaS/开源主流 | 原作者 nvie 于 2020 加了劝退注记，只推荐给\"多版本并存\"团队 |

三行字看不完的话，只记这三条：

1. **Trunk-Based**：\"我们信任 CI/CD 和 feature flag，直接干。\"
2. **GitHub Flow**：\"main 永远可发布，每个改动经 PR 评审后合入并部署。\"
3. **GitFlow**：\"我们发布是有仪式感的，需要冻结、需要 hotfix、需要多版本并存。\"

下面每种都配一个真实场景，感受一下它们各自\"在什么样的一天里\"运转。

### 7.3.1 Trunk-Based：短命分支 + 小步合流 + Feature Flag

**真实场景 · 一家 300 人的 SaaS 公司，周一上午。**

产品经理小美说要给结算页加一个\"分期付款\"入口。工程师阿凯听完，做的事：

1. 从 main 拉一个分支叫 `feat/installment-entry-akai`（他们的命名规则：`feat/xxx-<owner>`）。
2. 在代码里读 feature flag `installment_entry_v2`（当前值：`false`）。写入口按钮的时候用 `if (isEnabled('installment_entry_v2'))` 包起来。
3. 一小时后，改了三个文件，跑本地测试通过。提一个 PR 到 main。
4. CI 自动跑：单元测试、集成测试、代码质量扫描、UI 快照对比。绿灯。同事阿丽 review 了 20 分钟（因为改动只有 40 行），批了。
5. **合入 main**。CI 触发部署到 staging，跑冒烟测试。10 分钟后自动部署到 prod。
6. 生产环境上，flag 还是 `false`，用户看不到入口。**代码已经上生产，功能没上生产。**
7. 阿凯在管理后台把 flag 对内部员工开为 `true`，dogfood 两天，没问题。开 5% 灰度、20%、50%、100%。发布完成。
8. 一周后，flag 稳了，阿凯提一个 PR 删掉 flag 判断，永久开启。

这个流程里最反直觉的一件事：**\"未完成的功能\"和\"已合并的代码\"是解耦的。** 传统认知里，代码合进主干就等于功能上线，所以\"没做完不能合\"。Trunk-Based 用 feature flag 打穿了这个绑定——**代码可以早合、随时合、只要能编译能测试就合，"上线\"这件事被交给运行时的 flag 开关，而不是 Git 分支**。

好处三件：
- **合并冲突几乎不存在。** 你的改动最多在自己分支上活 8 小时。同事在 main 上再怎么改，你也就是那 8 小时的\"差量\"要处理。
- **回滚成本极低。** 出了问题，flag 关掉，不需要 revert commit、不需要重新部署，秒级止血。
- **持续集成是真正的\"持续\"。** 大家的改动一天融合几十次，问题当天暴露、当天解。不会积攒到某个\"合并日\"集体爆炸。

代价也三件：
- **必须有 feature flag 平台。** 没有的话就是\"半成品直接上线\"，等着背锅。
- **必须有靠谱的自动化测试。** 因为评审时间被压缩到 20 分钟量级，测试就是你的第二双眼睛。
- **团队要有小步走的习惯。** 一个 PR 500 行就已经算大了。这需要工程师主动把大任务拆小，很多人不习惯。

**什么样的团队适合？** 每天要上线多次、有 CI/CD 和 feature flag 基础设施、团队有拆任务的习惯。**大厂内部基本都是这套**——注意，是\"内部\"，不是\"给客户交付\"。

### 7.3.2 GitHub Flow：main + PR + 合并即部署

**真实场景 · 一家 15 人的创业公司，做一个 B2B SaaS 工具。**

工程师小林要加\"数据导出为 CSV\"功能。做的事：

1. 从 main 拉一个分支叫 `data-export-csv`（命名规则宽松，看得懂就行）。
2. 花了两天写代码，中途 push 了几次到远程分支（不是合到 main，就是同名远程分支）。
3. 写完开 PR 到 main。PR 描述里写清楚：改了什么、怎么测试、有没有 breaking change、截图。
4. CI 跑测试。CTO 老王 review。指出两处代码可以更简洁。小林改了 push。老王批了。
5. 合入 main。CD 触发部署到生产。功能立刻可用。
6. 半小时后有客户反馈 CSV 里日期格式不对。小林开一个 hotfix 分支 `fix/csv-date-format`，改一行，PR、合并、部署。20 分钟解决。

跟 Trunk-Based 的区别：
- 分支活得**稍微长一点**（几天 vs 几小时）。
- **不用 feature flag**——因为团队小、功能颗粒度天然就是端到端的\"一个功能\"，不需要把\"合并\"和\"上线\"解耦。
- **PR 是必经流程**——即使团队只有两三个人。PR 不是为了走过场，是为了留下评审痕迹和 CI 结果。

跟 GitFlow 的区别更大：
- **只有一个 main**——没有 develop、没有 release 分支、没有那些\"这个东西从哪合到哪\"的迷惑。
- **没有\"版本\"概念**——每次部署就是最新版。想追溯就用 tag（可选）或看 commit 历史。

**什么样的团队适合？** 中小团队、SaaS 产品、没有\"多版本并存\"负担、CI/CD 已经打通。这是最普适的选择——**大多数团队从这套开始就够了**，等团队大到 GitHub Flow 都嫌慢、每天要合上百个 PR 的时候，再考虑升级到 Trunk-Based。

### 7.3.3 GitFlow：全家桶策略

**真实场景 · 一家做工业控制软件的公司，60 个工程师，客户是电力、化工、制造业。**

产品线上同时活着 v3.4、v3.5、v4.0 三个大版本。v3.4 是某些老客户还在用的稳定版（只收 bug 修复），v3.5 是当前主推版本，v4.0 是下一个大版本，正在开发中。

他们的分支布局：

```
main               ← 永远指向已发布的最新稳定版（打了 tag 的那颗）
develop            ← 下一个版本的集成分支
feature/*          ← 从 develop 长出，回合到 develop
release/4.0        ← 4.0 快发布了，从 develop 切出，只接受修复
hotfix/v3.4.7      ← 客户报的 3.4 bug，从 v3.4 的 tag 切出
support/3.4        ← 长期支持分支（GitFlow 变种里的额外角色）
```

一次典型的日常流转：

- 工程师小赵开发\"新 SCADA 协议支持\"。从 develop 切 `feature/scada-modbus-plus`，写两周，PR 合回 develop。
- 4.0 快发布了，从 develop 切 `release/4.0`。这条分支上只接受 bug 修复和文档更新，不接受新功能。团队测试两周。
- release/4.0 稳定，合入 main（打 tag `v4.0.0`），同时也合回 develop（把测试期修的 bug 带回去）。
- 客户 A 报了个 v3.4 的严重 bug。从 tag `v3.4.6` 切 `hotfix/v3.4.7`，修完合入 main（打 tag `v3.4.7`），同时也合回 develop 和 support/3.4。发新的 3.4.7 补丁包给客户。

**看到那个\"同时合回\"了吗？** 这是 GitFlow 最让人头大的地方——你修一个 bug，可能要合到三条分支上。每合一次都可能冲突。团队必须有专门的 release engineer 或 tech lead 盯着这些"合并动线\"。

代价是明显的：
- **认知负担重。** 六种分支类型，每种都有\"从哪来、到哪去\"的规矩。新人入职培训得单独讲。
- **冲突频率高。** develop 和 main 长期分叉，release 分支上的修复要合两次三次。
- **发布流程慢。** 从代码写完到真正发布，中间有\"合到 develop → 切 release → 稳定 → 合到 main → 打 tag\"一整套。

好处也是明显的：
- **多版本并存的能力是真的。** v3.4 客户不用被强推到 v4.0，可以在 support 分支上继续吃补丁。
- **发布节点是清晰的。** 每个 tag 对应一次真实发布，release note 好写、审计好过。
- **回滚是清晰的。** \"回到 v3.5.2\" 这句话有明确的语义，因为 v3.5.2 是一个真实存在的、被冻结过的、有 tag 的稳定点。

**什么样的团队适合？** 有多版本并存需求（客户端软件、企业软件、SDK、嵌入式）、发布是仪式（有 QA 冻结期、有版本文档、有客户升级动作）、团队规模能养得起 release engineer。

**一个必须澄清的事实**：GitFlow 的原作者 Vincent Driessen（nvie）在 2020 年给他 2010 年那篇奠基文章加了一个显著的**注记**，大意是：如果你在做 Web 应用、SaaS、持续交付的产品，**请不要用 GitFlow，用 Trunk-Based 或 GitHub Flow**。GitFlow 是为\"版本发布制\"软件设计的，不是为\"永远最新版\"软件设计的。这句话被无数团队错过，导致 GitFlow 至今仍在被大量本该用 GitHub Flow 的团队使用——你猜他们开会时怎么讨论？\"业界最佳实践就是 GitFlow 啊。\"

## 7.4 判断框架：四个问题 + 一棵决策树

看完三种策略，问题从\"哪个好\"变成\"我们该选哪个\"。把这件事拆成四个问题，回答完就有答案了。

### 问题 1：你们的发布节奏是什么？

- **每天多次（甚至每小时）**：Trunk-Based 或 GitHub Flow。GitFlow 直接淘汰——它的分支同步开销大到根本追不上这个节奏。
- **每周一次或每两周一次**：GitHub Flow 最舒服。Trunk-Based 也行但可能过度。
- **每月一次或每季度一次，有正式的版本号和 release note**：GitFlow 或它的简化变种。GitHub Flow 撑不住\"版本冻结期\"这件事。
- **不定期，功能做完就发**：GitHub Flow。

发布节奏是**最强的决定因素**。它先把候选池砍一半。

### 问题 2：多人会不会改同一批文件？

- **经常改重叠区域**：需要短命分支 + 高频合流，也就是 Trunk-Based 的方向。长命分支下的重叠改动，最后合并时是灾难。
- **各自负责各自的模块，很少交叉**：GitHub Flow 甚至 GitFlow 的长命分支都能扛。
- **完全并行、几乎不重叠**：任何策略都行，选简单的。

这个问题实际上是在问\"你们的代码所有权（code ownership）分布\"。所有权越集中（\"这个模块就是老王的\"），长命分支就越安全；所有权越分散（\"这块每个人都在改\"），就越需要短命分支强制大家频繁同步。

### 问题 3：你们的工程成熟度到哪一档？

工程成熟度不是一个玄学词，它是几件具体能力的组合：

- **CI 覆盖率**：能不能在 PR 合并前跑完够用的自动化测试？
- **CD 自动化**：合并到 main 后，能不能自动部署到 staging、跑冒烟、灰度到 prod？
- **Feature flag 平台**：有没有一个稳定的开关系统，让代码和功能能解耦？
- **可观测性**：出了问题能不能几分钟内发现？

给个粗略档次：

| 档次 | 能力画像 | 适合策略 |
|---|---|---|
| L1 | 手动部署、没什么自动化测试、监控靠客服反馈 | 老老实实开分支 + PR + 人工评审 + 有节奏发布。GitFlow 或极简 GitHub Flow。**不要碰 Trunk-Based。** |
| L2 | 有 CI 自动化测试、CD 半自动、能一键部署 | GitHub Flow 是甜蜜点。 |
| L3 | 全自动 CD、蓝绿/金丝雀部署、feature flag 平台、指标可观测 | Trunk-Based 才能真正发挥威力。 |

**这一条最扎心**：很多团队想抄 Trunk-Based，但工程能力其实在 L1 或 L1.5。抄过去的结果不是\"我们变高效了\"，而是\"我们把生产事故的产量提高了\"。**先修工程能力，再谈策略升级。** 反过来说，如果你已经在 L3，还在用 GitFlow，那是浪费自己。

### 问题 4：回滚需求有多刚性？

- **需要\"回到某个明确发布版本\"（客户升级、监管审计、法规追溯）**：需要清晰的版本 tag 和长期支持分支。GitFlow 或类似结构。
- **能接受\"回滚 = 关个 flag\"**：Trunk-Based。
- **能接受\"回滚 = revert 一个 PR 再部署\"**：GitHub Flow。

回滚需求经常被低估。B2C SaaS 一次事故 20 分钟内 revert + redeploy 完事；但医疗设备、金融、工业控制的软件，\"回滚\"意味着一大批客户设备要重装到旧版本——这时候没有 tag 化的发布点，就是灾难。

### 决策树（贴出来直接用）


### 一个反例：\"我们是大厂所以用 GitFlow\"

这是最典型的伪需求。\"大厂\"三个字听起来很沉重，让人本能地觉得\"越复杂的策略越靠谱\"。但事实相反：

- Google 内部**主要用 Trunk-Based**（配合 monorepo + Piper + Blaze）。
- Meta 内部**主要用 Trunk-Based**（Sapling/Mercurial 也是 trunk-based 心智）。
- 字节内部**大量业务线用 Trunk-Based 或 GitHub Flow**。
- Netflix、Uber、Airbnb 内部**主流是 Trunk-Based**。

\"大厂用 GitFlow\" 这个印象哪来的？——大概率来自那些\"给客户交付软件\"的部门（SDK、桌面客户端、企业版），或者是外包/乙方公司的项目组。他们的产品形态确实吃 GitFlow。但**别把某个部门的策略当成整个大厂的策略**，更别把\"大厂\"当成\"复杂\"的通行证。

反过来说，如果你团队现在跑 GitFlow 跑得好、发布节奏和产品形态都对上了，**不要因为\"业界主流是 Trunk-Based\"就迁移**。策略切换本身是一次大的组织成本，只有当\"当前策略明显阻塞产出\"时才值得做。**没坏别修**。

## 7.5 AI 时代的新变量：从"人的并行度\"到\"人+AI 的并行度\"

传统的分支策略讨论里，隐含的假设是：**分支的粒度 = 一个工程师的一次工作粒度**。一个人一天开两三个分支，一周合几个 PR，节奏由人的手速决定。

AI 代理（Claude Code、Cursor Agent、Aider、Devin 等）把这个假设打碎了。

**新事实**：一个工程师 + 一群 AI 代理，一天可能产出几十个可合并的改动。有的是 5 分钟的小修复，有的是让 agent 后台跑半小时出来的重构。你的 Git 仓库突然变成了一个**多 producer 的并发系统**——而你还是那个唯一的 reviewer。

这个新事实对三种策略产生了不对称的影响。

### 对 Trunk-Based：价值放大

Trunk-Based 的核心信条——\"短命分支 + 高频合流\"——恰好就是 AI 高产出下的自然形态。

- AI 生成的每个改动天然就是短命的（几十分钟到几小时的生命周期）。
- 合流频率天然就高（一天几十次）。
- 未完成或未验证的功能藏在 feature flag 后面，AI 可以\"合但不上\"。

**AI 时代 Trunk-Based 的门槛反而降低了**——AI 帮你把大任务拆成小 PR、帮你写测试、帮你生成 PR 描述、帮你 review 自己的代码。以前需要\"团队小步走习惯\"的部分，现在 AI 能补一半。

但也带来新问题：**评审瓶颈。** AI 产 20 个 PR，人还是只有那两只眼睛。解法有几种：
1. AI 互审（一个 agent 生成，另一个 agent review + 提问题）——不能完全替代人，但能过滤掉低质量的。
2. 把 PR 拆得更小——小到人能在 5 分钟内看完。
3. 强化 CI 覆盖——把\"眼睛看得出来的问题\"尽可能变成\"CI 跑得出来的问题\"。

### 对 GitHub Flow：略微紧张

GitHub Flow 假设的是\"每个 PR 都过一次人评审\"。AI 产出量上来后，这个假设开始吃力。

补救方式两条：
- **给 AI 的 PR 打标签**（比如 `agent-generated`），走差异化流程：小改动 + 全绿 CI + 高置信度可以走\"轻评审\"甚至\"自动合并\"（谨慎！）；大改动或涉及关键路径的还是人 review。
- **worktree 化**（第 8 章专讲）：让 AI 在独立的 worktree 里跑长任务，不干扰你的主工作区。

### 对 GitFlow：更加艰难

AI 高产出 + GitFlow 的多分支合并动线，是一对天生的敌人。

- develop 上每天几十个改动，release 分支切出去后要往回合的 diff 越来越大。
- Hotfix 要合三条分支，AI 也帮不上——**合并冲突的语义判断，AI 没法完全自动化**。
- 长命 feature 分支和 develop 的分叉每天加深，rebase 一次就是半天。

**如果你的团队已经引入了 AI 代理并且开始重度用，还在跑 GitFlow，那是最痛的组合。** 优先考虑\"简化 GitFlow\"：只保留 main + hotfix + 短命 feature，去掉 develop。或者干脆迁到 GitHub Flow。

### 新的分支使用姿势

AI 时代有几个新的\"分支使用姿势\"值得单独提：

**姿势一：AI 的每次交互 = 一个原子分支或原子 commit。**
Aider 的做法是每次 AI 编辑自动 commit 一次。这带来的好处：AI 犯错时的回滚粒度是\"单次交互\"，不是\"半天的工作\"。要走得更远，可以让每个 AI 会话都在一个短命分支上——会话结束合流，出问题整条扔掉。

**姿势二：让 AI 跑在独立 worktree 上。**
你的主分支、你的 IDE、你的手动改动一动不动。AI 在旁边的 worktree 里干它的活，你随时能过去看它的分支状态。避免\"AI 改到一半、你也改到一半、切来切去把文件搞乱\"。

**姿势三：分支保护规则要收紧。**
以前 main 保护是\"防止手滑\"，现在还要\"防止 AI 一时糊涂\"。**main 必须开启保护：强制 PR、强制 CI 通过、禁止 force push、限制直接 push 权限**。这不是不信任 AI，是给它一个\"就算跑偏也能兜住\"的边界。

## 7.6 常见伪需求诊断

分支策略讨论里最耗时间的往往不是真问题，是几种反复出现的伪需求。列几个最常见的，教你识别。

**伪需求 1：\"我们是大厂/成熟公司/严肃业务，所以必须用 GitFlow。\"**

> **真问题**：你想要的是\"感觉专业\"，不是\"实际有效\"。GitFlow 的价值是\"多版本并存 + 冻结式发布\"，跟\"专业\"没关系。请问你们有多个版本并存吗？有严格的冻结期吗？如果都没有，你要的其实是简单靠谱的评审流程，用 GitHub Flow + PR 保护规则就够了。

**伪需求 2：\"main 上必须永远绝对稳定，不能有一点问题。\"**

> **真问题**：你在寻求的是\"发布后再进主干\"的安全感。但这个安全感的正确对应物是\"CI 门禁 + 灰度部署 + 快速回滚\"，不是\"多开一条 develop 分支\"。develop 分支不会让 bug 变少，只会让 bug 晚一点被合并进 main——如果你的 CI 不够好，develop 上一样烂。

**伪需求 3：\"我们要用 develop 分支把 QA 环境和 prod 环境分开。\"**

> **真问题**：你把\"环境隔离\"（部署到哪台机器）和\"分支隔离\"（代码在哪条分支）混为一谈了。环境隔离应该用**部署管道 + 环境变量 + feature flag**，不是用 Git 分支。用分支代表环境，会导致同一段代码在两条分支上活着，一旦 hotfix 就要合两次。

**伪需求 4：\"我们每个人都开自己的长期个人分支，避免互相干扰。\"**

> **真问题**：你们在回避\"合并冲突\"这件事，但代价是把冲突推迟到未来某个更痛的时刻。分支越长命，最后合流时的冲突就越可怕。正确的解法是**频繁 rebase 或 merge main 进来**，让分歧点始终很浅；或者干脆缩短分支寿命。

**伪需求 5：\"我们不用 PR，git push 到 main 更快。\"**

> **真问题**：你想要的是\"少走一步流程\"。但 PR 不是流程仪式，它是**评审痕迹 + CI 触发点 + 讨论载体 + 事后审计线索**。就算你团队只有两个人，也建议至少保留 PR + 自动合并（甚至可以互相秒批），因为它建立的是可追溯的历史。**\"直接推 main\" 省下的那 30 秒，可能在半年后某次事故复盘时让你后悔三小时。**

**伪需求 6：\"AI 生成的代码不需要 review，因为 AI 不会犯错。\"**

> **真问题**：AI 会犯错，而且犯的错经常和人不一样——它会写出\"看起来对但语义不对\"的代码，会引入没料到的依赖，会在\"给我修 A\"的过程中悄悄改了 B。**AI 时代评审的重要性不是降低了，是提高了。** 但评审形式可以变（AI 辅助 review、diff 摘要、语义级 lint），不是取消。

## 7.7 团队约定模板：写下来才算数

策略是选出来的，但**约定必须写出来**。没写下来的约定不叫约定，叫默契——而默契在新人入职、AI 加入、需求变更时会集体失效。

给一个可以直接抄的团队约定模板（假设你们选的是 GitHub Flow + AI 辅助）：

### 分支命名规则

```
main                    ← 主干，永远可发布
feat/<short-desc>       ← 新功能，如 feat/user-profile-avatar
fix/<short-desc>        ← Bug 修复，如 fix/csv-date-format
chore/<short-desc>      ← 杂务（依赖升级、配置调整），如 chore/upgrade-node18
docs/<short-desc>       ← 文档修改
spike/<short-desc>      ← 一次性实验分支，可随时整支删除
rescue/<date>           ← 抢救 detached HEAD 或误操作，如 rescue/2026-09-18
agent/<agent-name>/<desc> ← AI agent 生成的分支（可选，用于差异化流程）
```

**注意**：命名规则不重要，一致性才重要。选一套团队所有人（包括 AI）都遵守的规则，就够了。

### 分支生命周期上限

| 分支类型 | 建议寿命 | 硬上限 |
|---|---|---|
| feat/fix/chore/docs | 1-3 天 | 1 周（超过要么合并要么关闭） |
| spike | 到实验结束就删 | 2 周 |
| rescue | 抢救完立刻合并或删除 | 3 天 |

**超过硬上限的分支**：CI 每周扫描一次，自动 comment 提醒作者。三次不响应，自动关闭对应 PR 并删除远程分支（发布节点已经钉在 tag 上，分支不必留）。

### main 分支保护规则（GitHub/GitLab 都能配）

- ✅ 强制 PR 合并（禁止直接 push 到 main）。
- ✅ 至少 1 位 reviewer approval。
- ✅ CI 必须全绿（单元测试、集成测试、lint、类型检查）。
- ✅ PR 必须包含描述（模板里的 checklist 至少勾选前三项）。
- ✅ 合并方式：**Squash and merge**（保持 main 历史线性可读），或 **Rebase and merge**（保留每个 commit）。**禁用普通 merge**（避免不必要的 merge commit）。注意这套规则只适用本节的 GitHub Flow 模板——GitFlow 恰好相反，hotfix/release 合回主干要的就是 `--no-ff` 那颗 merge commit（见本章末命令侧栏）。另外把取舍说破：**选 squash 就是放弃 commit 级粒度——bisect 与单点回滚能力同时下降，两者不可兼得**。
- ✅ 禁止 force push 到 main。
- ✅ 合并后自动删除源分支（保持分支列表清爽）。

### PR 描述模板

```markdown
## 改了什么
（一句话说明本 PR 的核心变更）

## 为什么改
（关联需求/issue 链接，说明背景）

## 怎么测试
- [ ] 单元测试已覆盖
- [ ] 手动验证步骤：xxx
- [ ] 涉及数据库变更？如是，说明迁移策略
- [ ] 涉及 breaking change？如是，说明升级路径

## 风险与回滚
- 影响范围：
- 回滚方案：（revert 本 PR / 关闭 feature flag / 数据库回滚脚本）

## 是否 AI 生成
- [ ] 是（哪个 agent、大概交互轮数）
- [ ] 否
- [ ] 部分（人 + AI 协作）
```

**注意最后一栏**——AI 生成的代码需要额外说明，方便 reviewer 调整审查强度。不是歧视 AI，是**给评审者一个上下文**。

### AI 参与规则（新加的一栏）

- AI agent 生成的分支必须以 `agent/` 前缀命名（便于工具识别）。
- AI 生成的 PR 必须有明确的\"生成来源\"标注（在 PR 描述里勾选）。
- AI 不允许直接 push 到 main、develop、release/* 等受保护分支。
- AI 不允许执行 force push、reset --hard、history rewrite——这些操作必须由人明确触发（详见第 12 章红黄绿安全体系）。
- AI 生成的改动即使小，也走 PR 流程（不允许\"AI 直接合\"的旁路）。

### 例外流程

再周密的约定也有例外。写下例外流程本身：

- **紧急 hotfix**：可以省略部分 review（比如从 2 人 approval 降到 1 人 approval + 事后补审），但**不能省略 CI**。事后 24 小时内必须补一次 post-mortem PR。
- **纯文档改动**：可以走\"提交即合并\"的绿色通道（工具支持自动化）。
- **依赖升级**：Dependabot/Renovate 之类的机器人 PR，配置好自动合并规则，但要限定\"仅 patch 版本\"。

## 7.8 AI 指令箱 · 分支策略

以下指令模板与工具无关（Claude Code / Cursor / Copilot / Aider 皆适用）。分支策略话题是"上下文重\"的——AI 需要先了解你团队的实际情况，才能给出有意义的建议。

**🟢 诊断类（帮你把现状说清楚）**

- 「读一下我们仓库的最近 3 个月历史（`git log`）：本地和远程分支各有多少条、平均寿命多长、有没有长期没动的\"僵尸分支\"、合并方式是 merge/squash/rebase 里的哪种为主。给我一份现状报告。」
- 「基于这份仓库的历史（分支数量、平均寿命、合并频率、发布 tag 节奏），推断我们目前实际在跑的分支策略最像哪一种？找出跟三种主流策略不吻合的地方。」
- 「我们团队每天产出多少次 push、平均一个 PR 从开出到合并花多久、CI 平均跑多久？基于这几个数字，判断我们的\"工程成熟度\"接近 L1/L2/L3 哪一档。」

**🟢 选型类（辅助决策）**

- 「我给你我们团队的情况：[人数]、[发布节奏]、[产品形态]、[有没有 feature flag]、[有没有 CI/CD]、[有没有多版本客户]。基于第 7 章的四问决策树，推荐一个分支策略并解释为什么。」
- 「假设我们现在用的是 GitFlow，想迁移到 GitHub Flow。给我一个渐进式迁移方案：先做什么、后做什么、每一步的风险和回滚点。」
- 「我们团队想上 Trunk-Based，但没有 feature flag 平台。给我一份\"前置能力清单\"——哪些能力必须先建好、哪些可以之后补、大概需要多久投入。」

**🟢 规范类（把约定落地）**

- 「基于我给你的分支策略选择（GitHub Flow），生成一份团队约定文档：分支命名规则、生命周期上限、main 保护规则、PR 模板、例外流程。用 Markdown 输出，可以直接放到仓库的 CONTRIBUTING.md。」
- 「给我一份 GitHub 仓库的 branch protection 配置 checklist，我照着在 Settings 里勾选。逐条解释每一条能防止什么。」
- 「生成一份 PR 描述模板，包含\"改了什么/为什么改/怎么测试/风险与回滚/是否 AI 生成\"五段。放到仓库的 `.github/pull_request_template.md`。」

**🟡 需要盯着的（涉及历史或规则变更）**

- 「把我们仓库里所有已合并进 main 但还没删的本地和远程分支列出来。先只列表。」→ 看完再补一句「确认，批量删除远程分支列表里的这些，保留 xxx 和 yyy」。
- 「我们要把 develop 分支下线（迁到 GitHub Flow）。给我一个完整迁移剧本：怎么把 develop 上未合并的 PR 转到 main、怎么调整 CI 配置、怎么通知团队、每一步的回滚方式。**执行前给我看完整计划，我批准后再动。**」

**训练用指令（陪练模式）**

- 「模拟一个团队场景（自己编）：告诉我团队规模、产品形态、发布节奏、工程能力。我根据这些信息推荐一个策略。你评价我的推荐并指出遗漏考虑的因素。来 5 轮。」
- 「给我 10 道\"这是不是伪需求\"的判断题——场景覆盖\"我们要用 develop 分离环境\"、\"AI 生成的不用 review\"、\"大厂都用 GitFlow\"等。我判断真伪，你批改。」

## 7.9 执行后的世界

选定策略、写下约定、配好保护规则之后，你的仓库和团队会发生什么样的变化？透视一下：

| 你做的事 | 仓库/团队里的真实变化 |
|---|---|
| 开启 main 分支保护（强制 PR + CI 绿灯） | 所有\"直接 push 到 main\"的操作被服务端拒绝。事故通道被物理关闭。 |
| 约定分支命名前缀（feat/、fix/、agent/…） | CI 和工具可以基于前缀差异化处理（如 agent/* 走轻评审通道）。团队心智里\"这条分支是干嘛的\"变得一眼可知。 |
| 定义分支生命周期上限 + 自动扫描 | 僵尸分支不再堆积。半年后仓库的 `git branch -a` 输出不会有 200 条已死分支。 |
| 引入 Squash and merge | main 的历史变成一颗颗\"整洁的 PR 果实\"，而不是杂乱的中间 commit 流。`git log --oneline` 一行一功能，便于回溯和 revert。 |
| 强制 PR + reviewer | 每次改动都留下了评审痕迹和讨论历史。半年后追\"这个决定当时为什么这么做\"的时候，PR 里的对话是最好的档案。 |
| AI agent 分支加前缀 + 单独规则 | AI 的产出被纳入可管理的通道，而不是野生地混在人的分支里。评审强度可差异化。 |

看懂这张表，你就理解了本章的核心：**分支策略不是画图和讨论，是配置和习惯。** 图和讨论是引子，配置和习惯才是策略真正长在团队身上的方式。

## 7.10 命令侧栏

```
# 分支保护相关（这些主要在托管平台 UI 或 API 上做，不是 git 命令）
gh repo edit --enable-auto-merge                      # 开启自动合并（GitHub CLI）
gh api repos/{owner}/{repo}/branches/main/protection  # 查看分支保护配置（需管理员权限）

# 常用的策略辅助命令
git log --oneline --graph --all --since=\"3 months ago\"    # 观察团队实际的分支/合并形态
git branch --merged main | grep -v main                    # 列出所有已合并进 main 的本地分支
git branch -r --merged main                                # 已合并进 main 的远程分支
git for-each-ref --sort=-committerdate refs/heads/         # 按最近提交时间列出本地分支（找僵尸）

# 分支寿命观察
git log <branch> --not main --oneline                      # 看某条分支相对 main 有多少独立 commit
git rev-list --count main..<branch>                        # 一条分支相对 main 领先了几个 commit

# hotfix 常用组合（GitFlow 场景）
git switch main
git switch -c hotfix/v3.4.7
# ...修 bug...
git switch main && git merge --no-ff hotfix/v3.4.7 && git tag v3.4.7
git switch develop && git merge --no-ff hotfix/v3.4.7      # 合两次
git branch -d hotfix/v3.4.7
```

不需要背。策略层面的\"命令\"其实很少，真正繁重的是**配置**（分支保护、CI、PR 模板）和**沟通**（团队约定、评审习惯）。

## 7.11 本章小地图

```
分支策略 = 团队对\"怎么协作、怎么发布、怎么承担风险\"的一次公开表态
  │
  ├─ 三种主流：
  │    Trunk-Based   ← 短命分支 + 高频合流 + feature flag（大厂主干）
  │    GitHub Flow   ← main + PR + 合并即部署（SaaS/开源甜蜜点）
  │    GitFlow       ← main/develop 双主干 + release/hotfix（多版本并存产品）
  │
  ├─ 四问决策：
  │    1) 发布节奏？        每天多次 / 每周 / 每月 / 不定期
  │    2) 代码所有权？      重叠改动多不多
  │    3) 工程成熟度？      L1（手动）/ L2（半自动）/ L3（全自动+flag）
  │    4) 回滚需求？        关 flag / revert PR / 回到 tag 版本
  │
  ├─ AI 时代新变量：
  │    分支策略的粒度从\"人的并行度\"变成\"人+AI 的并行度\"
  │    → 短命分支 + 自动合流的价值放大
  │    → 分支保护规则需要收紧（不是不信 AI，是给它兜底边界）
  │
  └─ 团队约定必须写下来：
       分支命名 + 生命周期 + main 保护 + PR 模板 + AI 参与规则 + 例外流程
```

**三大典型误解拆解**

1. **\"业界最佳实践是 Trunk-Based / GitFlow / XXX，我们抄就对了。\"** ——半句话。\"最佳实践\"只有配上\"在什么样的团队、什么样的发布节奏下\"才成立。Google 的 Trunk-Based 和你们十人小团队的 Trunk-Based 不是一回事。抄形式不抄能力，翻车概率百分百。真正要抄的是\"如何判断该选什么\"这套思考方式，不是某个具体答案。

2. **\"我们用了 GitFlow 所以我们更严谨。\"** ——GitFlow 的复杂度是**成本**，不是**价值**。它的价值只在\"需要多版本并存 + 有仪式化发布\"的场景兑现。在不需要这两件事的场景下用 GitFlow，你付了成本（六种分支类型、合并动线复杂）却收不到对应回报，只留下\"看起来严谨\"的错觉。**严谨的定义是\"该防的都防住了\"，不是\"分支类型多\"。**

3. **\"分支策略是工程师的事，管理层不用管。\"** ——恰好相反。分支策略是**团队决策**——它反映的是发布节奏（业务决定）、代码所有权（团队结构决定）、工程成熟度（长期投入决定）、回滚需求（合规和产品形态决定）。这四件事没有一件是纯工程师能拍板的。管理层不参与讨论、只做拍板，就是圣战的源头——因为\"拍板\"往往拍的是\"业界主流\"这种听起来对但不落地的东西。**好的分支策略是团队上下一起选出来的，选之前四个问题都答清楚。**
