# 第 9 章　冲突：不是 Git 的错，是你的语义需要仲裁

> 场景决策部分第四章。前三张场景地图讲\"提交、分支策略、并行工作\"——都是**顺风时**的选择题；本章开始讲逆风。

## 9.1 场景引入：一屏红字，两种反应

周三下午三点半，你 `git pull` 之后屏幕突然停在这里：

```
Auto-merging src/api/user.ts
CONFLICT (content): Merge conflict in src/api/user.ts
Auto-merging src/pages/profile.tsx
CONFLICT (content): Merge conflict in src/pages/profile.tsx
Automatic merge failed; fix conflicts and then commit the result.
```

三个 CONFLICT，两个红色的文件名。你打开第一个文件，看见了那串所有开发者都见过的鬼画符：

```
<<<<<<< HEAD
export async function fetchUser(id: string, options?: FetchOptions) {
  return apiClient.get(`/users/${id}`, options);
=======
export async function fetchUser(userId: number) {
  return apiClient.get(`/users/${userId}`);
>>>>>>> feature/user-refactor
}
```

看到这里你的血压有两种走法。

**走法 A（新手反应）**：\"Git 出问题了。\"手抖着把 `<<<<<<<`、`=======`、`>>>>>>>` 三行全删掉，随便留下一侧（大多数人留下 HEAD 那一侧，因为它\"看起来是我这边的\"），保存、`git add`、`git commit`，绿了。事情结束。**过了两天生产报错**——因为你留下的 HEAD 版本里 `id` 是字符串，但整个前端已经改成传 `number` 了，几百个调用点全在传 number，你把它们全部悄悄破坏了。

**走法 B（老手反应）**：先深呼吸，把手从键盘上挪开，读完两侧。然后在心里问四个问题：\"我这一侧想干什么？对面想干什么？两个意图冲不冲突？如果冲突，谁对？\"——**这是本章要教的全部**。

对比一下这两种走法。**它们的技术操作完全一样**——都是编辑一个文件、删掉三行标记、`add` + `commit`。差别在心智：走法 A 把 `<<<<<<< ======= >>>>>>>` 当成了\"Git 报错\"，冲突的目的是\"消掉这个红色\"；走法 B 把它当成了\"Git 交给你的一次小型仲裁\"，冲突的目的是\"决定两个意图怎么共存\"。

这一章要摊开的地图，核心是一句反直觉的话：

> **冲突不是 Git 的错，是你（或你的团队）在语义层面还没有决定。Git 只是老老实实把决定权还给你。**

你会看到：`<<<<<<<` 标出来的不是\"代码错误\"，是\"Git 看不懂的地方\"；冲突不是异常，是\"两个人并行修改同一段代码\"这件事**本来就应该导致**的东西。真正危险的从来不是那些带红色 CONFLICT 的地方——是那些**没有** CONFLICT、但语义上已经冲突的地方（比如一个人改函数签名、另一个人写调用点，Git 看不出冲突，你的生产环境十分钟后看出来了）。

## 9.2 祛魅时刻：三方合并算法只看文本，不看语义

先把 `<<<<<<<` 里到底装了什么讲清楚。

回到第 5 章讲过的三方合并（three-way merge）。当你 `git merge feature`（或 pull、rebase）时，Git 做的机械动作是：

1. 找到两条分支的**共同祖先** B（merge base）。
2. 对每个文件，算出三份内容：**B 版**（祖先）、**当前分支版**（HEAD/ours）、**被合入分支版**（theirs）。
3. 对同一份文件，逐**行**（不是逐 token、不是逐句、不是逐语义单元）去看：
   - 如果只有一侧改了、另一侧没动——**采用改了的那一侧**。
   - 如果两侧都改了、但改成了**同一份**内容——**采用那份**。
   - 如果两侧都改了、改成了不同的内容——**Git 举手投降**，把两侧的行原样贴到文件里，用 `<<<<<<< ======= >>>>>>>` 圈起来。

看清楚这个算法：**它是一个纯文本的、逐行的、机械的操作**。它不认识 TypeScript 的函数签名，不知道\"改 id 参数类型\"和\"加 options 参数\"是不是同一件事，甚至不知道这个 `.ts` 文件是不是代码——它可能是一份 CSV、可能是一封邮件，Git 用的是同一套算法。

所以 `<<<<<<<` 标记的物理含义是：

> **\"这一段，两边都改过，我不知道你想怎么办。你决定。\"**

**它不是错误**（Git 没出问题）。**它不是坏代码**（两侧代码单独看都可能是好的）。**它是一次协商请求**。

### 一张对照图

```
   共同祖先 B
   ┌────────────────────────────┐
   │ export async function      │
   │   fetchUser(id) {          │
   │   return get(`/u/${id}`)   │
   │ }                          │
   └────────┬───────────────────┘
            │
     ┌──────┴──────┐
     ▼             ▼
 你这一侧          对面这一侧
 (HEAD)           (feature/user-refactor)
 加了 options 参数  把 id 改成 number 类型
     │             │
     └──────┬──────┘
            ▼
   Git 视角：这几行两边都动了，我不知道最终该长什么样
            │
            ▼
   <<<<<<< HEAD
     ...你这一侧...
   =======
     ...对面那一侧...
   >>>>>>> feature/user-refactor
```

*图 9-1：三方合并的机械视角。B 是祖先，两条分支各自演化出不同的版本，Git 把两个后代摆到一起，请你仲裁。*

如果两侧的改动落在**不同的行**上（比如你改的是第 10 行，对面改的是第 25 行），Git 会**自动合并**——两个改动一起留下，没有 `<<<<<<<`。这也是为什么改动量很大的合并里，**大部分文件都能自动合，只有零星几处标红**——那零星几处才是**真的**存在\"两个意图碰头\"的地方。

**改一个配置，让冲突块多给你一段"祖先原文"。**上面图 9-1 那个冲突块只给了两段：你这一侧、对面这一侧。但三方合并明明有三份输入——**merge base 那份祖先原文，默认被 Git 藏起来了**。而判断"两侧各自想干什么"时，祖先正是意图的锚点：不知道 B 原来长什么样，你就说不清每一侧到底"改了什么"。把冲突风格换成 zdiff3：

```
git config --global merge.conflictStyle zdiff3
```

之后每个冲突块会变成三段：

```
<<<<<<< HEAD
  ...你这一侧...
||||||| 祖先 B 原来的样子
  ...共同起点...
=======
  ...对面那一侧...
>>>>>>> feature/user-refactor
```

`|||||||` 和 `=======` 之间就是 merge base 的原文（`diff3` 风格就有这一段；`zdiff3` 是它的改良版，还会把冲突块外的公共上下文一并标出来）。本章三步法的第一步"读两侧、各自说人话"，有了这一段才算证据链完整：**两侧各自相对 B 改了什么、谁动了谁没动，一眼可对**。建议全局开着它。

### 三方合并的两个盲点

现在开始注意听——这是本章最重要的两条祛魅：

**盲点一：Git 只看重叠的**\"**文本行**\"**，不看代码结构。**

如果你的改动和对面的改动**落到了同一段代码上**——哪怕两个人写的其实是同一件事——Git 都会标冲突。反之，如果两个改动**分散在不同的行上**，Git 会自动合并，即使它们**在语义上有致命冲突**。

**盲点二：Git 看不见跨文件的语义关联。**

`user.ts` 里改了 `fetchUser` 的签名，`profile.tsx` 里的调用点没变——两个文件都能自动合、都没冲突标记，代码却在运行时炸掉。**Git 这时候一片安静，你以为万事大吉——这才是真正危险的情形。**

这两个盲点合起来说明了本章的核心：

> **有 CONFLICT 标记的地方，是 Git 能帮你识别的\"表层冲突\"；没有 CONFLICT 标记但真的冲突了的地方，是\"语义冲突\"——它们不出现在合并阶段，只出现在你启动服务、跑测试、或者上线以后。**

所以**冲突解决的第一原则不是\"消掉红色\"，是\"守住语义\"**。红色只是 Git 力所能及的那部分提示，剩下的部分靠你（或者你和 AI 合起来的判断力）。

## 9.3 三种冲突的分类

把\"冲突\"这个笼统的词拆开，你日常会遇到的有三类，处理姿势不同：

### 9.3.1 表层冲突：有 `<<<<<<<` 标记的那种

刚才那种。两侧都动了同一段。Git 拒绝猜、把决定权交给你。**这一类是本章的主战场**，9.4 会展开处理流程。

### 9.3.2 语义冲突：没标记但已经错了

上面盲点二讲的那种。两个人的改动落在不同文件、不同函数、甚至同一文件的不同行，Git 全自动合了，**没有一处 `<<<<<<<`**——但组合起来的代码在语义上矛盾。

举几个真实的例子：

- **签名 vs 调用点**：小王在 `user.ts` 里把 `fetchUser(id: string)` 改成了 `fetchUser(id: string, options: FetchOptions)`，同时更新了所有调用点。小李在自己的分支上写了个新页面，调用了 `fetchUser("abc")`（老签名）。两个分支合并——`user.ts` 的签名变成了两参数版（小王的改动没被覆盖），`profile.tsx` 里小李的调用是单参数——TypeScript 编译报错，或者更糟：JavaScript 直接跑起来 `options` 是 undefined。**Git 一个 CONFLICT 都没报**。
- **重命名 vs 新引用**：小王把 `useUserStore` hook 改名成了 `useCurrentUser`，同时改了所有旧调用点。小李在自己分支写的新组件里 `import { useUserStore }`。合并——`useUserStore` 已经不存在了，小李的 import 变成 undefined。**没有 CONFLICT。**
- **配置项迁移**：小王把 `config.retryCount` 迁移到 `config.retry.count`（嵌套结构变了），改完了所有引用。小李在别的地方新加了一行 `config.retryCount = 5`。合并后——一个不存在的字段被写入，实际的重试次数保持默认。**没有 CONFLICT，跑起来也不报错，几周后线上重试策略行为异常，追查两天。**
- **数据库迁移顺序**：小王加了个 migration 001-add-email.sql，小李加了个 migration 001-add-phone.sql（都是 001）。文件名不冲突（不同名），文件内容不冲突（改的是不同表）——**Git 无感**——但两个人的 CI 都会因为 migration 编号重复而挂掉。

看清楚：**这些例子里 Git 都会开开心心地完成 merge，不打一个喷嚏**。它们只在\"跑起来\"的那一刻才暴露。

所以本章后面会反复强调一句话：**冲突解决完之后必须跑测试**。原因就在这里——测试能捕捉到的语义冲突，比合并算法能捕捉到的表层冲突**危险得多**，因为它们不吼你、不闪红、也没有 `<<<<<<<` 提醒。

### 9.3.3 结构冲突：add/rm 对峙、二进制文件、模式变更

第三类冲突，Git 也会报，但样子不像 `<<<<<<<`：

- **add/add**：两个分支都新加了一个同名文件，内容不同——Git 会标冲突，但没法用 `<<<<<<<`（整个文件都是新增的，没有共同祖先）。你要**在两个文件中选一份，或者把两份合并出一份**。
- **modify/delete**：你改了 `oldConfig.ts`，对面直接删了 `oldConfig.ts`。Git 冲突消息是 \"deleted in theirs and modified in HEAD\"。**决策是\"这个文件到底还要不要\"**——不是文本合并问题，是产品/架构问题。
- **rename/rename**：两边都改了同一个文件的名字，改成了不同的名字。**你要选一个名字。**
- **二进制文件**：两侧都改了 `logo.png`。Git 没法逐行 diff，只能\"两份文件里选一份\"。冲突消息是 \"binary files differ\"。**你要选一份，或者用图片编辑器手工合成一份新的。**
- **文件模式**：一侧把脚本的执行位打开了（`chmod +x`），另一侧改了内容。Git 会标 mode conflict，需要你决定权限位跟哪一侧。

这一类冲突的处理策略是**结构性决策**（要不要这个文件、叫什么名字、用哪个版本），不是行级仲裁。

一张对照表：

| 冲突类别 | Git 是否报警 | 决策焦点 | 主要风险 |
|---|---|---|---|
| **表层冲突** | ✅ `<<<<<<<` 标记 | 两侧文本各自的意图 | 无脑接受一侧，语义丢代码 |
| **语义冲突** | ❌ 静默通过 | 只有测试/编译能捕捉 | 潜伏到运行时才爆炸 |
| **结构冲突** | ✅ add/rm/rename/binary 提示 | 这个文件/名字/版本要不要 | 决策拍脑袋，事后返工 |

**本章后面主要讲第一类的处理流程 + 第二类的防护网 + 第三类的常见情形。**

## 9.4 心智模型：把每一段冲突当作一次仲裁

现在讲最要紧的东西：**面对一段 `<<<<<<< ======= >>>>>>>`，应该怎么想？**

不是**\"怎么删掉标记\"**——这是走法 A 的问题。是**\"两个意图之间应该怎么决断\"**。

给一个稳定的四步心智模型。每一段冲突都走一遍。

### 第一步：读两侧，各自说人话

不要先看代码。先在心里（或者打字给 AI）用一句话说清：

- **HEAD 那一侧想干什么？**（意图 A）
- **theirs 那一侧想干什么？**（意图 B）

举回开篇那个例子：

```
<<<<<<< HEAD
export async function fetchUser(id: string, options?: FetchOptions) {
  return apiClient.get(`/users/${id}`, options);
=======
export async function fetchUser(userId: number) {
  return apiClient.get(`/users/${userId}`);
>>>>>>> feature/user-refactor
}
```

- **意图 A（HEAD）**：给 `fetchUser` 加一个可选的 `options` 参数，用来传缓存策略、超时之类的配置。**功能扩展**。
- **意图 B（theirs）**：把用户 id 的类型从 `string` 改成 `number`，跟后端 ID 类型对齐。**类型重构**。

**读出来的这一刻，一半的事情已经结束了**。你已经知道\"这不是同一件事\"——A 加了个新参数，B 换了参数类型。它们不是\"两个方案二选一\"，是\"两件不相干的改动碰到了同一段代码\"。

**这一步 AI 做得极好**——比大多数人做得好。语言模型对\"读懂代码在干什么\"这种任务是有优势的：它没有肌肉记忆里的偏见（\"我这边肯定是对的\"），能同等地把两侧当输入分析。**这也是本章后面 AI 指令箱最大的用法：让 AI 读两侧、总结意图，但不改任何文件。**

### 第二步：判断关系

意图读出来之后，四种关系里选一种：

**（a）真冲突——两个意图互斥，只能选一个。**
比如\"把某个开关默认打开\"vs\"把它默认关闭\"——两个人对默认值有分歧，必须选一个。**这一类通常需要拉两位改动者到一起对齐**（比如 Slack 上问一句）——**不是技术判断，是产品/架构判断**。技术上你可以任选一侧，但你要选\"对的那一侧\"，就需要业务上下文。

**（b）伪冲突——两个意图正交，其实两个都要。**
上面那个例子就是。给函数加 options 参数、把 id 改成 number——这两件事互不影响，本来可以同时存在。**Git 只是因为它们碰到了同一段文本才报冲突**。**这一类的解决方案是\"把两侧合起来\"**——保留 B 的 number 类型、也保留 A 的 options 参数：

```typescript
export async function fetchUser(userId: number, options?: FetchOptions) {
  return apiClient.get(`/users/${userId}`, options);
}
```

**这一段代码在原始的两侧里都不存在**——它是**第三个版本**，从两侧的意图中综合出来。这才是\"解决冲突\"的正确姿势。走法 A 的错误在于它只会\"二选一\"，从不合成第三份。

**（c）过时冲突——一侧的意图已经不需要了。**
比如你半个月前在自己的分支上改了个函数，今天要合入 main，发现 main 上那个函数早已被另一个人整个重写了、你原来那个改动已经不适用了。此时正确的选择是**放弃你这一侧**（这个场景里你在自己分支上合入 main，对面 main 才是 `--theirs`：`git checkout --theirs <file>`，等价的新写法 `git restore --theirs <file>`；**方向反过来——在 main 上合你的分支——同一段代码就得用 `--ours`**。或手工留下对面版本）——**不是因为你输了，是因为你要解决的问题已经被别人用别的方式解决了**。**\"接受对方\"在这里不是投降，是识别现实**。

**（d）需要改设计——两个意图叠加暴露了架构问题。**
比如两个人都在给同一个函数加\"特殊情况处理\"，两边加的处理逻辑合起来会让这个函数臃肿不堪、责任混乱——**这时候真正正确的做法不是\"合并两侧\"，是\"停下来把这个函数拆开\"**。冲突不是一个待清理的红色，是一个信号：**这一处的设计已经不能承受再多的\"if 分支\"了，架构需要动手术**。

（d）这种关系很少见但很重要——**它是资深工程师和熟练工的分水岭**：熟练工把冲突当噪音、专注于消掉红色；资深工程师把冲突当信号、听懂它想告诉你的架构信息。

### 第三步：动手

- 是 (a)：拉相关人对齐、选一侧。用 `git checkout --ours <file>` / `git checkout --theirs <file>` 一键取一侧，或手工编辑。
- 是 (b)：手工合成第三份。**必须自己想清楚合成后的语义，AI 只能提议、你必须过目**。
- 是 (c)：一键取对面（`--theirs`，前提是合并方向为"在你自己分支上合入 main"；方向反过来它取的就成了你自己，要换 `--ours`——新写法对应 `git restore --theirs/--ours <file>`）。**顺手看一眼你被丢弃的改动想解决的问题，现在是不是真的已被别的方式解决了**——如果不是，你还要补一次改动，不是就此结束。
- 是 (d)：不要立刻解决。开个新 commit 或新分支做设计调整，然后再回来 merge——**冲突可以被\"绕开\"，前提是你识别出它是设计信号**。

### 第四步：验证

**这是走法 A 从来不做的事**，也是本章反复强调的：

- 编译通过（如果是编译型语言）。
- 类型检查通过（TypeScript、Flow、mypy 等）。
- **单元测试和集成测试全部跑一遍**——不是\"跑一下我改过的\"，是**跑一遍**，因为语义冲突可能藏在你没碰过的地方。
- 手工冒烟一下你合并的这段功能真的还工作。

**忘了这一步的\"冲突解决\"，只解决了红色的 1/3，剩下 2/3 的语义风险留给下一个人（很可能是几小时后的你自己）**。

用一张图把四步心智模型总结一下：

```
每一段 <<<<<<< ======= >>>>>>>
   │
   ├─ 第一步：读两侧 → 用人话说清各自意图（A 想干什么、B 想干什么）
   │                    ↑
   │                    AI 在这一步做得比大多数人好
   │
   ├─ 第二步：判断关系
   │       ├─ (a) 真冲突 ── 拉人对齐、选一侧
   │       ├─ (b) 伪冲突 ── 手工合成第三份
   │       ├─ (c) 过时  ── 接受对面
   │       └─ (d) 设计信号 ── 停下重构
   │
   ├─ 第三步：动手（选一侧 / 合成 / 保留对面 / 重构）
   │
   └─ 第四步：验证（编译 + 类型 + 测试 + 冒烟）
              ↑
              走法 A 从来跳过这一步
```

**你如果只从这一章带走一样东西，就是这四步**。它比任何具体的命令都重要——它是把\"消红色\"变成\"做仲裁\"的心智切换。

## 9.5 特殊情形：AI 时代的几种典型冲突

上面的四步适用于\"两个人写代码碰头\"的常规冲突。但你日常还会碰到几种特殊情形，它们的最佳姿势和常规冲突有出入，单独说一下。

### 9.5.1 lockfile 冲突（package-lock.json / yarn.lock / Cargo.lock / go.sum）

假设你 `pull` 后 `package-lock.json` 冲突了——那个文件通常有几万行，`<<<<<<<` 密密麻麻散布在里面。**新手会试图\"手工合\"**——挨个看每一段冲突、决定保留哪个版本号。**十分钟后彻底放弃，随便留一侧了事，结果依赖树坏掉，`npm ci` 报一堆奇怪的错**。

**lockfile 的正确处理姿势是\"重新生成\"，不是\"手工合\"**。因为：

- lockfile 是**从 `package.json` 出发的确定性推导结果**——只要 `package.json` 的语义合并对了，lockfile 应该重新算出来的。
- **手工合的 lockfile 几乎必然是\"坏的\"**——依赖树里各版本约束互相牵制，你手工挑的组合大概率不满足所有约束。
- 手工合还有一个更阴险的问题：即使你合出来的 lockfile 侥幸能装、能跑，也**不能保证**它反映的依赖版本组合和别人合出来的是同一份——**同一段代码在不同开发者机器上安装出不同版本的依赖**，是 lockfile 存在的意义之被彻底架空。

标准处理流程：

1. 手工合 **`package.json`**（或对应语言的清单文件——只有几十行到几百行，四步心智模型正常适用）。
2. **删掉冲突中的 lockfile**——`git checkout --theirs package-lock.json` 或直接 `rm`。
3. **`npm install`**（或 `yarn`、`cargo build`、`go mod tidy`）——让工具从合并后的 `package.json` 重新算一份 lockfile。
4. `git add package-lock.json` 一起提交。

同样的原则适用于：`yarn.lock`、`pnpm-lock.yaml`、`Cargo.lock`、`Gemfile.lock`、`poetry.lock`、`go.sum`、`Podfile.lock`——**所有\"从清单文件推导出来的锁定文件\"**。**判定标准**：如果这个文件是**由工具生成、而不是人手写的**——碰到冲突，**扔掉重新生成，不要手工合**。

### 9.5.2 生成物冲突（dist / build / migrations 的编号）

同一个道理外推：任何工具生成的产物在 lockfile 之外——`dist/`、`build/`、`.next/` 这类构建输出——出现在仓库里本身就是配置错误（应该在 `.gitignore` 里），碰到冲突时也是\"扔掉重新生成\"。

数据库 migration 是个特殊变体：**migration 文件本身是手写的，但编号是全局有序的**。两个分支各加了一个 `001-add-x.sql`——**这不是 Git 能报的冲突**（文件名不同、内容不同），但一合并就是编号重复。**解决方案是把后到的那个 migration 重命名成下一个可用编号**（002），并检查内部是否依赖前一个 migration 的结果。**这也是本章前面 9.3.2 讲过的\"语义冲突\"典型例子**——Git 不知道，测试/CI 才发现。

### 9.5.3 二进制文件冲突（图片、字体、Office 文档）

`logo.png` 两个分支都改了。Git 不会给你 `<<<<<<<`（没法 diff），会说 `warning: Cannot merge binary files`。你必须**在两份文件之间选一份**：

```
git checkout --ours logo.png       # 用我这一侧的
git checkout --theirs logo.png     # 用对面那一侧的
git add logo.png
```

或者更负责的做法：**打开图片对比软件、把两侧的改动人工合成一份新图**——比如你改了 logo 颜色、对面改了 logo 尺寸，最终版本颜色 + 尺寸都要——**再 `git add`**。

**大二进制文件天然不适合并行修改**——设计资产、模型权重、大文档，都应该在团队约定里\"同一时间只有一个人在改\"，或者用 Git LFS + 加锁机制（`git lfs lock`）。**Git 本身对二进制文件的合并支持基本是零，别期待它。**

### 9.5.4 rebase 冲突 vs merge 冲突

第 5 章讲过，rebase 遇到冲突是\"逐颗珠子停\"、merge 遇到冲突是\"一次性全爆\"。**这两种停下来的时刻，心智模型是同一个**（还是四步仲裁）——但操作细节不同：

| 项 | merge 冲突 | rebase 冲突 |
|---|---|---|
| 冲突同时暴露的量 | 一次性全部 | 每颗新珠子最多一批 |
| `HEAD` / `--ours` 是谁 | 你当前所在分支 | **正在被重放的目标分支**（rebase 会把 --ours 和 --theirs 的语义颠倒——这里是最容易搞错的一处） |
| 解决完提交的命令 | `git add` + `git commit` | `git add` + `git rebase --continue` |
| 放弃退出 | `git merge --abort` | `git rebase --abort` |
| 一颗珠子里只想跳过 | ——（无） | `git rebase --skip`（慎用） |

**rebase 冲突里 `--ours` 和 `--theirs` 的语义颠倒**是个大坑：merge 里 --ours 是你当前的分支、--theirs 是被合入的分支；rebase 里 --ours 是**目标 base**（你要重放到的分支）、--theirs 是**你自己**（正在被重放的分支）——因为 rebase 的物理动作是\"把你的珠子重放到别人分支上\"，Git 视角里\"当前所在\"其实是别人的分支。**这一点每次 rebase 冲突时都要提醒自己一遍**，或者干脆看具体内容不看 --ours/--theirs。

### 9.5.5 冲突相关的 Git 内置武器

顺手记一下这几个救急工具，遇到再看：

- **`git status`**：随时告诉你哪些文件还有未解决的冲突（\"both modified\"）、哪些已经 add 完了。冲突过程中反复用它对位。
- **`git diff --check`**：检查文件里是不是还有漏删的 `<<<<<<<` 或 `>>>>>>>` 标记——**手工合的时候万一漏了一行标记，代码会编译不过**，这条命令一秒查出来。
- **`git diff --ours` / `git diff --theirs`**：只看你解决出的版本相对某一侧的差异。**手工合完后用来\"复盘\"——我的最终版本相对哪一侧改了什么？如果相对某一侧完全一致，那我其实就是选了一侧，没做合成**。
- **`git checkout --ours <file>` / `--theirs <file>`**：整个文件保留一侧，不进入行级仲裁。lockfile / 二进制 / 明确的整体决策场景用。
- **`git merge --abort` / `git rebase --abort`**：一键放弃，回到操作前。**\"我搞不定，先不合了\"是完全合法的选项，不是失败**——总比合出一份烂代码强。
- **`git mergetool`**：调起一个三方合并 UI（VS Code、Meld、Beyond Compare 都行），用图形化的方式看 base + ours + theirs 三栏。**手工合复杂冲突时值得一开**，尤其对新手。

## 9.6 AI 介入点：能做什么、不能做什么

这是本章最有 AI 时代特色的一节。前面反复暗示过，现在系统讲一遍。

### 9.6.1 AI 能做得好的事（绿色区）

**① 读两侧、总结意图。**
把 `<<<<<<< ======= >>>>>>>` 那一段代码贴给 AI，让它用中文说清楚\"HEAD 那一侧想干什么、theirs 那一侧想干什么\"——**这一步 AI 做得比大多数人做得好**。它没有\"我这边肯定是对的\"的偏见，能同等地把两侧当输入。这是本章 AI 指令箱的头号用法。

**② 分类冲突关系（真冲突 / 伪冲突 / 过时 / 设计信号）。**
你把两侧意图告诉 AI，让它判断这是 (a)(b)(c)(d) 里的哪一种、给出理由——**它的分类通常靠谱**，尤其在 (b) 伪冲突（\"其实两个都要\"）的识别上。

**③ 对伪冲突提议合成版本。**
让 AI \"给我一份把两侧意图都保留的合成版本\"。**它能提出一个可读的第三版**——你要过目，但通常八九不离十。这是节省时间最直接的地方。

**④ 冲突后帮你审查语义完整性。**
合完之后，让 AI \"扫一遍这个文件，看看有没有类型不一致、有没有引用了不存在的函数/字段、有没有 dead code 或未使用的 import\"——**这是对语义冲突（9.3.2）的一道 AI 层防护网**，比\"跑测试\"更快、但不能替代跑测试。

**⑤ 为 lockfile 之类的机械冲突自动跑重新生成流程。**
\"帮我 checkout --theirs package-lock.json 然后 npm install 再 add\"——**这类无需仲裁的机械步骤，AI 是最省事的操作代理**。

### 9.6.2 AI 只能提议、必须人确认的事（黄色区）

**① (a) 类真冲突的仲裁选择。**
AI 可以告诉你两侧各自想干什么、甚至可以给出建议\"如果你的产品目标是 X 我倾向于 A 侧\"——**但\"选 A 还是选 B\"这一步必须人拍板**，因为它取决于产品意图和团队上下文，AI 不知道。

**② (d) 类设计信号的重构。**
AI 可以识别出\"这段冲突暗示函数职责过多、建议拆开\"——但\"拆成什么样、要不要现在拆\"是架构判断，涉及范围远超冲突本身。**AI 提议合理，落地必须人主导**。

**③ 跨文件的语义冲突识别。**
上面 9.3.2 讲的那种（改签名 vs 改调用点）——**AI 可以帮你扫**（\"给我列出这次合并涉及的所有函数签名变更，以及可能受影响的调用点\"），但它给的清单**不能替代跑测试**。它能减少你 grep 的工作量，不能给你交付信心。

### 9.6.3 AI 绝不能做的事（红色区）

**① 无脑\"自动接受一侧\"。**

这是本章的一号警示。市面上的一些 AI 工具在冲突解决上有\"one-click resolve\"或\"auto-accept\"式的按钮/命令——**尤其在批量冲突（比如 rebase 遇到十几颗珠子的连续冲突）时特别诱人**，一键之后红色都没了。

**这是失败模式的头号来源。** 调研报告里记录过多起真实事故：

- **AI 在 rebase 冲突里默认选择\"接受 incoming\"**（对应 --theirs），把开发者一天的改动全部覆盖。事后 reflog 里能找回，但发现问题时已过了两个 sprint。
- **AI 在解决 lockfile 冲突时\"任选一侧\"完事**，结果依赖版本组合和其它开发者的机器不一致，CI 挂了三天没人反应过来问题在这。
- **AI 在设置了 `git rerere`（重复冲突自动记录）后按上一次的选择自动应用**——但这次的\"上下文\"和上次不一样，自动选择的其实是错的，语义悄悄丢了。

**核心原理**：\"自动接受一侧\"本质上是**用二选一代替仲裁**——它对 (a) 类冲突可能勉强凑合（如果它选对了那一侧），对 (b) 类冲突（伪冲突）就是**灾难**——因为 (b) 类的正确解是\"合成第三份\"，二选一必然丢掉另一侧的意图。**AI 无脑接受一侧时，语义丢代码是必然结果，只是问题什么时候暴露**。

**② 修改文件不留痕迹地绕过冲突。**

个别 AI 工具在遇到 rebase 冲突时会尝试\"改写你的旧 commit\"来绕过冲突——这是**破坏历史 + 破坏隔离**的双重违规。**任何 AI 冲突解决的过程都必须留下 Git 记录**（新 commit / rebase --continue 后的新 SHA），绝不允许\"神秘地就好了\"。

**③ 在共享分支上强推冲突解决结果。**

冲突解决结束后如果发现 push 被拒（non-fast-forward），AI 不应该\"顺手 --force\"——这一条已经在第 5 章讲过（黄金规则）、第 12 章还会讲，本章只是把它再叮嘱一遍：**冲突解决 ≠ 授权 force push**。

### 9.6.4 一张 AI 介入点全景表

| 环节 | AI 表现 | 人的角色 |
|---|---|---|
| 读两侧、说人话 | ⭐⭐⭐⭐⭐ | 听、点头 |
| 分类冲突关系 (a)(b)(c)(d) | ⭐⭐⭐⭐ | 核对分类 |
| 伪冲突合成第三份 | ⭐⭐⭐⭐ | **必须过目并验证** |
| 真冲突的选边 | ⭐⭐ | **决策权在人** |
| 设计信号的重构 | ⭐⭐⭐（提议） | **主导权在人** |
| 语义冲突扫描 | ⭐⭐⭐ | 跑测试兜底 |
| lockfile / 机械冲突 | ⭐⭐⭐⭐⭐（执行） | 检查结果 |
| \"自动接受一侧\" | 🚫 禁止 | 禁止 |
| 冲突后 force push | 🚫 禁止 | 禁止 |

## 9.7 AI 指令箱 · 冲突

以下指令模板与工具无关（Claude Code / Cursor / Copilot / Aider / Windsurf 皆适用）。**颜色标注**：冲突处理的指令主要是黄色——所有\"动文件\"的动作都要盯着；只有\"读两侧、说人话\"这一类是绿色的。

**🟢 仲裁辅助类（只读，不改文件）**

- 「我现在在冲突状态。用 `git status` 列出所有还未解决的冲突文件，按'两边都改'/'一边加一边删'/'二进制'/'lockfile'分类。这一步不要改任何文件。」
- 「读文件 `src/api/user.ts` 里的每一段 `<<<<<<< ======= >>>>>>>`。对每一段告诉我：（1）HEAD 那一侧的改动想干什么，用一句话；（2）theirs 那一侧的改动想干什么，用一句话；（3）这两侧的意图是相同的、正交的、还是互斥的。**不要改任何文件**——只输出分析。」
- 「读这次 merge 涉及的两侧最近 10 个 commit 的 message，告诉我：HEAD 分支这段时间在做什么主题的工作，theirs 分支在做什么主题的工作。冲突集中在哪些主题的交界处。」
- 「用 `git log --merge --oneline` 列出这次冲突涉及的两侧独有 commit，帮我判断：（1）这次合并跨了多久（两侧分叉多久了）；（2）冲突主要来自哪一侧的哪几个 commit。」

**🟡 合成/仲裁类（会改文件，先看方案再动手）**

- 「针对 `src/api/user.ts` 里那段 `fetchUser` 的冲突：我判断这是伪冲突（HEAD 加 options 参数、theirs 改 id 类型，两个都要）。**先给我一份合成后的代码文本、不要动文件**——我读过之后你再帮我写进去。」
- 「针对整个文件级别的冲突，帮我操作：（1）`git checkout --theirs package-lock.json`；（2）`rm -rf node_modules`；（3）`npm install`；（4）`git add package-lock.json`。执行前先把这四步列给我确认。」
- 「这个二进制文件 `assets/logo.png` 有冲突。给我三个选项：（a）保留我这一侧（`git checkout --ours`）；（b）保留对面（`--theirs`）；（c）打开图片对比工具让我手工看。我选完你再动手，不要默认选任何一个。」

**🟡 复盘/验证类（冲突解决之后必跑）**

- 「我刚解决完所有冲突，还没 commit。执行前的自查：（1）用 `git diff --check` 检查有没有漏删的 `<<<<<<<` 或 `>>>>>>>` 标记；（2）用 `git status` 列出所有 add 完的和未 add 的；（3）用 `git diff --ours` 展示我最终版本相对我这一侧的改动、`--theirs` 展示相对对面的改动——**让我看看有没有一整段冲突我实际上只是接受了一侧（这可能是我漏做了合成）**。」
- 「冲突解决完了。跑一遍完整测试（不只是我改过的文件）：（1）编译/类型检查；（2）单元测试；（3）集成测试；（4）如果有 lint，也跑一下。有任何失败停下来告诉我，不要\"自动修复\"。」
- 「合完之后扫一遍这个 diff，找语义冲突的迹象：（1）有没有函数签名变了、但调用点没跟着改；（2）有没有引用了不存在的字段/函数/import；（3）有没有类型看起来不匹配的地方（比如 string 传给期望 number 的参数）。**只列可疑处，不改代码**。」

**🔴 明确禁止（哪怕 AI 自己想做也拒绝）**

- 「任何情况下**不要\"自动接受一侧\"**（不要因为一侧看起来是主流、更新、或和别处一致就默默选它）——**永远先让我读两侧的意图**。」
- 「rebase / merge 冲突处理过程中**不要修改冲突以外的 commit**，不要\"顺手整理\"我别的 commit。这次任务只处理当前冲突。」
- 「冲突解决后 `push` 被拒（non-fast-forward）时**不要**执行 `git push --force`。停下来告诉我为什么被拒（可能是 rebase 改了历史 / 可能是远端有新推送 / 可能是共享分支），我来决定。」

**训练用指令（陪练模式）**

- 「给我 5 段虚构的 `<<<<<<< ======= >>>>>>>` 冲突片段，覆盖：真冲突 (a)、伪冲突 (b)、过时冲突 (c)、设计信号 (d)、和一段实际上没有真冲突（应该合成）。我读完告诉你我判断是哪一类、要怎么处理，你批改。」
- 「造一个跨文件语义冲突的场景：一个分支改函数签名、另一个分支写新调用点。用两段 diff 告诉我'合并算法看到的是干净的自动合并'，然后让我说出这里为什么危险、我该做什么检查。」

## 9.8 执行后的世界

冲突处理过程中你（或 AI）敲的每一条命令，`.git` 目录里发生了什么？透视一下：

| 你说的话 | AI 大概率执行 | `.git/` 里的真实变化 |
|---|---|---|
| \"pull 一下\" | `git pull`（= fetch + merge） | `refs/remotes/origin/...` 更新；发现两条项链分叉需要 merge；`.git/MERGE_HEAD` 写入待合入分支的 sha；`.git/MERGE_MSG` 写入默认合并消息；冲突文件里插入 `<<<<<<< ======= >>>>>>>` 标记；工作目录停在\"合并中\"状态 |
| \"我在冲突里\" | `git status` | 只读 `.git/index` 和上一条留下的 `MERGE_HEAD`——报告\"you have unmerged paths\"；对每个冲突文件显示 index 里的三个 stage（stage 1 = base、stage 2 = ours、stage 3 = theirs）|
| \"用 theirs 的整个 package-lock.json\" | `git checkout --theirs package-lock.json` | 从 index 的 stage 3 读出 theirs 版本的内容，覆盖工作目录里的 `package-lock.json`。**index 里的三个 stage 还在**，直到你 `git add` 后才会归并为单一 stage 0 |
| \"add 一下这个文件\" | `git add <file>` | 把工作目录里的当前内容写进 `.git/objects/`（造一颗 blob）；`.git/index` 里那个文件的三个 stage（1/2/3）**合并为单一 stage 0**——从 Git 视角这个文件的冲突就解决了 |
| \"commit\" | `git commit` | 造一颗新 commit 对象；**如果 `MERGE_HEAD` 存在，这颗 commit 会有两个 parent**（ours 和 theirs 各一）——这就是第 5 章讲过的 merge commit；`MERGE_HEAD` / `MERGE_MSG` 被删掉；当前分支名牌前移到新 commit |
| \"rebase 冲突里 continue\" | `git rebase --continue` | 读 `.git/rebase-merge/`（或 `rebase-apply/`）里的\"接下来要重放的珠子清单\"；用当前工作目录内容造一颗新 commit；再尝试重放清单里的下一颗——如果又冲突，再停一次 |
| \"放弃这次合并\" | `git merge --abort` | 读 `.git/MERGE_HEAD` 和 `ORIG_HEAD`；把工作目录、暂存区、当前分支名牌都恢复到 merge 之前的状态；删掉 MERGE_* 文件；**冲突过程中你手动改过的内容全部丢失**（除非你 stash 过） |
| \"放弃这次 rebase\" | `git rebase --abort` | 读 `.git/rebase-merge/orig-head`；把分支名牌恢复到 rebase 开始前；工作目录、暂存区也一并恢复；删掉 rebase 状态目录；**rebase 中间你手动解冲突的内容也都丢失** |
| \"reflog 找回刚才被 abort 掉的解冲突进度\" | ——（找不回） | **reflog 记的是分支/HEAD 的移动**，不记你在工作目录里的临时编辑。**没 add 过的手工合内容，abort 后就是没了**——这就是为什么冲突解决过程中\"先小步 commit 保命\"（工作目录里合一部分就 `git add` 一部分）比\"想合完了一次 commit\"更安全 |

看懂这张表你会最终确认本章的两条底层事实：

1. **\"解决冲突\"这个动作，在 Git 里就是\"往 index 的 stage 0 里写一份内容 + 一次 commit（如果是 merge）或 rebase --continue（如果是 rebase）\"**——它是普通的\"造珠子 + 挪名牌\"，没有魔法。
2. **`MERGE_HEAD` 存在就意味着你处于\"合并中\"状态**。这个状态下的每一次 commit 都会自动带上两个 parent——它是从\"合并中\"跨到\"合并完\"的具体机制。你查看这个文件（`cat .git/MERGE_HEAD`）随时能确认\"我现在到底还是不是在合并中\"。

## 9.11 三大典型误解拆解

**误解一：\"冲突意味着我做错了什么。\"**

**没有**。冲突是**并行工作的必然产物**——两个人（或两个分支上的你自己）在同一段代码上有独立的改动、Git 老老实实把这件事告诉你、请你决定怎么办。这是 Git 忠于职守的表现，不是它\"出错\"，更不是你\"做错\"。**看到 CONFLICT 就慌\"是不是我搞坏了\"是新手最常见的心理反应**——它让你手忙脚乱地想\"消掉红色\"，然后走向本章开头那种 \"走法 A\" 的语义灾难。心态调整：**每次看到 CONFLICT，把它读成\"轮到你做决定了\"**——不是\"Git 报错了\"。真正让你担心的场景恰恰是**没有** CONFLICT 但两侧都改过的情形（9.3.2 语义冲突）——那才是需要跑测试才能防的、真正藏刀子的地方。

**误解二：\"AI 现在这么强，让 AI 自动解冲突就好了。\"**

**这句话最危险的地方在于\"自动\"这两个字**。让 AI **辅助**解冲突（读两侧、分类、提议合成、扫语义）是本章鼓励的做法；让 AI **自动**解冲突（无脑接受一侧、批量一键 resolve）是本章明确禁止的红色区。区别在哪？在于\"仲裁\"这个词——冲突的本质是**两个意图之间的取舍**，取舍需要业务上下文、需要架构判断、需要\"我知道我们团队的默认值是什么\"这类只有人（或团队）知道的东西。AI 可以帮你把仲裁做得更快（读得更透、合得更整齐），但它**不能替代你做仲裁**——一替代就退化成二选一，二选一遇到伪冲突就是丢代码，遇到设计信号就是错过重构机会。**记住这条口诀：AI 是你的仲裁助手，不是你的仲裁员。**

**误解三：\"合完不冲突就可以推了。\"**

**不冲突≠没问题**。这是全章最重要的一条祛魅，值得再重复一遍：Git 的合并算法只看文本、只看行、只看重叠——它捕捉的是\"表层冲突\"这一小片。**\"跨文件的签名 vs 调用点\"、\"重命名 vs 新引用\"、\"配置项迁移 vs 新写入\"、\"migration 编号撞车\"、\"两侧独立引入了不兼容的第三方库版本\"——这些语义冲突全都是 Git 无感的**，合完 log 干干净净、没有一个红字，但你一跑就爆炸。**所以本章反复说的那句话必须变成肌肉记忆：冲突解决完（即使合得看起来很顺利）必须跑一遍完整测试——不只是编译过、不只是类型检查过，是把测试跑一遍**。有 CI 的仓库把这一步交给 CI；没 CI 的仓库自己在本地跑；懒得跑的仓库就是把语义炸弹埋在下一次生产事故里。**你觉得\"这次合得挺干净的，测试可以不用跑\"的每一次侥幸，都是在下注**——赌注是\"这几个改动之间没有跨文件的语义关联\"，赢多少次赔一次都不划算。

## 9.12 下一章预告

你已经会\"读两侧、做仲裁、验证结果\"——冲突这一关的心智模型已经交到你手上了。**但真实世界里，还有一类更急的场景**：**你不是在合并两条项链，你是在慌乱地想找回一条以为丢了的项链**。

**第 10 章《事故恢复：Git 几乎不扔东西》** 是场景决策部分的一个转折——从\"顺境和逆境下的日常决策\"转到\"事故现场的止损与救援\"。六大高频事故 + 一套稳定的恢复剧本：

- 提交到错误分支（还没 push）；
- 误删分支（`branch -D` 已按下、reflog 是最后一根救命稻草）；
- rebase 搞砸了（`.git/rebase-*` 目录还在 vs 已经 finish）；
- detached HEAD 上写了一堆 commit、切走之前忘挂名牌；
- stash 冲突（stash 恢复时又和当前工作目录冲突）；
- 已经 push 出去的错误（涉及第 5 章讲过的 revert vs reset 抉择）。

**核心论点**：**读者不必记住 `reflog` + `reset ORIG_HEAD` 的具体组合**——只需要能对 AI 说清\"我刚 rebase 搞砸了，帮我回到之前\"、并且**知道 AI 什么时候在建议一个不可逆的操作、需要你踩刹车**。本章教你的\"AI 是助手不是仲裁员\"这条原则，到那一章会变成\"AI 是救援副驾不是主驾\"——**你才是那个握方向盘的人**。

**从这一章开始，前面所有章节的\"造珠子 + 挪名牌\"、\"reflog 是保险丝\"、\"共享分支上不重写\"这几条底层原理，全部会变成你在事故现场稳住心跳的具体工具**。

> **🤖 AI 指令箱 · 本章实战演练**
>
> 找一个你自己的真实仓库（或造一个沙盒仓库）——不建议在生产分支上做这些练习。按顺序练：
>
> - **造真冲突、走一遍四步**：「在 main 上造 3 颗 commit。开 feature 分支，在其中一个函数里加 options 参数并更新一个调用点。回 main，在同一个函数里把 id 类型改成 number 并更新调用点。回到 feature，`git merge main`——预期会有冲突。**按四步走**：（1）问 AI 用中文说清两侧意图；（2）分类；（3）合成第三份（伪冲突场景）；（4）跑测试（造一个简单的类型检查即可）。」
> - **造语义冲突、体会\"合得干净但错\"**：「同样的仓库，另开分支，一个只改函数签名（新增可选参数）、一个只在别的文件加一个用老签名的调用点。合并——观察 Git **没报冲突**。让 AI 扫一遍 diff，看它能不能识别出跨文件的语义风险。然后 `tsc`（或对应工具）跑一下——观察问题在这一步暴露。」
> - **练 lockfile 冲突**：「造一个 npm 项目，两个分支各自 `npm install` 加入一个不同的依赖。合并——`package-lock.json` 冲突。**不要手工合**：让 AI 走\"删掉 lockfile → npm install → add\"这套流程。」
> - **练\"放弃是合法选项\"**：「造一个复杂 merge，故意让冲突多而丑。开始解、解到一半发现太乱、`git merge --abort` 退出。**观察工作目录被完整恢复、你手工合的内容全部消失**。以后每次开始合之前问自己一句\"如果我搞不定，abort 出来的代价是什么\"——答案通常是零，这就是你敢试的底气。」
> - **练 AI 的边界**：「故意让 AI 犯错——问它\"给我批量一键 resolve 所有冲突，随便选一侧就行\"。观察 AI 是听话地干、还是拒绝并解释为什么不能这么做。如果 AI 老老实实一键解了，**这就是这个工具在你手上不能被信任解冲突的证据**——从此这类操作永远手工过，或者换工具。」
