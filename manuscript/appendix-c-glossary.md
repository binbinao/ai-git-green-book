## 一、仓库与对象（对应第 1 章）

**Repository（仓库）**：一个自包含的历史数据库，全部机密都藏在项目根目录下的 `.git/` 里。克隆一个仓库，就是把这整个数据库复制一份到你手上。
　常见混淆：**≠ 项目源码文件夹**。工作区（working directory）是仓库"照到当前时刻的镜面"，`.git/` 才是仓库本体。删掉 `.git/` 不影响文件，但仓库就没了。

**`.git/` 目录**：仓库的物理实体，一个纯文件+索引结构的迷你数据库，包含所有对象、引用、配置、日志。
　常见混淆：**≠ 隐藏配置**。它不是"配置文件"，是**整个项目的时间机器**。全世界被复制次数最多的迷你数据库。

**Object（对象）**：Git 内部的最小存储单元，共四种：blob、tree、commit、tag。每个对象都由内容算出 SHA-1，存放在 `.git/objects/` 下。
　常见混淆：**≠ 文件**。对象是"内容的不可变胶囊"；同样内容永远得同样 SHA，跨仓库都能对上。

**Blob（数据块）**：一个文件某个版本的内容快照，去掉了文件名——只是"这坨字节"。
　常见混淆：**≠ 文件**。文件名不在 blob 里，而在 tree 里。同一段内容不论叫什么名字，全仓库只存一份 blob。

**Tree（树对象）**：一个目录快照。列出这个目录下每个条目的文件名 + 权限 + 指向的 blob 或子 tree。
　常见混淆：**≠ 文件夹**。tree 是一份"清单快照"，本身不占空间意义上的目录，只是引用其它对象。

**Content-addressed storage（内容寻址存储）**：Git 用"内容的 SHA-1 哈希"作为对象的地址。同内容 = 同地址；改一个字节 = 换新对象。
　常见混淆：**≠ 位置寻址**。你不问"这个文件存在哪"，你问"这份内容存在吗"。这就是 Git 去重、可信、可分布式同步的物理基础。

**SHA-1 / Object ID**：40 位十六进制字符串（如 `d3adb33f...`），Git 内部所有对象的唯一身份证。
　常见混淆：**SHA 不是"版本号"**。它是内容指纹，没有先后大小之分。日常你用前 7–8 位（`d3adb33`）指代一个提交，仍然精确。

**Bare repository（裸仓库）**：只有 `.git/` 目录内容、没有工作区的仓库，专门供 push 用。服务端仓库（如 GitHub 上那一份）本质就是裸仓库。
　常见混淆：**裸 ≠ 空**。裸仓库里可以有全部历史，只是没铺开工作区；你不能在它里面直接改文件。

**Working directory（工作区）**：你能用编辑器打开、能 `ls` 看到的那份铺开的文件树。它是仓库照到"当前 HEAD"的镜面。
　常见混淆：**≠ 仓库**。改工作区不等于改历史；不 `commit`，改动就只在工作区里飘着。

**Staging area / Index（暂存区）**：介于工作区和仓库之间的一层"待办清单"。`git add` 把改动搬进来，`git commit` 把清单一次性打包成快照。
　常见混淆：**≠ 备份**。暂存区不是保险箱，它随时会被 `add` 覆盖。真正的"存住"要等 commit。

**三区模型（Working / Staging / Repository）**：Git 日常操作围绕的三层结构。工作区里改、暂存区里挑、仓库里定型。
　常见混淆：**≠ 客户端/服务器**。三区都在你本地。远程仓库是第四层，与三区正交。

## 二、提交与快照（对应第 2 章）

**Commit（提交）**：一次不可变的**全量快照** + 元信息（作者、时间、消息、父提交）。历史项链上的一颗珠子。
　常见混淆：**≠ 差异（diff）**。提交存的是"这一刻整个 tree 长什么样"，不是"改了哪几行"。diff 是 Git 事后算出来给你看的。

**Snapshot（快照）**：一次提交所指向的整棵 tree。全量，不是增量。
　常见混淆：**≠ 备份文件**。快照是逻辑概念，物理上由对象共享去重，不会真的每次都复制一遍全项目。

**Parent（父提交）**：一个提交里记录的"我是从哪个提交长出来的"。普通提交有 1 个父，合并提交有 2 个及以上，初始提交没有父。
　常见混淆：**≠ 时间上的前一个**。父指针决定的是拓扑关系，不是时间戳先后；rebase 之后时间戳可能乱，父指针才是历史真相。

**Merge commit（合并提交）**：有两个及以上父提交的提交，代表两条历史在此汇合。
　常见混淆：**与"普通提交"的唯一区别是父的数量**。合并提交本身也是一颗珠子，只不过它有两根线拴上去。

**Author vs Committer（作者 vs 提交者）**：作者是最初写下改动的人，提交者是最后把它记进历史的人。rebase / cherry-pick 时两者会分离。
　常见混淆：**多数场景两者相同**，你不必区分；当 AI 帮你 rebase 或你替别人 apply patch 时，才会分家。

**Commit message（提交信息）**：附在提交上的一段人类可读文本。第一行是标题，空一行后正文。
　常见混淆：**≠ 注释**。提交信息是**给未来的自己和团队写的说明书**，进历史后就是永久文档（除非重写历史）。第 6 章专门讲怎么写。

**Empty commit（空提交）**：一次不带任何文件改动的提交，用于打标记、触发 CI 等。用 `--allow-empty` 制造。
　常见混淆：**≠ 无用提交**。空提交在项链上仍占一格，是正当的"仪式性节点"。

## 三、分支与引用（对应第 3 章）

**Branch（分支）**：一张可以移动的书签，指向某个提交。物理上只是 `.git/refs/heads/<name>` 里一行 40 字符的哈希。
　常见混淆：**≠ 副本 / ≠ 独立世界**。创建分支不复制任何提交；删除分支不会删提交；分支的全部代价就是那一行文本。

**Ref（引用）**：任何"名字 → 提交 SHA"的映射的通称。分支是 ref，tag 是 ref，remote-tracking 也是 ref。
　常见混淆：**分支是 ref 的一种**，不是反过来。所有 ref 存放在 `.git/refs/` 或打包进 `packed-refs`。

**HEAD**：一个特殊的引用，指向"你当前所在的位置"。通常指向一个分支（`ref: refs/heads/main`），间接指向该分支所指的提交。
　常见混淆：**HEAD 不是分支，是"你在哪"**。切分支时移动的是 HEAD，不是分支本身。

**Detached HEAD（游离头指针）**：HEAD 不指向任何分支，而是直接指向某个提交。此时新做的提交没有分支书签"拴住"。
　常见混淆：**游离 ≠ 危险**，但**游离 + 切走 + 没打分支 = 提交容易被 GC 回收**。第 3 / 10 章反复提醒。

**Fast-forward（快进）**：目标分支的提交是当前分支的直接后代时，合并只需把书签往前挪，不产生合并提交。
　常见混淆：**FF 不是 merge 的一种策略，是一种"不需要 merge"的情况**。加 `--no-ff` 才会强制生成合并提交。

**Tag（标签）**：给某个提交起的一个不动的名字。两种：轻量标签只是一个 ref；附注标签（annotated）是一个独立的 tag 对象，带作者/时间/消息，可签名。
　常见混淆：**tag ≠ branch**。tag 一旦打上就应视为**不动**——移动 tag 是团队约定层面的禁忌（虽然物理上能做到）。发布用**附注标签**，临时书签用**轻量标签**。

**Ref namespace（引用命名空间）**：`refs/heads/` 放本地分支，`refs/tags/` 放标签，`refs/remotes/<remote>/` 放远程跟踪分支。
　常见混淆：`refs/remotes/origin/main` 与 `main` 是**两个不同的 ref**，一个是"我最后一次 fetch 时 origin 上 main 的样子"，一个是"我本地的 main"。混淆这两个是初学者最常见的 rebase 事故起点。

**Symbolic ref（符号引用）**：一个指向另一个 ref 的 ref。HEAD 就是最典型的例子。
　常见混淆：与"直接引用"（存 SHA）相对；detached HEAD 状态下的 HEAD 就是从符号引用退化成了直接引用。

## 四、远程（对应第 4 章）

**Remote（远程）**：本地仓库配置里的一个别名，指向另一份仓库的地址（URL）。默认名 `origin`。
　常见混淆：**远程 ≠ GitHub**。GitHub / GitLab / 内网 Git 服务器都只是"托管远程"的地方；一个仓库可以配 N 个 remote。

**origin**：新克隆的仓库自动配置的第一个 remote 的默认名字，仅是约定俗成，不是关键字。
　常见混淆：**origin 不特殊**。你可以改名、删掉、加多个。它只是"我克隆时的那个源"。

**upstream**：两个含义，看语境——(1) 分支的"上游跟踪目标"，即 `branch.<name>.remote` + `branch.<name>.merge`；(2) fork 场景下"我 fork 出来的那个原始仓库"的惯用 remote 名。
　常见混淆：**upstream 与 origin 不是同一层**。语境 (1) 是 ref 层，语境 (2) 是 remote 层。fork 场景下，你有两个 remote：`origin`（你自己 fork 的那份）和 `upstream`（原始仓库）。

**Remote-tracking branch（远程跟踪分支）**：形如 `origin/main` 的本地 ref，记录"我最后一次 fetch 时远程 main 的位置"。
　常见混淆：**它不是远程分支本身**，只是本地缓存。远程真正的 main 只在服务器上，你能看到的永远是"上次同步时的照片"。`git fetch` 就是刷新这张照片。

**Tracking / Upstream branch（上游跟踪分支）**：本地分支配置的"我默认与哪个远程分支通信"的对象。设置后，`git pull` / `git push` 才知道去哪里。
　常见混淆：**跟踪关系是配置**，不是自动发生。`git push -u origin feature` 里的 `-u` 就是在设这个。

**Fetch**：把远程的对象与 ref 拉到本地缓存，只更新 `origin/xxx`，**不动你当前分支**。
　常见混淆：**fetch ≠ pull**。fetch 是"拿数据回来看看"，pull 是"拿回来并立刻并进当前分支"。fetch 永远安全。

**Pull**：`fetch` + `merge`（或 `fetch` + `rebase`，看配置）。一步到位把远端改动合进当前分支。
　常见混淆：**pull 不是原子的**——真正发生的是两步，第二步在**你本地**跑合并，冲突也在本地产生。

**Push**：把本地对象和 ref 更新推到远程。默认拒绝非快进（non-fast-forward）的推送。
　常见混淆：**push 不是"上传文件"**，是"让远端某个 ref 移到我这个 SHA 上"。理解这点，force push 的危险就直观了。

**Force push（强制推送）**：加 `--force` 或 `-f`，允许非快进推送，覆盖远端 ref 的位置。
　常见混淆：**force 不删提交**，只是让 ref 挪走。别人本地可能还留着旧提交；但对共享分支来说，效果等价于"抹掉别人已同步的历史"。**共享分支上是黄线操作**（第 12 章）。

**Force-with-lease（带租约的强制推送）**：`--force-with-lease` 版本的 force push。只有"远端的现在还等于我上次 fetch 到的样子"时才推，否则拒绝。
　常见混淆：**比 --force 安全一档**，但**不是万能保险**——它只挡"别人推了新提交"这一种事故，挡不住协作层面的语义冲突。

**Fork**：托管平台层面的概念（GitHub/GitLab），把某个仓库复制成你账户下的另一个仓库。
　常见混淆：**fork 是平台功能，不是 Git 命令**。git 层面 fork 就是"再多一个远端仓库而已"。fork 之后你本地通常有两个 remote：`origin`（你的 fork）和 `upstream`（原始）。

**Pull Request / Merge Request（合并请求，PR / MR）**：托管平台上的一个协作对象——"请求把 A 分支的改动合到 B 分支"，附带评审、评论、CI 状态。
　常见混淆：**PR 不是 Git 概念**，是 GitHub 等平台在 Git 之上加的社交层。git 命令行里没有 `git pr`。

## 五、历史操作（对应第 5、9、10 章）

**Merge（合并）**：把两条历史线汇合成一条。多数情况下产生一个"合并提交"，父指针指向两边的顶端。
　常见混淆：**merge ≠ 覆盖**。merge 保留两边所有提交，只在冲突处需要你仲裁语义。

**Fast-forward merge（快进合并）**：见上文 Fast-forward。目标分支是当前分支的祖先时，merge 退化为"挪书签"。
　常见混淆：**看起来没合并的合并**。历史图上不会出现分叉，容易让人误以为"啥也没发生"。

**Rebase（变基）**：把一串提交"重新长在另一个基座上"。物理上是**复制**出一批新提交（新 SHA），然后把分支书签挪过去。
　常见混淆：**rebase 不是移动提交**，是重造。旧提交在 reflog 里还在，SHA 已经不一样了。**已推送的历史别 rebase**（黄→红线）。

**Interactive rebase（交互式变基，`rebase -i`）**：rebase 的交互模式，能对每个提交做 pick / reword / squash / fixup / drop / edit。
　常见混淆：**这是"重整项链"的主力工具**，也是第 5 章的核心。它做的仍然是"复制"，不是"编辑原提交"。

**Squash（压缩）**：把多个提交合并成一个的操作，通常在 rebase 或 merge 时使用。
　常见混淆：**squash 不是删除**——被压缩的提交内容一个不少地进入新提交，只是历史上少了几颗珠子。

**Fixup**：`rebase -i` 里的一种 squash 变体，把当前提交压进前一个提交，**丢弃当前提交的消息**。
　常见混淆：与 squash 的唯一差别就是提交信息处理方式。

**Revert（反向提交）**：**生成一个新提交**，其内容是抵消目标提交的改动。历史上加珠子，不减珠子。
　常见混淆：**revert ≠ reset**。revert 是"公开撤销"，safe for shared branches；reset 是"私下重挂书签"，仅适合未推送历史。

**Reset（重置）**：把当前分支的书签挪到指定提交。三种模式：
- `--soft`：只挪分支书签，工作区和暂存区不变；
- `--mixed`（默认）：挪书签 + 清空暂存区；
- `--hard`：挪书签 + 清空暂存区 + **强制覆盖工作区**（危险）。
　常见混淆：三态最容易混。记忆法：**从 soft 到 hard，破坏面从"只动书签"扩到"连你没保存的改动都吃掉"**。`--hard` 是全书黄线操作的代表。

**Cherry-pick（挑拣）**：把某个提交（的改动）"抄"到当前分支上，生成一个新的提交（新 SHA）。
　常见混淆：**cherry-pick 不移动原提交**，是复制一份放到别处。适合"我只想要那一个改动"。

**Bisect（二分定位）**：`git bisect` 用二分法在历史里找出"哪次提交引入了 bug"。你标好一个 good、一个 bad，Git 帮你切中间，反复几次收敛。
　常见混淆：**bisect 不修 bug，只定位**。收尾一定要 `git bisect reset`，否则 HEAD 会留在游离状态。

**Reflog（引用日志）**：`.git/logs/` 里的本地日志，记录每个 ref（尤其是 HEAD）在过去 90 天里的每次移动。
　常见混淆：**reflog 只在本地存在**，克隆不会带上。它是**几乎一切"我误操作了"的救命索引**（第 10 章）。默认保留 30–90 天。

**Stash（暂存栈）**：一个把"当前未提交改动"打包塞进 stash 栈的机制，用完可 `pop` / `apply` 回来。
　常见混淆：**stash 不是暂存区**。stash 是"临时藏"，暂存区（staging area）是"打包待提交"。同名不同物。

**Amend（修补提交）**：`git commit --amend` 把新改动并进上一次提交（或改上一次的消息），实际上生成了一个新的提交、替换掉了旧的。
　常见混淆：**amend 不修改旧提交**，是"用新提交替换书签指向"。因此已推送的提交做 amend 也算历史重写。

## 六、场景与策略（对应第 6–11 章）

**Worktree（工作树）**：`git worktree add` 让**同一个仓库同时铺开多个工作区**，每个绑到不同分支。
　常见混淆：**worktree ≠ clone**。worktree 共享同一个 `.git/`（对象、reflog、配置都共用），只是工作区多铺了几张；比 clone 便宜、比切分支干净。

**Conflict（冲突）**：合并/rebase/cherry-pick 时，Git 在同一段代码上无法自动决定要哪边，把两边都写进文件、用 `<<<<<<<`/`=======`/`>>>>>>>` 标出，让你仲裁。
　常见混淆：**冲突不是 Git 的错**，是**你的团队在语义上真的分叉了**。Git 只是把无法自动裁决的部分抬到桌面上（第 9 章）。

**Three-way merge（三方合并）**：Git 合并时用的算法。找到两条分支的最近共同祖先（merge base），比较两边相对祖先的改动，逐段自动/人工融合。
　常见混淆：**三方 = 你的、他的、共同祖先**，不是"三个分支"。理解这一点，冲突标记里为什么会出现 `|||||||` 就顺理成章。

**Merge base（合并基点）**：两条分支的最近共同祖先提交，三方合并的锚点。
　常见混淆：**merge base 不是分叉点的时间**，是**祖先提交的 SHA**——rebase 之后同一个"逻辑分叉"可能有全新的 merge base。

**Trunk-Based Development（主干开发）**：所有人在一条主干上高频、短命地做小分支，很快合回主干，靠 feature flag 控制发布。
　常见混淆：**TBD ≠ 只有一个分支**。它有短命的 feature 分支，只是寿命以小时/天为单位，不长期存在。

**GitFlow**：Vincent Driessen 2010 年提出的分支模型，含 `main`/`develop`/`feature/*`/`release/*`/`hotfix/*` 多条长命分支。
　常见混淆：**GitFlow 是一种策略，不是 Git 内置功能**。它适合有稳定版本发布节奏的产品，不适合每天多次发布的 SaaS。近年作者本人也提醒它"不该被无脑照搬"。

**GitHub Flow**：单一 `main` + 短命 feature 分支 + PR + 持续部署的极简工作流。
　常见混淆：**≈ TBD 的托管平台版**。三者的选择判据在第 7 章。

**Feature branch（特性分支）**：为某一功能/修复短命存在的分支，完成后合回主干并删除。
　常见混淆：**是分支策略里的角色，不是 Git 内置概念**。技术上它只是一个普通分支。

**Long-lived branch（长命分支）**：存活周期以周/月计的分支（如 `develop`、`release/1.x`）。策略层面越少越好，越少 rebase / merge 成本越低。
　常见混淆：**长命 ≠ 稳定**。长命通常意味着"合并债"在累积。

**Branch protection（分支保护）**：托管平台的规则，禁止对某分支的 force push / 直接 push / 未过 CI 的合并等。
　常见混淆：**分支保护是平台层功能**，Git 本身不知道 `main` 特殊。是外部规则让 `main` 变特殊。

**Feature flag（功能开关）**：在代码里用配置开关控制某功能是否可见，配合 TBD 让"未完成代码"也能安全进主干。
　常见混淆：**feature flag 与 Git 无关**，是应用层机制。但它是让"主干开发"成立的关键前提。

**Code review（代码评审）**：合并前人工审读改动的过程，通常在 PR/MR 上进行。
　常见混淆：**review 是流程，不是 Git 功能**；但它是 PR 存在的根本理由。

**Git blame**：对一个文件逐行显示"最后一次改这一行的是哪次提交、谁改的"。
　常见混淆：**blame ≠ 甩锅**，是**代码考古**。第 11 章的核心工具。

**Git log**：查看提交历史。搭配 `--graph`、`--oneline`、`--author`、`-S` 等参数，是最灵活的历史查询工具。
　常见混淆：**log 不修改任何东西**，纯读。

**Merge strategy（合并策略）**：`ort`（Git 2.34+ 默认；更早的默认 `recursive` 已在新版移除）/`octopus`/`ours` 等。日常一般不需要指定。注意：**没有 `-s theirs` 这个策略**——"取对面那一份"是 `checkout --theirs` / `-X theirs` 这类选项，不是合并策略。
　常见混淆：**策略是算法层**，与"你要不要用 rebase 还是 merge"这种流程决定不是一个层次。

**Submodule / Subtree（子模块 / 子树）**：把另一个仓库嵌进本仓库的两种方式。submodule 只留一个"外部引用 SHA"，subtree 把外部代码合进历史。
　常见混淆：**submodule ≠ 目录**——它是仓库里对另一个仓库某次提交的引用；对新人是著名的"惊喜工厂"（第 13 章）。

## 七、AI 协作（对应第 0、12、14 章）

**AI 指令箱（AI Prompt Box）**：本书自创栏目名。每章末尾给出的、可直接对 AI 助手复制粘贴的自然语言指令模板集合。
　常见混淆：**指令箱不是命令**，是**说话方式**。它与具体 AI 工具（Claude Code、Cursor、Copilot、Aider、Windsurf……）无关。

**红黄绿分级（Red / Yellow / Green）**：本书对 AI 执行 Git 操作的安全分级，口径是"要不要人确认、要哪种确认"。
- **绿**：只读，或只造新对象不动既有引用（生成 message、写 diff 说明、整理 log、解释历史）——AI 可直接放行，无需人确认。
- **黄**：会动引用 / 工作区 / 远端，但出了事还有安全网兜底（reflog、备份分支）——AI 可提议，**你必须看懂并确认后才放行**。
- **红**：不可逆销毁、拆安全网、覆盖共享远端、涉及凭证 / 生产——须**流程级确认**（先备份、先吊销、先打招呼），**AI 不该动手**，由你亲手执行。
　常见混淆：**颜色不是命令属性，是场景属性**。`push --force` 到你个人的实验分支是黄——你点头就能执行；同一条命令到共享 main 是红——要先打招呼走流程。判断要看**这条命令这次落在谁头上**。

**陪练模式（Sparring mode）**：AI 只解释、只出题、只诊断，不动 Git。用于概念学习期。
　常见混淆：**陪练 ≠ 助手模式**。陪练下 AI 甚至不生成命令，只当苏格拉底式对话对手。第 0 章的示范模式。

**执行模式 / 副驾模式（Copilot mode）**：AI 允许提议并（在确认后）执行 Git 命令。全书从第 3 章起主要模式。
　常见混淆：**副驾不是自动驾驶**。任何黄色及以上操作都需要人确认；确认框是防线的物理形式（第 12 章）。

**执行后的世界（The world after the command）**：本书栏目名，一张三列表：**你说的话 → AI 执行的命令 → `.git/` 里真实发生的变化**。用于揭示"点确认"之后仓库真实的状态迁移。
　常见混淆：**不是命令说明**，是**因果透视**。它治的是 cargo-cult：让你每次都看到指令→命令→物理变化的完整链条。

**最小权限（Least privilege）**：给 AI 助手配置能力时，只授它完成当前任务必需的最小权限——读优先于写，本地优先于远端，个人分支优先于共享分支。
　常见混淆：**最小权限不是"少用 AI"**，是"AI 用的账号能干的事最少"。第 12 章的核心原则之一。

**Prompt injection（提示词注入）**：外部内容（网页、issue、文件）中夹带的伪装成指令的文本，欺骗 AI 越权操作。
　常见混淆：**这是攻击面，不是使用姿势**。AI 拿到不受信内容后不应直接执行其中的指令；第 12 章列为红线之一。

**Confirmation gate（确认关卡）**：AI 客户端在黄/红操作前展示的"这些命令即将执行，确认？"对话框。
　常见混淆：**确认框不是免责签字，是最后一道防线**。防线的前提是**你读得懂它给你看的命令**——否则就只是一道要点掉的关卡（第 0 章）。

**Vibe coding（凭感觉编码）**：只看结果不看过程地接受 AI 生成的代码/命令。SO 2025 指出 72.2% 专业开发者对此警惕。
　常见混淆：**vibe coding 是 cargo-cult 的 AI 时代升级版**——两者共享同一个病根：因果链条被跳过。

**MCP（Model Context Protocol）**：一种让 AI 助手安全对接外部工具/数据源的开放协议，也可用于给 AI 挂 Git 能力。
　常见混淆：**MCP 是协议层，不是产品**。第 13 章外延话题。

## 八、其他你会读到的词

**Origin/HEAD**：远端仓库的"默认分支"指针，克隆时同步下来。指向 `origin/main` 或 `origin/master`。
　常见混淆：**不是你的 HEAD**——是 origin 那边的 HEAD 的缓存映像。

**Ancestor / Descendant（祖先 / 后代）**：提交图上的拓扑关系，沿父指针能到达则为祖先。
　常见混淆：**基于父指针，不是时间**。rebase 会重排祖先关系。

**Diff / Patch**：diff 是两个 tree/commit 之间的差异；patch 是这个差异的文本序列化，可以用 `git apply` 打回去。
　常见混淆：**Git 内部不存 diff**，diff 是实时算出来给你看的。这一点是许多"为什么 rebase 会冲突"直觉误差的源头。

**Hunk（差异块）**：diff 中一段连续的改动。`git add -p` 就是让你逐 hunk 决定要不要暂存。
　常见混淆：**hunk 是差异的最小交互粒度**，不是"一行"。

**`.gitignore`**：项目里配置 Git 应忽略哪些路径（不进入 tracking）的文件。
　常见混淆：**ignore 只影响未跟踪文件**。已跟踪文件即使写进 `.gitignore` 也仍然会被跟踪，需要先 `rm --cached`。

**Hook（钩子）**：`.git/hooks/` 目录下的可执行脚本，在特定事件（pre-commit、pre-push、post-merge……）时被 Git 触发。
　常见混淆：**hooks 不随 clone 分发**（除非用 `core.hooksPath` 或 husky 之类工具管理）。第 13 章展开。

**Git LFS（Large File Storage）**：一个把大文件（媒体、二进制）替换为指针、真身另存的扩展。
　常见混淆：**LFS 是扩展，不是 Git 本体**。第 13 章外延。

**Monorepo（单体仓库）**：把多个项目放在同一个仓库里的组织策略。
　常见混淆：**Monorepo 与 Git 无关**，是策略；只是它对 Git 的规模挑战（大 checkout、稀疏克隆等）催生了一系列 Git 扩展。第 13 章外延。

**Signed commit / Signed tag（签名提交/签名标签）**：用 GPG / SSH / X.509 密钥对提交或标签签名，供他人验证身份。
　常见混淆：**签名不防篡改内容**（内容改了 SHA 就变了），**签名证明"这个 SHA 是我做的"**。第 12 章。

**Sparse checkout（稀疏检出）**：只把仓库的一部分路径铺开到工作区，其余隐藏，用于超大仓库。
　常见混淆：**未检出的路径不是"没了"**，历史里都在，只是工作区不铺开。

**Shallow clone（浅克隆）**：`git clone --depth N` 只拉最近 N 次提交的仓库，用于快速拉取或 CI。
　常见混淆：**浅克隆能力受限**——不能 push 到需要旧历史的场景，不能作为共享中心。

**Packfile（包文件）**：Git 定期把散落的对象压缩合并成 `.pack` 文件，减小磁盘占用、加快传输。
　常见混淆：**对象没消失**，只是从"松散对象"打包了。

**Garbage collection（GC）**：`git gc` 定期清理不可达对象、打包松散对象。
　常见混淆：**GC 有宽限期**——reflog 里还引用的对象不会被立即回收，这是 reflog 能救命的物理原因。

**Config（`.git/config` / `~/.gitconfig` / `--system`）**：三层配置，作用域依次是本仓库、当前用户、整个系统。
　常见混淆：**同一个键在不同层可能都有值**，作用时越近越优先。`git config --list --show-origin` 帮你看清楚。

## 九、如何用这份表

1. **概念卡壳时倒查**：读某章遇到英文术语，回来查一次比 Google 快。
2. **发指令前默念颜色**：AI 协作术语区（第七组）里的红黄绿，是发出每条 AI 指令前的反射动作。
3. **和 AI 对话时明用**：越是把这份表里的英文词直接用进你的自然语言指令（"把这三个 commit `squash` 成一个，保留 committer 信息，不动已 push 部分"），AI 越能精确翻译。这就是第 0 章说的 **API**。

术语不是背的，是**用出来的肌肉记忆**。查一次会一半，用三次就是你的了。
