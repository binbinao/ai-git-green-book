# 第 2 章　提交：不可变的快照

> 《Git 的概念地图》第 2 章 · 定调稿 v1.0
> 五张地图的第二张：档案馆里那一颗颗真正的\"资料\"。

---

## 2.1 场景引入：一次心惊的 amend

深夜十一点，你把最后一次编译跑过，`git commit -m "fix: 修复用户注册时邮箱大小写敏感的问题"`，回车。工作完成，准备关机。

关机前你决定看一眼 log，习惯性地。`git log --oneline -5`。

**问题来了。** 那条 message 你手滑打成了\"用户驻册\"。不是别的错，是你自己会脸红的那种低级错误。你叹了一口气，用了那条你已经用过无数次的命令：

```
git commit --amend -m "fix: 修复用户注册时邮箱大小写敏感的问题"
```

回车。log 里那行\"驻册\"变成了\"注册\"。世界重回宁静。

**请诚实地回答一个问题：** 你刚才那条 `--amend`，到底做了什么？

如果你的第一反应是\"改了一下 message\"——那么你和大多数 Git 用户站在同一个坑里。这一章要做的第一件事，就是把这个坑填平：**你没有\"改\"任何东西。你造了一颗新珠子，把 main 标签从旧珠子上摘下来，挂到了新珠子上。旧的那颗\"驻册\"珠子还在你的 objects 目录里安眠。**

这不是文字游戏。这是 Git 世界最基本的物理定律：**提交是不可变的。** 一旦造出来，它就永远待在那里；你能做的只是造新的，然后把标签挪走，让旧的从视线里消失。

看懂这个定律，你会理解为什么 revert、cherry-pick、bisect、reflog、rebase 全都长成现在这个样子——**它们不是在\"改历史\",它们是在\"造新珠子 + 挪标签\"**。 而这一整套物理，都建立在同一个原语上：**一次不可变的全量快照**。

## 2.2 祛魅时刻：一颗珠子里装着什么

先给结论。

> **一次 commit，是一个不可变的三元组：项目状态的全量快照 + 一个或多个 parent 指针 + 一段元信息（作者、时间、message）。用一个 SHA 哈希作为它的身份证号，全世界唯一。**

关键词三个：

- **全量快照**：不是 diff，不是增量。是**整个项目**在那一刻的完整状态。
- **parent 指针**：链回上一颗珠子（合并 commit 会有两个 parent，链回两颗）。这就是历史\"串起来\"的方式。
- **不可变**：造出来就永远不变。改一个字节，SHA 就变，就是另一颗珠子了。

一颗一颗地讲。

### 全量快照——不是 diff，是完整存档

这是全书最反直觉的一条，也是最多人搞错的一条：**Git 的 commit 里，存的是那一刻整个项目所有文件的完整状态。**

不是\"和上一次相比改了什么\"。

不是\"这次多加了 3 行 A.py、少了 1 行 B.py\"。

是\"A.py 完整的这一版、B.py 完整的这一版、C.py 完整的这一版、README 完整的这一版……一直到项目里最后一个文件的完整的这一版\"。全部打包。

你可能会立刻质疑：\"那不是特别浪费磁盘吗？我改一个字符就要存整个项目一遍？\"

**Git 并不浪费——但它\"节省\"的方式与你想的不同。** 关键在于第 1 章讲过的\"内容寻址\"：

- 项目里有 3000 个文件，你这次只改了 1 个。
- 那 1 个改过的文件——Git 存一份新的 blob 对象（因为内容变了，哈希变了）。
- 那 2999 个没动的文件——Git 直接复用它们**上次已经存过的 blob 对象**（内容没变，哈希没变）。
- 目录树（tree 对象）也是这样：每个目录记录\"它包含哪些文件的哈希、哪些子目录的哈希\"，只有内容变了的目录会生成新的 tree。

结果就是：**逻辑上是全量快照，物理上按内容去重。** 从语义看每次 commit 都是完整的存档，随便挑一次都能独立还原整个项目；从磁盘占用看每次只增加了改动的那点字节。**两全其美。**

那你可能还会追问：\"那为什么 `git log -p`、`git diff` 每次都能显示 diff？\" 因为 diff 是**展示时算出来的**——Git 拿这次的完整快照和上一次的完整快照相减，把结果显示给你。**diff 不是 Git 存的东西，是 Git 现算给你看的东西。** 这个反转很多人第一次听会怔一下——他们以为 diff 是本体，而 snapshot 才是本体。

**为什么这个反转如此重要？** 因为一旦你接受\"每次 commit 都是完整独立的存档\",很多后续操作立刻不再神秘：

- `cherry-pick <sha>` 能把某颗珠子\"复制\"到另一条项链上——**因为那颗珠子里有完整信息，独立可用。**
- `git bisect` 能在两个 commit 之间做二分查找——**因为你可以直接把任何一颗珠子的快照铺开、跑测试，不需要\"重放\"什么。**
- `git checkout <老 sha> -- 某个文件` 能只从某次快照里取出一个文件——**因为那个快照本身就是完整的，取哪个都行。**
- `git show <sha>` 能显示某次提交的完整内容——**因为它就在那儿，不需要从头累加。**

如果 commit 存的是 diff（就像某些老系统那样），上面每一条都会痛苦得多——要么每次都要从初始版本一路 replay 到目标，要么要维护复杂的 delta 链。**Git 选了朴素但强大的一条路：每一颗珠子都是完整的\"当时的样子\"。**

### parent 指针——历史怎么串起来

一颗珠子里除了快照，还有一个或多个指向上一颗珠子的指针，叫 parent。

- **常规 commit**：1 个 parent，指向上一次提交。这是绝大多数情况。
- **首个 commit**（`git init` 后的第一次）：0 个 parent。这是历史的起点。
- **合并 commit**（merge 产生的）：2 个 parent，各指向被合并的两条历史的末端。这是历史的合流点。

这些 parent 指针串起来，就是你在 `git log --graph` 里看到的那张图——**Git 术语叫 DAG（有向无环图）**。有向，是因为每条边只从子指向父，永不反向；无环，是因为你不可能造出\"祖先里包含自己\"的珠子（内容一变，SHA 就变，逻辑上根本无法自我包含）。

用第 3 章的比喻：**每颗珠子的 parent 指针，就是把这颗珠子和上一颗珠子串起来的那截线。整条项链就是靠这些线维系起来的。分支只是挂在某颗珠子环上的标签；标签换了、摘了、加了都没关系，珠子之间的线永远在那儿。**

一个直接推论：**历史是从\"当前\"往\"过去\"读的。** 每颗珠子知道自己的爹是谁；但一颗珠子不知道自己有几个儿子。这就是为什么 Git 里从新到旧走很容易（跟着 parent 指针），从旧到新走要靠外挂（reflog、branch 列表、tag 列表——都是\"外部索引\"帮你反查）。

### SHA——一颗珠子的身份证

每颗珠子有一个 40 位十六进制的名字，是它内容的 SHA-1 哈希（新版本可选 SHA-256，同理）。

哪些内容参与哈希计算？**几乎所有你能感觉到的东西**：

- 快照的哈希（也就是 tree 对象的哈希）
- parent 的哈希
- 作者名、作者邮箱、作者时间戳
- 提交者名、提交者邮箱、提交时间戳
- commit message

这些拼在一起，算 SHA-1，得到珠子的 SHA。

**这带来一个至关重要的推论：改动任何一样，SHA 都变。**

- 改一个字节代码 → tree 变 → commit SHA 变。
- 改 message 一个字符 → commit SHA 变。
- 改 parent（rebase 的本质）→ commit SHA 变。
- 甚至 commit 时间戳精确到秒的差异 → commit SHA 变。

所以\"改 message\"这件事在 Git 世界里根本不存在——**你只能造一颗新珠子**，它拥有你想要的新 message，然后把当前分支的标签指过去。旧珠子还在，但没人指着它了（除了 reflog 还记得）。这就是 `git commit --amend` 的真相。

再回到开篇那个\"驻册\"的场景。你 amend 之后：

- 那颗 message 里写着\"驻册\"的旧珠子：**还在** `.git/objects/` 里，SHA 不变。
- 一颗 message 里写着\"注册\"的新珠子：**刚刚被造出来**，有一个全新的 SHA。
- 你所在分支的标签：**从旧珠子上摘下，挂到了新珠子上**。
- `reflog`：**记住了**这次 HEAD 从旧珠子挪到新珠子的动作，30 天内你还能翻回去。

**没有任何一颗珠子被\"改\"。 只是标签挪了，视线跟着挪了。你以为的\"改\"，是标签移位造成的错觉。**

## 2.3 三个直接推论

**推论一：cherry-pick、revert、bisect 全都以\"某一颗珠子\"为操作对象。**
因为珠子是完整独立的存档，它随时可以被搬到别处（cherry-pick 复制到当前项链末端）、被反着做一遍（revert 造一颗\"抵消\"珠子）、被跑起来验证功能是否正常（bisect 铺开跑测试）。**这些命令的力量，全都建立在 commit 是完整快照这个前提上。** 如果 commit 是增量，你连\"独立跑一颗珠子\"这件事都做不到。

**推论二：\"丢弃\"一颗珠子的意思是\"没有标签指着它了\",不是\"消失了\"。**
`git reset --hard HEAD^` 把分支标签往回挪一格——但那颗被跳过的珠子还在 objects 里，reflog 也记得它。默认情况下 Git 会保留这颗珠子 30 天以上（`gc.reflogExpire` 默认 90 天，实际由 reflog 和 gc 配合决定），你随时可以找回来。**丢珠子非常难。**（正因为难，第 5 章会告诉你 reflog 是你的隐形保险丝。）

**推论三：SHA 是团队沟通的最小单位。**
一颗珠子的 SHA 是全球唯一的。你说\"看一下 a1b2c3d\",全世界任何一个 clone 了这个仓库的人，都能精确定位到同一颗珠子——不受分支名影响、不受标签影响、不受时区影响。**这是分布式系统里\"共同指称\"的黄金标准**。日常沟通里前 7 位一般就够用（Git 会自动帮你缩到不冲突的最短长度），除非仓库真的巨大到有前缀冲突。

## 2.4 三区模型：为什么 Git 要在你和仓库之间塞一层

现在来面对第 0 章自测题第 4 题的答案——**三区模型**。这是 Git 命令表里让新手最困惑的一层，也是 Git 提供给你的\"提交塑形工具\"。

从工作目录到仓库，Git 中间塞了一个叫\"暂存区\"（staging area，也叫 index、cache）的东西。三层长这样：

```
   ┌────────────────────┐     ┌────────────────────┐     ┌────────────────────┐
   │   工作目录          │     │   暂存区            │     │   仓库              │
   │  (working dir)     │     │  (staging area)    │     │  (.git/objects/)   │
   │                    │     │                    │     │                    │
   │  你实际编辑的文件    │ add │  下一次 commit      │commit│  已提交的历史       │
   │  A.py (改了)       │────▶│  会包含哪些内容      │─────▶│  一颗颗珠子的档案库  │
   │  B.py (新增)       │     │  的一个\"入库单\"     │     │                    │
   │  C.py (没动)       │     │                    │     │                    │
   └────────────────────┘     └────────────────────┘     └────────────────────┘

               ◀────── checkout / restore ──────
               (从仓库里读出某个版本到工作目录/暂存区)
```

*图 2-1：三区模型。add 是\"搬上入库台\",commit 是\"入库\"。*

**为什么要有这层暂存区？** 一句话：**为了让你能在\"提交\"这个动作前，精确塑造\"这次要提交什么\"。**

具体来说，暂存区回答了一个问题：\"我现在工作目录里有一堆变化——A.py 改了 3 处、B.py 新增了、C.py 被我删了、还有 5 个我暂时不想 commit 的杂七杂八——**这一次 commit 里，我想让哪些进去？**\"

SVN、Mercurial 这类工具没有这一层：改了什么就 commit 什么，粒度是\"整个工作区\"。Git 多加了一层\"入库单\",你可以：

- **只提交部分文件**：`git add A.py`（只加 A，B 和 C 的改动这次不进历史）。
- **只提交某个文件里的一部分改动**：`git add -p A.py`（在 A.py 的 10 处改动里，只挑其中 3 处放上入库单）。
- **修完 bug 顺手改了个 typo，想拆成两个 commit**：分两次 add + commit 就行。
- **临时把一个不小心 add 上去的文件从下次 commit 里撤下来**：`git restore --staged <file>`。

这套机制让你能造出\"干净的、逻辑内聚的 commit\"——每颗珠子只装一件事，历史读起来就是清晰的故事。**这是原子提交观（第 6 章会展开）的物质基础。**

**代价是**：你需要理解一件文件此刻可能同时存在于三个层里的\"三份不同状态\"：

```
     工作目录版本         暂存区版本            仓库版本（HEAD）
        A.py               A.py                  A.py
       （改到 v3）         （add 时是 v2）        （上次 commit 是 v1）
```

`git status` 就是在告诉你这三份的相对关系：

- **\"Changes to be committed\"**：暂存区版本 ≠ 仓库版本（有东西已经上了入库台）
- **\"Changes not staged for commit\"**：工作目录版本 ≠ 暂存区版本（工作目录里还有没上台的改动）
- **\"Untracked files\"**：Git 完全不认识的新文件（连暂存区都不知道它存在）

新手常见的\"我明明改了怎么 commit 上去还是老版本\"的谜团，几乎都是因为**改了工作目录之后忘记再 `add` 一遍**——暂存区里还是上一次 add 时的旧版本，commit 出去的自然还是旧版本。

### add 的三种典型用法

- `git add <file>`：把文件当前的完整内容放上入库台（如果已经在台上、内容变了，就更新）。
- `git add .`：把当前目录下所有改动全部搬上台。**方便，但要小心**——它不区分\"你想提交的\"和\"你不小心动了的\"。commit 前用 `git status` 或 `git diff --staged` 检查一下。
- `git add -p`：**逐块交互式添加**。Git 会把你的改动切成一小块一小块（hunk），一块一块问你要不要 add。这是造精致 commit 的利器；AI 时代它的意义在下降（你可以直接说人话让 AI 帮你拆），但概念上你要知道它存在。

### commit 的两种典型用法

- `git commit`：把**暂存区**当前的状态打包成一颗新珠子，parent 是当前 HEAD 指向的那颗，标签自动前移。**注意主角是暂存区**——不是工作目录。工作目录里还没 add 的改动**不会**进这个 commit。
- `git commit -a`：一个便利参数——先自动把所有**已跟踪文件**的改动 add 一遍，再 commit。等于 `add -u` + `commit`。**新增文件不会自动进来**（Git 不知道它算不算你想跟踪的东西），这是 `-a` 的一个常见坑点。

## 2.5 commit message：团队最便宜的通信协议

一颗珠子除了快照和 parent，还带一段元信息，其中最重要的是 **commit message**——你留给未来（未来的你、未来的同事、未来读 git blame 的运维、未来做 code archaeology 的实习生）的一句话。

**它的地位比大多数人想的重要得多。** commit message 是这样一样东西：

- **异步、可搜索、永不过期**：它跟着 commit 走，只要仓库还在，它就还在。你不用担心 message 会随着 Slack 消息滚走、随着 Jira 单归档、随着邮箱清理消失。
- **一对多**：写一次，未来任何人读到这行代码都能看到。
- **零边际成本**：写好写坏都是几十秒的事，但读者省下的可能是几小时的\"这行代码是干嘛的\"的追溯。

一条好的 commit message 通常长这样：

```
fix(auth): 修复邮箱大小写敏感导致的登录失败

用户注册时保存的邮箱保留了原大小写，但登录时按大小写敏感
匹配，导致 \"User@Example.com\" 注册后用 \"user@example.com\"
无法登录。

修改点：在保存前 lowercase 邮箱字段，同时给已有用户
补一个数据迁移。

Fixes #1234
```

包含四层信息：

1. **第一行摘要**（50 字以内，动词开头，说清\"这次提交做了什么\"）
2. **空行**
3. **正文**（可选，说\"为什么这么做\",不是\"怎么做\"——怎么做 diff 里已经写了）
4. **引用**（可选，链到 issue/PR/文档）

第一行的固定格式 `<type>(<scope>): <subject>` 是 **Conventional Commits** 约定（第 6 章会展开），它让 message 变成可机器解析的——能自动生成 changelog、能触发 CI、能按 type 过滤 log。

**AI 时代最好用的辅助之一**就是让 AI 从 diff 生成初稿 message。它读 diff 比你快，能一眼看出\"这次改的语义是什么\"。你要做的是**审、改、发出**——把 AI 写的\"看起来对但没说到点子上\"的 message 修成\"说到点子上\"的 message。这是第 6 章的核心话题。**这里你要记住的一件事是**：commit message 不是仪式，是资产。**别浪费你在别人未来时间上的这次杠杆。**

## 2.6 场景判断：什么时候造一颗新珠子

**规则一：一颗珠子装一件事。**
判断标准：**这颗珠子的 message 能不能用一句话讲清\"做了什么\"？** 讲不清就说明你把两件事混塞进一颗珠子了，拆开。原子提交对未来的\"回溯定位 bug\"（bisect）、\"局部撤销\"（revert）、\"评审\"（PR）都是决定性优势。

**规则二：能通过测试的珠子才配上项链。**
每一颗 commit 都是可能被 checkout 出来单独跑的（bisect 就是干这个的）。所以\"半成品\"（编译不过的、测试不过的）尽量不要留在共享分支上。**在你自己的开发分支里造半成品是可以的**（甚至是推荐的——commit 是廉价的存档手段），但在合入 main 之前，最好把这批\"半成品珠子\"整理成\"每颗都能独立跑\"的干净序列（第 5 章的 rebase 会帮你做这件事）。

**规则三：写清 message 再回车。**
`git commit -m "fix"`、`git commit -m "更新"`、`git commit -m "wip"`——这些 message 是**通信协议里的空包**，占了字节但没送信息。给未来的你和你的同事一点尊重：多花 30 秒，说清\"改了什么、为什么改\"。

**反规则一：不要为了整齐把\"半个改动\"分次 commit。**
比如\"新增一个函数\"和\"调用这个函数\"如果一起才有意义，不要拆成两颗珠子——把它们塞进同一颗珠子里，历史更好读，revert 更好做。原子的意思是\"完整的一件事\",不是\"最小的粒度\"。

## 2.7 关于\"不可变\"和\"可塑历史\"如何共存的伏笔

到这里你可能会有一个合理的困惑：既然珠子是不可变的，那第 5 章要讲的\"历史是可塑的\"是怎么回事？我 rebase、squash、reword，明明能把历史改得面目全非啊？

答案在这里，先埋着，第 5 章展开：

> **珠子本身不可变——你造出来的珠子，SHA 永远是那个 SHA，内容永远是那个内容。但一条项链是由\"分支标签指向哪颗珠子\"决定的——你可以造一批新珠子（内容与旧珠子相同或近似）、把标签指过去，让 log 上呈现的\"历史\"完全变个样。**
>
> **换句话说：珠子是不可变的建筑材料，项链是可塑的编织。你不能改一颗珠子，但你可以造新珠子重新串。**

`git rebase` 的本质就是这个操作：**把某一段项链复制一遍，用新的 parent 关系连接起来**——每颗珠子都被造成了一颗新的珠子（内容一样但 parent 变了，所以 SHA 全变），旧珠子还在（reflog 记得）。表面看历史被\"改\"了，里子看，是造了一批新珠子。

**这是第 5 章的钥匙。** 你现在不用完全理解，只要记住：\"不可变\"和\"历史重写\"不是矛盾的两件事——一个说的是\"每颗珠子\",一个说的是\"整条项链\"。造新珠子的成本几乎为零，所以\"重写历史\"在 Git 里是一种廉价、安全（对你自己而言）、且频繁使用的能力。

## 2.8 AI 指令箱 · 提交

以下指令模板与工具无关。**颜色标注**：本章大多是绿色（造提交、看提交、写 message），涉及 `--amend`、`reset` 的转黄（因为它们会挪标签、让别的珠子从视线里消失）。

**🟢 造提交类（低风险，正常操作）**

- 「我现在改了 5 个文件。看一下每个文件的变化，判断哪些属于'新功能'、哪些属于'顺手修 bug'、哪些属于'重构清理'。分成 2-3 个逻辑上独立的 commit 分别提交，每个 commit 给我起一个符合 Conventional Commits 格式的 message。执行前先把分组方案给我确认。」
- 「从当前暂存区的 diff 生成一条 commit message，遵循这个仓库的历史风格（先扫一下最近 20 条 commit）。生成 3 个候选让我挑，我挑完你再 commit。」
- 「我要提交一个 WIP 存档，message 里说清楚\"这是半成品、还没跑测试\",然后带上当前 TODO 列表。这个 commit 只是我本地档案，不会推。」

**🟢 查看类（只读，随便用）**

- 「给我看看当前分支最近 10 个 commit——每个的 SHA 前 7 位、第一行 message、作者、时间。表格。」
- 「显示 SHA `a1b2c3d` 这颗 commit 的完整信息：作者、时间、parent、改动的文件列表、每个文件的 diff。用中文帮我用一句话总结'这次提交做了什么、为什么'。」
- 「找出仓库历史里所有 message 写得含糊的 commit（比如只写\"fix\"、\"update\"、\"wip\"）。列前 20 个，按时间排序。」

**🟡 需要盯着的（会挪标签或让珠子失联）**

- 「我刚 commit 的这条 message 打错字了。用 `--amend` 帮我改成'<正确文本>'。执行前告诉我：这个操作会造一颗新珠子，旧珠子进 reflog；如果这条 commit 已经推过，会有什么后果。」
- 「把当前分支最新 3 个 commit 撤回到暂存区、保留改动。用 `git reset --soft HEAD~3`。执行前明确：这只挪标签、不丢改动，reflog 里旧位置还在。」
- 「我不小心 add 了一个不该 commit 的大文件到暂存区（我还没 commit）。帮我把它从暂存区撤下来，工作目录里保留。」

**训练用指令（陪练模式）**

- 「假装我是一个只用过\"改文件→保存→交给团队\"的开发者，从没接触过暂存区概念。给我出 6 道题：'为什么改了文件 commit 上去还是老版本''add 和 commit 的区别''为什么 `git commit -a` 有时候不管用'等等。一次问一个，根据我的回答决定下一题。」
- 「用'档案馆入库单'的比喻，向一个纠结'为什么 Git 要多一个暂存区'的新手解释：三区模型的价值是什么。300 字以内。」
- 「给我 5 个真实的 diff 片段（你随便造，涵盖新功能、bugfix、重构、文档、依赖升级）。让我练习给每个写 commit message，我写完你按 Conventional Commits 标准打分并给建议。」

## 2.9 执行后的世界

| 你说的话 | AI 大概率执行 | `.git/` 里的真实变化 |
|---|---|---|
| \"帮我把这些改动分成 2 个 commit 提交\" | `git add ...` × 2 + `git commit` × 2 | `objects/` 里新增 **2 颗 commit 对象** + 相应的 tree 和 blob；`refs/heads/<current>` 前移 2 格；reflog 加 2 条记录 |
| \"改一下刚才 commit 的 message\" | `git commit --amend -m "..."` | `objects/` 里**新增一颗 commit 对象**（新 SHA）；`refs/heads/<current>` 从旧 SHA 挪到新 SHA；**旧 commit 还在 objects 里**，reflog 记得它 |
| \"撤回最近 3 个 commit 但保留改动\" | `git reset --soft HEAD~3` | `refs/heads/<current>` 往回挪 3 格；被跳过的 3 颗 commit **对象还在**；index 保持不变；reflog 记录这次跳跃 |
| \"看看 abc123 这颗 commit\" | `git show abc123` | **零变化**（纯读） |
| \"把 abc123 复制到当前分支末端\" | `git cherry-pick abc123` | `objects/` 里**新增一颗 commit 对象**（新 SHA，内容近似 abc123 但 parent 变了）；`refs/heads/<current>` 前移 1 格 |

看懂这张表你会记住一件事：**\"改\" commit、\"撤销\" commit、\"复制\" commit——本质都是\"造新 commit + 挪标签\"。 从来没有一颗已经存在的 commit 被真正修改过。**

## 2.10 命令侧栏

```
git add <file>            # 把文件当前内容放上入库台
git add -p                # 逐块交互式添加（造精致 commit 用）
git add .                 # 把所有改动一股脑放上台（小心）
git restore --staged <f>  # 从入库台上撤下来（工作目录改动保留）
git status                # 三层之间的差异报告
git diff                  # 工作目录 vs 暂存区
git diff --staged         # 暂存区 vs 上次 commit
git commit                # 把暂存区状态打包成一颗新珠子
git commit -a             # 已跟踪文件的改动自动 add + commit（新增文件不管）
git commit --amend        # 造一颗新珠子替换掉刚才那颗（旧的进 reflog）
git show <sha>            # 显示某颗珠子的完整信息 + diff
git log --oneline         # 一行一颗珠子的浏览
git log -p <file>         # 追某个文件的完整改动史
git cherry-pick <sha>     # 复制某颗珠子到当前项链末端
git revert <sha>          # 造一颗\"抵消\"珠子挂到项链末端
```

## 2.11 本章小地图

```
提交 = 一个不可变的三元组
  │
  ├─ 全量快照（不是 diff！物理上按内容去重，逻辑上每次都完整）
  ├─ parent 指针（1 个 = 常规、2 个 = merge、0 个 = 首个）
  └─ 元信息 + SHA 身份证（改任何一点，SHA 就变，就是新珠子了）

三区模型 = Git 塞在你和仓库之间的\"提交塑形工具\"
  │
  ├─ 工作目录  你实际编辑的文件
  ├─ 暂存区    下次 commit 会包含什么的\"入库单\"
  └─ 仓库      已入库的历史珠子
  
  add   = 搬上入库台
  commit = 入库（把暂存区打包成一颗珠子）

关键推论：
  1) cherry-pick/revert/bisect 都以\"一颗珠子\"为原子对象
  2) 丢弃的珠子 ≠ 消失（reflog 里都在）
  3) SHA 是团队沟通的最小单位
  4) \"改\" commit 都是\"造新+挪标签\"——珠子从不被修改
```

## 2.12 三大典型误解拆解

**误解一：\"Commit 存的是 diff。\"**
最流行的错。它源自 SVN、CVS 那些老工具的心智模型——那些系统里 commit 确实存 delta。Git 反其道而行之：**每次 commit 存全量快照，diff 是展示时算出来的**。这个反直觉的决定换来了整个 Git 命令表的自洽——cherry-pick 可以独立、bisect 可以跳跃、任意 commit 可以 checkout 独立跑测试。如果你还带着\"存 diff\"的直觉，你会发现 Git 的很多行为莫名其妙；一旦切换到\"存全量快照 + 内容去重\"的视角，一切自然。**不是所有你以为的常识，都是常识——SVN 教你的东西 Git 里得反着来。**

**误解二：\"我用 --amend 把 commit 改了。\"**
你没有改任何东西。你**造了一颗新珠子**（新的 SHA），把当前分支的标签从旧珠子上摘下、挂到新珠子上。旧珠子还在 `.git/objects/` 里安眠，reflog 记得它，30 天内你可以随时找回。**这不是文字游戏——它有实际后果**：如果你 amend 的那颗 commit **已经推送到共享分支了**，`--amend` 就是在偷偷制造分叉——你本地的新珠子和远端的旧珠子是两颗不同的 commit，SHA 不同、historical identity 不同。下次 push 会被拒（non-fast-forward），你可能会本能地去 `--force`——然后就把已经拉过这颗珠子的同事们坑了。**\"珠子不可变\"这条物理定律不是给理论家看的，它是给你划红线的：已推送的珠子上，不要 amend。**（第 5 章会展开这条黄金规则。）

**误解三：\"我 `reset --hard` 之后，那些 commit 就没了。\"**
没有。reset 挪的是分支标签——把你所在分支的标签往回挪几格。被跳过的那几颗珠子还在 objects 里，reflog 也记得它们（记的是\"HEAD 曾经指到哪儿\"）。**默认配置下你有大约 30 到 90 天的宽限期**，用 `git reflog` 找到那些旧 SHA，`git reset --hard <sha>` 或 `git branch rescue <sha>` 就能救回。真正的数据丢失要三样同时发生：**（1）没有任何标签指着这颗珠子；（2）reflog 也忘了它（过期）；（3）`git gc` 运行了，把无引用的对象扫走。** 三件事同时发生的概率对普通用户接近于零。所以：**\"完了完了 reset 把东西删了\"是 Git 世界里最常见但最不必要的恐慌之一**——你的珠子几乎永远救得回。
