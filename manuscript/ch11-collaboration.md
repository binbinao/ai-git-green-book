# 第 11 章　团队协作：从推送权到代码考古

> 《Git 的概念地图》第 11 章 · 场景章 · v1.0
> 场景决策部分的最后一章。第 10 章教你在事故里活下来，本章讲**为什么大多数事故根本不该发生**——它们在\"团队协作\"这一层就该被结构性预防。
> 结构：症状 → 候选 → 判断 → 指令。三段式。

---

## 11.1 场景引入：五点四十分，那个绿色的 Merge 按钮

周四下午五点四十分。你刚写完一个功能——用户资料页的重构——`git push` 完毕，切到浏览器，GitHub 上你的分支旁边冒出一个熟悉的黄色横条：

> Compare & pull request

你点它。跳到 PR 创建页。标题栏里 GitHub 已经根据你的分支名自动填了 `feature/user-profile-refactor`。下面是一个空的描述框，占位符写着 `Leave a comment`。

你盯着这个空框，看了 6 秒。

在这 6 秒里，你的手指开始条件反射地打字：

> \"重构用户资料页。\"

然后你补了一句：

> \"如题。\"

然后你按了 `Create pull request`。绿色按钮出现——`Merge pull request`。你考虑了 0.5 秒——反正是自己的分支、CI 也绿了——**你按了 Merge**。回到工作区，切回 main，`git pull`，走了。

第二天早上十点，团队周会。技术负责人翻你昨晚的 PR：\"这个 refactor 具体动了什么？\"你张嘴——**卡住了**。你想说\"就是重构了一下\"，但对面盯着你等一个具体答案。你打开 GitHub，PR 描述框里躺着两个字：\"如题。\"下面的 diff 里有 800 行改动，横跨 12 个文件。你开始逐个 diff 讲，讲了 8 分钟。

**周会结束你会意识到几件事**——PR 描述框那 6 秒犹豫里，你**本来可以**花 3 分钟写清楚这次改动的动机、范围、风险、要审查什么；你没写，是因为你把 PR 当成了\"把代码推上去\"的**流程手续**，而不是**通信协议的一部分**。

同样的犹豫，还会出现在这些时刻：

- 打开一个别人的 PR 准备 review 时——\"我该看什么？逐行看 diff？看到了合理的就点个赞？\"
- 看到 `git blame` 显示某行是你三个月前写的、而你**完全不记得为什么这么写**时——\"当时的我是不是傻？\"
- 团队里有人 `git push --force` 把共享分支覆盖掉，群里一片惨叫时——\"这条命令在我这里为什么就没那么危险？\"
- 你要向一个新加入的实习生解释\"我们为什么用 fork 不用 shared repo\"、\"为什么 main 要开分支保护\"、\"为什么直接 push main 会被拒\"时——**你能用一句话讲清楚吗？**

这一章要摊开的地图，核心是一句反直觉的话：

> **团队协作不是\"把代码推上去\"，是\"让别人看懂你项链上的这一段变化\"。PR、评审、blame、分支保护——它们不是流程形式主义，是通信协议的延伸。**

读完这一章你会发现：那个空着的 PR 描述框，不是\"没什么可写\"，是\"你还没决定让别人怎么读你的项链\"。

## 11.2 祛魅时刻：PR 是什么、评审在评审什么

先给结论。

> **一个 Pull Request 的物理本质，是一次\"把我这条分岔的项链合流回主线\"的正式请求。它由三部分组成：（1）远端两条分支之间的 commit 差集，（2）一段人写的\"变更意图说明书\"，（3）一个允许他人评论、审批、阻拦的讨论区。这三部分里，只有第一部分是 git 本体的产物；后两部分——描述和讨论——是托管平台在 git 之上加的一层通信协议。**

这句话里三个字最要紧：**\"分岔\"、\"合流\"、\"意图\"**。展开三条推论。

### 推论一：PR 不是命令，是平台特性

`git pull-request` 这个命令**不存在**。你在终端里敲不出一个原生 git 命令去创建 PR。GitHub 的 `gh pr create`、GitLab 的 `glab mr create`、腾讯工蜂/Gitea 的对应命令——它们全都是**平台的 CLI**，而不是 git 的一部分。第 4 章讲过\"Fork 是平台特性\"，第 1 章讲过 GitHub 只是\"远端副本 + 权限/PR 层\"，PR 是这个\"层\"里最重要的一件东西。

**为什么这件事重要？** 因为它决定了 PR 里发生的一切——评论、批准、要求修改、CODEOWNERS 触发、CI 卡关、分支保护规则——**在你切换到 GitLab / Gitea / Bitbucket / 工蜂上时，都要重新学一遍**。git 本体是通用的，PR 层是平台方言。**很多团队冲突源自这里**：一个从 GitLab 转到 GitHub 的老手会误以为\"squash 合并\"是 git 的行为，其实是 GitHub 的 merge 按钮下拉菜单里的一个选项。

### 推论二：PR 请求的是\"合流\"，不是\"推送\"

想象项链。你 fork（或者 clone + 开分支），你的项链从 main 的某颗珠子上分岔出去，你在你的分岔上串了几颗新珠子。**PR 说的是**：\"我这段分岔项链的末端是 X 颗珠子，请把它们合流回主线项链。\"

**合流不是推送**。推送是\"我把我的一段搬到远端\"——这一步在你 `git push` 到自己的分支时**已经完成了**。合流是\"远端主线的守护者（人或规则）批准之后，让主线项链的末端**长出**你这几颗珠子\"。这两个动作在物理上是分离的：

```
      主线项链（origin/main）
      ──▶(A)──▶(B)──▶(C)
                     │
                     └─ 你 fork/开分支的分岔点
                     
      你的分岔项链（origin/feature/xxx）
                     │
                     └──▶(X1)──▶(X2)──▶(X3)  ← 你 push 到自己的分支
                     
      PR 请求的语义：把 X1、X2、X3 合流回主线
      
      主线项链（合流后 origin/main）
      ──▶(A)──▶(B)──▶(C)──▶(X1')──▶(X2')──▶(X3')
                                （或 M merge commit）
```

*图 11-1：PR 是一次\"请求把分岔合流回主线\"的通信，不是一次\"推送\"。你 push 完成的是分岔项链的建造，合流是主线守护者按下 Merge 按钮时才发生的动作。*

**这个物理分离解释了很多困惑**：为什么你 push 完了 PR 里还是显示\"Open\"（因为合流还没批准）；为什么你 close PR 之后你的分支还在（因为你 push 出去的分岔项链一颗珠子都没少，只是它\"合流请求\"被撤回了）；为什么 revert 一个 merged PR 会造一颗新的\"抵消 commit\"而不是回退历史（因为主线项链上真的多长了几颗珠子，要\"撤销\"必须再长一颗反向的珠子——第 10 章讲过）。

### 推论三：评审评的是\"意图\"，不是\"diff\"

打开一个 PR，你看到的最显眼的东西是 diff——一堆绿色的 `+` 和红色的 `-`。**新手评审员会做的事**：从上到下把 diff 读一遍，看到\"能理解的\"就点个赞，看到\"看不懂的\"就问一句 \"why here?\"，最后按 Approve。

**这样评审出来的东西，几乎等于没评审**。

为什么？**因为 diff 只是变更的\"证据\"，不是变更的\"内容\"**。你要评的是**这次变更想干什么、干得对不对**——那个\"想干什么\"不在 diff 里，在 PR 描述里、在关联的 Issue 里、在 commit message 里、在这次改动**没做但本该做的**那些地方。

给一个具象例子。假设你收到这么一份 PR：

```
标题：Fix bug in user login
描述：（空）
diff：
  src/api/auth.ts   | 3 +--
  src/api/user.ts   | 1 +
  2 files changed, 2 insertions(+), 2 deletions(-)
```

差三行代码。你逐行读，代码本身没毛病——修改后的语法正确、类型对得上、变量命名正常。你按 Approve。

**你漏掉了什么？** 你不知道\"bug\"到底是什么 bug、有没有对应的 Issue、有没有加测试来防止回归、有没有其它相似的地方也有同一个 bug、这个 fix 会不会引入新的 bug（回归风险）。**这些问题的答案，全都不在 diff 里**——它们本来应该在 PR 描述里，但那个描述是空的。

**所以真正的评审从来不是\"看 diff\"，是\"追问意图\"**。评审员要能回答的四个问题：

1. **这次变更想解决什么问题？**（关联 Issue、bug 描述、需求文档）
2. **为什么这个方案是合适的？**（对比其它候选方案的取舍——第 6 章讲过好 commit message 就该讲清\"why\"）
3. **这次变更的边界在哪、有没有过度扩张？**（应该只改 auth 却顺手改了 utils？拆分成两个 PR？）
4. **这次变更会不会引入新的问题？**（回归风险、性能、安全、下游依赖）

**这四个问题里，只有第 3 问部分可以从 diff 里读出来**。其它三问需要**上下文**——需要 PR 描述、需要 Issue 链接、需要评审员的领域知识。

**祛魅到这里，一个转折**：既然评审要评的是意图，而 diff 只是证据——那么**\"读 diff\"这件苦力活谁做？** 答：**AI 做**。

## 11.3 AI 时代的评审分工：机械的给 AI，判断的给人

第 6 章讲过\"commit message 里 AI 能生成 what、你必须写 why\"。评审这里是同一套分工的放大版。

**AI 擅长做的评审工作（机械性的）**：

- **风格一致性检查**：命名、缩进、import 顺序——linter 层面的东西 + 团队特定约定。
- **低效模式识别**：N+1 查询、循环里 await、无限制的正则、拼字符串式 SQL。
- **缺失测试提示**：\"这次改动动了 `calculatePrice` 函数，但 `tests/pricing.test.ts` 没有更新——是否需要加测试？\"
- **相似位置扫描**：\"你在 `user.ts` 修了这个 bug，`admin.ts` 里第 47 行有一段几乎一样的代码，是否也需要修？\"
- **依赖影响分析**：\"你改了 `apiClient` 的返回类型，仓库里有 23 处调用它——是否都跟着更新了？\"
- **安全模式扫描**：SQL 注入模式、`.env` 或凭证的痕迹、危险 API 使用。

这些工作**AI 做得比人快 10 倍且不会疲劳**。让 AI 在你打开 PR 的第一分钟里做一次\"机械预审\"，是把评审员的注意力**留给真正需要人的地方**的最好方式。

**人必须做的评审工作（判断性的）**：

- **意图与实现是否匹配**：PR 描述说\"重构性能\"，diff 却在加新功能——这不是 diff 的问题，是**意图和证据对不上**。AI 能看到不匹配，但**判断这个不匹配算不算问题**要人来做。
- **设计层面的取舍**：这个新加的抽象层是否必要？这个类是否应该继承而不是组合？这些问题**没有唯一正确答案**，评审员在**代替团队做集体决策**。
- **业务语义的正确性**：这个折扣计算逻辑对不对？这个权限检查是否覆盖了所有场景？——**AI 不知道你们业务的历史包袱**。
- **可读性与可维护性**：这段代码半年后新来的人能看懂吗？这个函数名是不是有更好的选择？——**这是审美判断**，AI 能提议但不能拍板。
- **代码考古结论**：\"这行代码半年前被 Alice 加过一次又删掉了，为什么现在又加回来？\"——**这需要人调 git blame 加上团队记忆**。

**分工原则一句话**：**AI 做\"能靠代码本身回答的问题\"，人做\"必须联系代码之外的东西才能回答的问题\"**。

### AI 能写 PR 描述，但你要核实——message 与 diff 不匹配的毒瘤案例

第 6 章讲过一条经验：\"AI 生成的 commit message 有可能和 diff 不匹配——它是从 diff 反向猜意图，猜错了就是一个持久的谎言\"。**PR 描述这里同一坨毒瘤会放大**：

- **AI 编 PR 描述的常见毒瘤**：AI 看 diff 猜出\"这可能是在做 X\"，写进描述里；但你的**真实意图**是 Y——你其实是在为 Y 做准备的一次半成品重构，diff 表面看起来像 X。**评审员读完 AI 写的描述，以为是 X 通过了；三周后 Y 上线时，他才发现自己批准的其实是 Y 的第一步。**
- **AI 帮你写描述的正确姿势**：让 AI 写**初稿**，你**读一遍并改写\"why\"部分**。**\"what\"部分（改了什么、涉及哪些文件）AI 写就行——那是 diff 的自然语言化。\"why\"部分（为什么改、为什么这样改、为什么不那样改）必须你写——那是 diff 之外的东西**。
- **一次 3 分钟的守卫**：AI 出初稿花 30 秒，你读+改花 2 分钟——**这 2 分半钟是团队协作里 ROI 最高的时间投资**，能把接下来评审员花在\"猜你意图\"上的时间从 10 分钟压到 2 分钟。

## 11.4 场景判断：常见协作情境的选择树

铺垫完毕。落到具体场景。**四类高频协作情境**，每类给一条判断规则。

### 规则一：怎么开 PR、开多大——原子 PR vs 巨型 PR

**症状**：你在一个分支上写了两周，攒了 800 行改动、12 个文件——同时做了 3 件事：加了一个新功能、修了一个不相关的 bug、顺手重构了一个工具函数。你正在犹豫\"开一个大 PR 还是拆开\"。

**候选方案**：

- **方案 A：一个大 PR 全塞进去**——省事，一次评审通过就完事。**代价**：评审员看到 800 行改动会\"关键性能力下线\"——他要么草率地全部 Approve、要么打回让你自己拆。前者是最常见的\"看 diff 假装评审\"的元凶。
- **方案 B：拆成 3 个原子 PR**——每个 PR 只做一件事，评审员一次只需要装载一个上下文。**代价**：你要在本地 `git cherry-pick` 或者交互式 rebase 拆分历史，加上 10-20 分钟的整理时间；也要处理\"PR B 依赖 PR A\"的顺序问题。
- **方案 C：一个 PR 但用多个 commit 明确分段**——把\"新功能\"、\"修 bug\"、\"重构\"分成三颗清晰的 commit，PR 描述里写清楚顺序。**代价**：评审员如果不看 commit-by-commit 视图，还是被 diff 淹没；\"取一舍二\"的合并操作（比如\"只合功能，不合重构\"）无法做到。

**判断规则**：

- **PR 的核心指标不是\"改了多少行\"，是\"评审员能否在一次心智装载里读完\"**。经验值：**200 行以内是舒适区，200-500 行是勉强区，500 行以上是\"评审员会草率\"区**。
- **\"能否原子化\"的判断标准**：如果这次改动里任意一件事撤下（比如\"重构\"整个不做），剩下的两件事仍然是**独立、可合并、可上线**的——那么这次改动**应该拆**。
- **反面案例**：修 bug 时顺手重构相邻代码。**顺手很爽，但你把\"修 bug 该合\"和\"重构值不值得\"两个判断绑在一起了**——评审员没法只批准前者。

**AI 指令模板**：

> 「我这个分支上有 800 行改动，横跨 12 个文件。帮我列出所有 commit 及其涉及的文件，识别哪些 commit 是\"新功能\"、哪些是\"修 bug\"、哪些是\"重构\"——如果一个 commit 混了多类改动，标出来。然后建议一个拆分方案：拆成几个 PR、每个 PR 包含哪些 commit、有没有依赖顺序。**不要**动我的分支，只出方案。」

### 规则二：如何做代码评审——AI 预审 + 人审判

**症状**：你被 assign 了一个 PR，早上 9 点收到通知，你 10 点开会前想尽快过一下。

**候选方案**：

- **方案 A：草率的\"眼过一遍\"**——从上到下滚一遍 diff，看得懂的点 Approve，看不懂的就问一句 \"why here?\"。**这是绝大多数评审的实际状态**。10 分钟一个 PR 走完，评审质量约等于零。
- **方案 B：一个人硬啃 diff**——认真逐行读，装载上下文，交叉检查其它文件。**这是理想状态**。**代价**：一个 500 行的 PR 认真评审需要 45-90 分钟，你日常工作节奏根本吃不下。
- **方案 C：AI 预审 + 人聚焦判断**——先让 AI 做一遍机械预审（列 diff 摘要、扫已知模式、检查测试、列相关文件），你拿着 AI 的输出**只聚焦于机械层扫不出来的部分**——意图、设计、边界、业务语义。**代价**：需要预先培养\"如何指挥 AI 预审\"的肌肉记忆；AI 有可能漏报或误报，你要有能力甄别。

**判断规则**：

- 除非 PR 极小（≤ 20 行）或极紧急，**默认走方案 C**。
- **AI 预审要求结构化输出**：不要让 AI \"看看这个 PR 有什么问题\" —— 它会给你一段没有边界的散文。**要求 AI 按类别输出**：变更摘要 / 潜在 bug / 测试覆盖 / 命名一致性 / 与描述的匹配度。
- **AI 输出的每一条你都要\"翻译\"到你的评审心智里**——AI 说\"这段有 N+1 查询风险\"，你要判断\"在这个业务场景下 N+1 值不值得改\"；AI 说\"缺测试\"，你要判断\"这段代码值不值得加测试\"。**AI 是快速侦察兵，判断权在你**。

**AI 指令模板**（此处是核心指令，展开写全）：

> 「我要评审 PR #123。请按以下六节结构化输出：
> 1. **变更摘要**：一句话总结这个 PR 想做什么（读 PR 描述和 commit messages），80 字以内。
> 2. **意图-证据匹配**：PR 描述里声称做了 A、B、C；diff 里实际做了什么？有没有描述里没提但 diff 里做了的（\"顺手\"改动）？有没有描述里承诺但 diff 里没做的（漏项）？
> 3. **测试覆盖**：这次 diff 里改动的每个函数/模块，对应的测试文件有没有更新？如果没测试文件，是否需要新建？列表输出。
> 4. **风险模式**：机械扫一遍是否触碰这几类模式——SQL 注入、密钥/凭证痕迹、N+1 查询、循环 await、无限递归风险、无 catch 的 promise、未处理的错误路径。命中即列出行号。
> 5. **相似位置**：diff 里修的地方，仓库里其它类似位置有没有一样的问题？（例：改了 `user.ts` 的类型，`admin.ts` 里有没有一样的？）
> 6. **命名与风格**：新增的函数/变量名是否符合仓库既有惯例？是否有更好的候选？
> 
> **明确要求**：每条结论都给出**文件路径 + 行号**作为证据。**没证据的判断不要写**——我不要\"整体看起来还可以\"这种话。」

拿到这份输出后，你**只需要**：

1. 看第 2 节——意图和证据对不对得上？对不上的地方要问 PR 作者。
2. 看第 3、4 节——AI 提出的风险你逐条判断该不该处理。
3. 看第 6 节——如果你有更好的命名想法就提建议。
4. **第 1、5 节是背景信息**，帮你装载上下文。

**评审总时间从 45 分钟压到 10 分钟**，且质量比\"眼过一遍\"高一个数量级。

### 规则三：什么时候用 fork vs shared repo

**症状**：你们团队正在建一个新项目，主管问：\"用 fork 工作流还是 shared repo 工作流？\"

**候选方案**：

- **方案 A：Shared repo（共享仓库）**——所有人 clone 同一个仓库，每个人在同一个远端上开自己的分支。**优点**：分支同步简单、PR 之间可以互相依赖、上手简单。**缺点**：所有人都对同一个远端有 push 权，权限粒度只能靠分支保护做；仓库分支数量会膨胀（几十上百个 feature/xxx）。
- **方案 B：Fork（分叉仓库）**——每个人 fork 一份到自己名下，从自己 fork 开发、PR 到 upstream。**优点**：权限最小化（贡献者对 upstream 无 push 权）、upstream 分支列表干净、易于处理外部贡献者。**缺点**：多一层远端配置（第 4 章讲过的\"三层项链\"）、分支同步稍复杂。

**判断规则**：

- **信任模型定选择**：
  - **完全内部团队、成员固定、都签过 NDA**——用 **shared repo**。省事。
  - **有外部贡献者、开源项目、有实习生/短期合作**——用 **fork**。权限最小化是安全底线。
  - **大型内部项目跨多团队协作**——**fork**。避免\"我们 A 团队的人不小心 push 了 B 团队的分支\"。
- **回顾第 4 章的三层图**（origin=你的 fork、upstream=官方项目、local=本地）。**fork 工作流的心智负担是\"我 push 到哪个远端\"这个问题**——一旦你能张口说出\"我从 upstream fetch、push 到 origin、PR 到 upstream\"这句话，fork 工作流对你就是零心智负担的。
- **绝大多数中小团队默认用 shared repo**——因为团队信任度足够、上手快。**但即便用 shared repo，也一定要开分支保护**——见规则四。

### 规则四：分支保护、CODEOWNERS、直接 push vs PR-only

**症状**：新加入的实习生给你发消息：\"我刚 `git push origin main` 被拒了，报错说 `protected branch hook declined`——我做错了什么？\"

**候选方案**：

- **方案 A：不开分支保护，靠\"团队约定\"**——所有人自觉不直接 push main、都走 PR。**代价**：约定=没人守。总有一天有人（可能是你自己）在赶时间时敲下 `git push origin main`——第 10 章剧本 8 就是这么发生的。
- **方案 B：开分支保护（推荐）**——在 GitHub/GitLab/Gitea 上开启 main 分支保护，禁止直接 push、要求 PR、要求至少一个 review approval、要求 CI green。**代价**：所有人（包括你自己）都要走 PR 流程；紧急 hotfix 时有几分钟等 CI 的\"仪式感痛苦\"。
- **方案 C：分支保护 + CODEOWNERS**——B 的基础上再加一层：某些目录（比如 `/security/`、`/db/migrations/`、`/.github/workflows/`）改动必须由**指定的 owner** approve 才能合。**代价**：owner 成为瓶颈，owner 休假时相关目录改不了——**这是有意的痛感**。

**判断规则**：

- **任何 shared 分支（main、develop、release/*）都应该开分支保护**。这是第 10 章教训的直接对策。
- **分支保护的最小配置**：
  1. 禁止直接 push
  2. 要求 PR（且 PR 至少 1 个 approval）
  3. 禁止 force push
  4. 禁止删除
  5. 要求 CI 通过
- **CODEOWNERS 用于\"高风险目录\"**——不是所有目录都需要。**\"改这个目录的成本应该被结构化地拉高\"**的地方才配得上 CODEOWNERS。典型清单：安全策略、数据库迁移、CI 配置、发布脚本、依赖清单（package.json / go.mod）。
- **对实习生那句话的答案**：\"你没做错，是 main 分支开了保护——push 被拒是**系统在替你守规矩**。**你的工作方式应该是**：开 feature 分支 → push feature 分支 → 在 GitHub 上开 PR → 等 review + CI。\"

### 规则五：远程协作礼仪——force push 三思、rebase 后重推的时机、不重写共享历史

**症状**：你在协作分支 `feature/checkout-v2` 上工作两周，review 意见回来了：\"提交太散了，压成几个原子提交\"。你想 `git rebase -i main`——第 10 章剧本 4 的开场。

**候选方案**：

- **方案 A：一言不合直接 rebase + `push --force`**——1 分钟操作，1 小时后小李在群里刷屏。**这是第 10 章剧本 4 完整重演**。
- **方案 B：rebase + `push --force-with-lease`**——比 `--force` 稍安全一档：**只在\"远端没在你上次 fetch 之后被别人改过\"时才允许覆盖**。**但这不是免死金牌**——而且它的盲区和直觉相反：同事上周就推过而你一直没 fetch，缓存是旧的，lease **会**把你拦下（这正是它起作用的时刻）；它真正拦不住的是你 fetch 之后又把别人的提交从分支上抹掉——缓存已等于远端，检查必然通过（第 10 章剧本 4 详解，含带期望值的写法和 `--force-if-includes`）。
- **方案 C：先在群里喊一声、再 rebase + `--force-with-lease`**——最完整的礼仪。\"@小李 @小王 我要 rebase 一下 feature/checkout-v2 整理历史，接下来 30 分钟你们先别推东西，rebase 完我在群里 @ 你们更新本地。\"

**判断规则**：**回想第 5 章的黄金规则**——

> **不要 rebase 已推送到共享分支的 commit。**

如果**必须**（review 明确要求整理历史、要 squash-and-merge），走**方案 C**——三件套：

1. **先 fetch**：`git fetch --all`——保证你操作的是最新状态。
2. **先喊话**：群里通知，让协作者暂停推送。
3. **`--force-with-lease` 而不是 `--force`**：多一道保险。

**关于 rebase 后重推的时机**——如果你是**唯一**在这条分支上工作的人，rebase 完立刻 push 就行；如果有多人协作，rebase 完**必须**通知协作者**先删掉他们本地的这个分支再重新 fetch + checkout**，不然他们那边一 pull 就会造出一堆重复 commit（因为 SHA 全变了但内容一样，Git 会以为是两条不同的历史）。

**关于\"不重写共享历史\"**——第 5 章的黄金规则不是\"技术上做不到\"，是\"社交上不允许\"。**技术上 Git 允许**：只要你有 push 权 + 分支保护允许 force——你就能覆盖历史。**但你的团队的所有本地 clone、CI 缓存、外部贡献者的 fork——都会被这次覆盖搞乱**。**这是把\"你 5 分钟的方便\"换成\"团队若干小时的清理成本\"**——绝大多数情况下这个交易亏得离谱。

## 11.5 代码考古：blame、log、shortlog

场景切换。**你不是在写代码、也不是在评审，而是在**\"考古\"——试图搞清楚某段代码为什么会变成现在这个样子。这是团队协作的一个隐形维度：**你要读的不只是同事今天推的 PR，还有半年前离职的同事、一年前的自己、两年前重构留下的沉积岩**。

### 三个考古工具、三个问题

**问题一：这行代码是谁写的、什么时候写的？** → **`git blame`**

`git blame src/api/user.ts` 会在每一行前面标注：**最后修改这行**的 commit SHA、作者、日期。**注意\"最后修改\"这三个字**——如果我三个月前加了这行、你昨天改了个空格，blame 显示的是**你昨天**。所以 blame 不是\"谁最初写了这行\"，是\"这行在现在这个形状上，最后被谁碰过\"。

**要看\"最初写的人\"**：`git log -L 47,47:src/api/user.ts`——追这一行的完整历史，从最早出现到现在。

**问题二：为什么这么写？** → **`git log` + commit message + PR 描述**

blame 给了你一个 SHA。接下来 `git show <sha>` 看这颗珠子的 commit message；如果 message 里提到 PR 编号（\"See PR #456\"），去 GitHub/GitLab 上翻那个 PR 的描述和讨论。**这是\"why\"的完整链条**：

```
一行代码
  │
  └─ blame → 找到 commit SHA
                │
                └─ show → 读 commit message（80 字的\"why\"）
                                │
                                └─ 找到 PR 编号
                                       │
                                       └─ 翻 PR 描述、讨论、关联 Issue
                                              │
                                              └─ 完整的\"当时为什么这么做\"
```

**这条链条的完整度，取决于团队协作的规范度**。如果 commit message 都是\"fix\"、\"update\"、\"改了一下\"——链条在第二步就断了；如果 PR 描述都是空的——链条在第三步断。**\"代码考古能不能挖到东西\"，就是团队\"通信协议质量\"的最终检验。**

**问题三：整个团队在这段时间里贡献分布是什么样的？** → **`git shortlog`**

`git shortlog -sn --all`——每个作者的提交数，按数量排序：

```
   234  Alice
   187  Bob
    92  Carol
    43  你
     3  离职的 Dave
```

**这不是绩效考核**（提交数不代表贡献质量），但**它是一张团队健康的雷达图**：

- 有人的提交数是零——他真的不写代码，还是签名配错了（`user.email` 没配对导致他所有提交都算别人头上）？
- 某个模块的贡献者只有一个人——**这就是巴士因子**（bus factor）等于 1，那个人一走这个模块没人接得起。
- 某个时间段所有提交都集中在一两个人——那段时间团队协作出问题了、还是只是大促封版期？

**`git shortlog --after='2025-01-01' --before='2025-06-30' -sn`** 加时间范围，看某个阶段的贡献分布。

### 一个高频误区：blame 不是问责

看到\"blame\"这个词，很多团队氛围会瞬间紧绷——\"是谁写的这段烂代码？\"**这是错误使用**。

**blame 的原始英文含义确实是\"归咎\"**，但在 git 里它是**技术工具**。**正确使用**：\"这行看起来奇怪，我 blame 一下**是在什么背景下加进来的**——可能有我不知道的历史\"。**错误使用**：\"我 blame 出来是你写的，你解释一下\"。

**前者叫考古**，是搞清楚背景**再**决定要不要改；**后者叫追责**，是给\"改代码\"这件事绑上情绪负担，让人怕改代码。**长期跑，团队里\"考古\"氛围会孵化出敢改代码的人；\"追责\"氛围会孵化出躲着不改的人**。

## 11.6 AI 指令箱 · 协作与考古

**颜色标注**：本章指令里 blame/log/shortlog/PR review 都是绿色（只读）；写 PR 描述属于黄色（要人核实）；rebase-then-force-push 是黄红交界（第 12 章会展开）。

**🟢 PR 起草类（AI 出初稿、你改 why）**

- 「基于当前分支相对于 origin/main 的差异（`git log origin/main..HEAD`、`git diff origin/main..HEAD --stat`），起草一份 PR 描述。要求六节结构：
  1. **背景/动机**（关联的 Issue 编号、要解决的问题）——**这一节标 [TODO：作者补充]，你不要编**；
  2. **改了什么**（面向读代码的人，按模块列表）；
  3. **为什么这样改**（技术方案的取舍，如果 diff 里看不出来就标 [TODO]）；
  4. **测试**（列出改动的测试文件、如果没加测试就明说\"未加测试\"，别粉饰）；
  5. **风险与回滚**（这次改动可能影响哪些下游、如何回滚——通常是 revert 这个 PR）；
  6. **审查重点**（希望评审员重点看哪几个文件的哪几处）。
  **明确要求**：任何你不确定的地方标 [TODO：作者补充]，**不要编造 why**。」

- 「读这份 PR 描述初稿。指出以下问题：（a）有没有和 diff 不匹配的\"编造出来的意图\"；（b）有没有 diff 里改了但描述里没提的\"顺手\"改动；（c）有没有明显应该说明但没说的（比如没提 breaking change、没提 migration 步骤）。**只指出问题，不要替我改**。」

**🟢 评审预审类（前面 §11.4 已给完整模板，此处补几条简版）**

- 「预审 PR #<number>，按六节结构输出：（1）变更摘要；（2）意图-证据匹配（PR 描述声称的 vs diff 里实际做的）；（3）测试覆盖；（4）风险模式（SQL 注入 / 密钥痕迹 / N+1 / 无 catch 的 promise 等）；（5）相似位置（diff 里修的问题在仓库其它地方还有没有）；（6）命名与风格。**输出必须带文件+行号**。」

- 「这份 PR 的作者声称做了 X。基于 diff 判断：作者做的实际上是不是 X？如果不是，实际做的是什么？（做\"意图-证据比对\"这一件事就够，其它别写。）」

- 「这份 PR 改了 `apiClient` 的返回类型。全仓库搜索 `apiClient` 的所有调用点，列出：（a）改动后仍然工作的（类型兼容）；（b）改动后会 break 的；（c）不确定的。给我一个表格。」

**🟢 代码考古类**

- 「这个文件的第 47 行看起来很奇怪：`if (user.role === 'admin' && !user.legacy_flag) { ... }`。用 blame + log 挖一下：（a）这行最早是哪次 commit 加进来的？（b）当时的 commit message 和 PR 描述说了什么？（c）`legacy_flag` 这个字段在仓库里其它地方是怎么用的？（d）用一段话总结\"这行代码为什么长成这样\"。」

- 「查一下 `src/pricing/discount.ts` 这个文件近 6 个月的完整变更历史：每次 commit 的作者、日期、message 第一行，以及那次动了多少行。用时间轴表格给我。」

- 「查一下本仓库最近 3 个月的贡献分布：（a）每个作者的提交数（`shortlog -sn`）；（b）每个作者主要贡献的模块（用 `log --author=xxx --name-only` 聚合出他动最多的前 5 个目录）；（c）**巴士因子分析**：有没有哪个目录只有一个人贡献过？如果那个人明天不在，谁最有可能接手？」

- 「找出本仓库里 6 个月没被任何人改过、但依然在被引用的\"沉睡代码\"——列出 top 20 个这样的函数/模块。用 `log --before='6 months ago' --name-only` 加过滤逻辑。」

**🟡 需要盯着的（改历史/影响他人）**

- 「我要在 feature/checkout-v2 上 rebase 一下 main 来整理历史。**执行前必须先做的三件事**：（1）`git fetch --all` 确认最新；（2）用 `git log feature/checkout-v2 --format='%an' | sort -u` 列出这条分支上所有贡献者，如果有其他人，**停下来让我发群通知**；（3）`git branch backup/before-rebase-$(date +%Y%m%d-%H%M%S)` 建备份分支。三件事都做完再动 rebase，rebase 完用 `--force-with-lease` 推。」

- 「基于 review 意见，把当前分支上散落的 15 个 commit 整理成 4 个原子 commit。**方法**：交互式 rebase（`rebase -i main`），你先给我一份**完整的 rebase todo 脚本**（每颗 commit 选 pick/squash/fixup/reword），我确认后你再执行。**中途遇到冲突，停下来展示两侧内容让我判断，不要自作主张**。」

**训练用指令（陪练模式）**

- 「给我 8 道\"PR 描述里的信息够不够\"判断题。每道题给一份 diff + 一份描述，我判断这份描述能不能让评审员做出\"是否 approve\"的判断——不够的话缺什么。你批改讲评。」

- 「给我 5 段真实感的 commit message（既有好的也有坏的），我打分（1-5 分），你也打分并给出你的评分理由。看我和你打分的差异——差异大的地方一起讨论。」

- 「假装你是新来的实习生，问我 6 个关于\"我们团队为什么这么用 Git\"的问题，覆盖：为什么开分支保护、为什么用 PR 不能直接 push、为什么要写 PR 描述、fork 和 shared repo 的区别、force push 为什么危险、CODEOWNERS 是干什么的。我答完你打分。」

## 11.7 执行后的世界

把本章指令交给 AI 执行后，`.git/` 里和\"平台层\"发生了什么？透视一下：

| 你说的话 | AI 大概率执行 | `.git/` 或平台的真实变化 |
|---|---|---|
| \"起草一份 PR 描述\" | 读 `git log`、`git diff`、生成文本 | **零 git 变化**——只是生成了一段文字，你要复制粘贴到 GitHub |
| \"评审 PR #123\" | `gh pr view 123 --json` + `gh pr diff 123` | 零 git 变化。**平台层**：如果你用 `gh pr review --comment` 交评审意见，PR 的评论区多出一条 |
| \"blame 这行\" | `git blame -L 47,47 src/api/user.ts` | **零变化**（纯读 objects 里已有的 commit） |
| \"考古半年前的一个函数\" | `git log -L :funcName:file.ts` | **零变化**（纯读，可能触发一次 pack 文件解压缓存） |
| \"看团队贡献分布\" | `git shortlog -sn --all` | **零变化**（读 refs + 遍历 objects） |
| \"rebase 后 force-with-lease push\" | `git rebase main` + `git push --force-with-lease` | **本地**：rebase 造一批新 commit（SHA 全变），旧 commit 在 objects 里孤儿化（30 天托管期）；**远端**：`refs/heads/<branch>` 从旧 SHA 挪到新 SHA，旧 commit 在远端 objects 里孤儿化（远端 gc 前） |
| \"交互式 rebase 整理成 4 个 commit\" | `git rebase -i main`，按 todo 执行 pick/squash | 每颗 squash 掉的 commit 都不再被引用，进入孤儿化；新的\"压缩过的\"commit 被造出来，refs 前移 |
| \"创建 PR\" | `gh pr create --title xxx --body xxx` | **git 侧零变化**。**平台侧**：GitHub 数据库里新增一个 PR record，触发一堆自动化（CI 触发、CODEOWNERS 通知、bot 检查） |
| \"审批并合 PR\" | `gh pr review --approve` + `gh pr merge --squash` | **平台侧**：批准记录写库、根据你选的 merge 策略（merge / squash / rebase）执行远端合并——**远端 `refs/heads/main` 前移一格或几格**；**你本地**：这一秒**没有任何变化**（除非你之后 `git pull`） |

看懂这张表你会理解：**协作层的动作 90% 发生在\"平台侧\"，而不是 git 本体侧**。**PR、评审、评论、批准、合并策略——这些都是平台在管理**。git 本体只在两个地方参与：（1）你 push/fetch 时同步 objects 和 refs；（2）你 merge 后本地 pull 拿到新状态。**理解这个分层，你就不会再被\"为什么这个操作在 GitHub 上做和在 GitLab 上做不一样\"困惑**——因为你在两边使用的其实是两套不同的\"平台方言\"，git 只在最底层保持一致。

## 11.8 命令侧栏

```
远程协作（push / pull / fetch，第 4 章讲过）
git fetch --all                 # 更新所有远程缓存（协作第一动作）
git push -u origin <branch>     # 首次推自建分支
git push --force-with-lease     # 温柔的 force（比 --force 安全）

PR 创建与管理（GitHub CLI，其它平台类似）
```

**三大典型误解拆解**

1. **\"PR 描述不重要，代码本身会说话。\"** ——**代码只会说 what，不会说 why**。第 6 章讲 commit message 时讲过这条，PR 描述是它的团队级放大版。**没有描述的 PR，评审员只能凭 diff 猜你意图；猜错就 approve 了错的东西，猜对了但花了 10 分钟猜——这 10 分钟是你 3 分钟写描述就能省下的**。**\"代码会说话\"这句话是懒惰的自我安慰**：代码能说的是\"我做了什么\"，说不了\"为什么这样做而不是那样做\"、\"我考虑过 A 但没选 A\"、\"这个改动依赖了下周才要上的 feature flag\"——这些永远不在 diff 里。**PR 描述框那 3 分钟，是团队协作里 ROI 最高的时间投资**。
2. **\"评审 = 逐行看 diff。\"** ——**diff 是证据，不是评审对象**。你要评的是**这次变更想干什么、干得对不对、有没有过度、有没有漏项、能不能维护**——这些问题的答案 80% 不在 diff 里，在 PR 描述里、Issue 里、commit message 里、代码之外的团队记忆里。**\"逐行看 diff\"最后往往退化成\"看得懂就 approve\"**——因为一个刚被 diff 淹没 800 行的评审员，认知资源全花在解析代码语法上了，没有余力做\"这个方案好不好\"的判断。**AI 时代评审员的正确姿势**：让 AI 逐行看，你聚焦判断。**\"从代码里看不出来的东西才是评审的核心\"** ——这条直觉建立起来，评审质量会跳一个档次。
3. **\"blame 是拿来问责的。\"** ——**blame 是考古工具，不是审判工具**。当你 blame 出\"这段烂代码是三个月前的 Bob 写的\"时，正确反应不是\"@Bob 你解释一下\"，是\"我 show 一下这颗 commit + 翻一下对应的 PR，看看当时是什么背景\"——**很可能当时的 Bob 是在赶一个 deadline、当时的团队还没有现在的规范、当时那段代码是为了兼容一个后来被删掉的旧功能**。用\"考古\"氛围而不是\"追责\"氛围看历史，团队会孵化出**敢改代码的人**；反之孵化出**躲着不改的人**——因为改了就意味着自己被 blame。**\"blame\"这个英文词是历史包袱**，你在心里把它换成\"archaeology\"，姿势就对了。

> **🤖 AI 指令箱 · 本章实战演练**
>
> 找一个你有权限的**真实**（或你自己的沙盒）仓库——**推荐用你正在合作的项目**，因为本章的很多演练需要\"真人协作对象\"才有意义。按顺序执行下面这几组\"协作演练\"。**每组做完对着本章的判断规则复盘**：你的决定和本章的判断规则一致吗？不一致的地方是你的场景确实特殊，还是你的直觉需要校准？
>
> - **演练 1 · 起草一份高质量的 PR 描述**：找一个你**正在开发的分支**（哪怕是本地还没 push 的），让 AI 按 §11.6 那个六节结构起草 PR 描述。**关键动作**：拿到初稿后，你**逐节读一遍**——第 1 节（背景/动机）如果 AI 编了内容，就整段删掉重写；第 3 节（为什么这样改）如果 AI 从 diff 里\"猜\"出来的 why 你觉得不对，也重写。**做完这一遍你会震惊地发现**：AI 出的初稿把\"what\"部分（改了什么）写得又快又完整，你**只需要花 2 分钟改 why**。这就是本章说的\"3 分钟 ROI 最高投资\"的肌肉记忆。
> 
> - **演练 2 · 用六节模板做一次结构化 PR 评审**：找一个**别人开的**开源项目 PR（GitHub 上随便选一个近期的、你能读懂业务的），用 §11.4 规则二那个完整指令模板让 AI 出预审报告。**关键动作**：（a）AI 输出的第 2 节（意图-证据匹配）你重点看——如果 AI 说\"描述里没提但 diff 里做了 X\"，你自己去 diff 里核对 X 到底存不存在；（b）AI 输出的第 4 节（风险模式）你抽查 2 条——沿着 AI 给的行号去看，那个\"N+1 查询风险\"真的存在吗？**目的是校准 AI 的假阳率和假阴率**——用几次后你会知道 AI 在你的技术栈里可信度大概多少。
>
> - **演练 3 · 做一次代码考古**：在你熟悉的仓库里，随便挑一个**长得奇怪的函数**（比如注释写着 `// HACK` 或者一段你不理解的复杂逻辑），按 §11.6 考古指令挖一遍。**关键动作**：（a）从这行代码追到最初的 commit、追到 PR、追到 Issue——链条走到哪一步断掉？（b）如果链条断在\"commit message 太烂\"这一步，反思你自己写的 commit 是不是也这样；（c）如果链条走完了、你**理解了那段代码为什么长成这样**——记下这个瞬间的感受。**这个瞬间就是\"团队协作规范度\"这个抽象词汇变成体感的时刻**。
>
> - **演练 4 · 团队巴士因子分析**：在你所在仓库跑 `shortlog -sn --after='6 months ago'`，然后让 AI 分析\"某个人如果明天离职，哪几个目录/模块最没人接得起\"。**关键动作**：（a）看结果里最脆弱的那个模块是什么；（b）思考\"如果那个人真的明天不来了，团队该怎么办\"；（c）**这个问题的答案不是\"再找一个懂那个模块的人\"，是\"从今天开始安排另一个人参与那个模块的评审、让第二个人在血脉里流经过那段代码\"**——巴士因子只能通过**日常协作分布**降低，不能通过\"应急预案\"降低。
>
> - **演练 5 · 一次真实的 rebase-then-force-push（在协作分支上）**：**注意：这个演练必须用你自己的沙盒仓库或者你确定不会影响别人的分支**。**流程**：（a）在一个 feature 分支上造几颗\"散乱\"的 commit（每颗一点点改动）；（b）用交互式 rebase 把它们 squash 成 2-3 颗原子 commit——**中途至少经历一次冲突让你手动解决**；（c）rebase 完先 `git branch backup/$(date +%Y%m%d-%H%M%S)` 打个备份分支；（d）**在群里假装@协作者**（可以是你自己扮演）通知一句；（e）`git push --force-with-lease`。**关键动作**：整个流程走完后，回看**你在哪一步差点手抖 skip 掉**——那一步就是你未来真正协作时最容易出事的地方。
>
> **五个演练总用时 60-90 分钟，做完你会发现——之前那些\"跟同事协作时的紧张、评审时的心虚、看历史时的困惑\"，绝大多数都是\"没有把协作当成一个可以刻意练习的技能\"造成的**。**这就是本章的最终交付**：**从\"协作 = 撞运气\"的心理模型，升级到\"协作 = 可以设计的通信协议 + 可以练习的判断力\"的心理模型**。第 12 章会把这套心理模型套上最后一层护甲——安全边界。
