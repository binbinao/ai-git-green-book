## 0. 通读结论

**这本稿子的骨架是对的，而且"对"得很罕见**——`origin/main ≠ 服务器上的 main`（ch04）、"diff 不是 Git 存的东西，是现算给你看的"（ch02）、"三个 CONFLICT 里有两个是语义冲突"（ch09）、"先吊销、再清理"（ch10）、"clone 是一次跑代码"（ch12）：这些是能真正纠正读者心智模型的段落，市面上多数 Git 书给不出来。

但作为一本**必须可信**的书，它现在有一类不能带病交付的问题：

1. **有 6 处"照做会失败或失去保护"的技术错误**，其中 `--force-with-lease` 一条最严重——第 5 章教"先 fetch 最能挡住同事的推送"，第 10 章的救援剧本又要求"不要 fetch 直接 push --force-with-lease"。**这两个说法互相否定，而且实测两条路一条会失效、一条会被 Git 拒绝**（见 P0-1）。
2. **第 10 章的"Git 几乎不扔东西"被自己的细节拆台**：分支 reflog 其实会随分支一起被删、`git add` 过的 blob 没有 30 天保护（实测一次 `gc --prune=now` 就没了）、`git fsck --dangling` 在 reflog 有效期内**看不见**只被 reflog 引用的珠子（要加 `--no-reflogs`）。这三处恰好同时打击本章的兜底三件套。
3. **体量分布失衡**：`ch10` 一章 13,332 汉字，是全书章节中位数（`ch08` 7,818）的 **1.7 倍**；而承担"概念章风格模板"角色的 `ch03` 只有 3,457 汉字，是中位数的 0.44 倍。**该减的是最长章，该加的是最短章**——现在两边反向。
4. **术语层有一个必须动手的隐患**："标签"一词同时指**分支/引用**（ch03 38 次、ch05 56 次）、`git tag`（ch01、ch13）、以及"备份分支"（ch05）。全书核心比喻靠这个词立着，读者一旦串义，五张地图会一起松。
5. **外部事实层缺"版本锚点"**：第 12 章有 4 处硬错、3 处已过时（Gitea 没有 secret scanning、GitHub push protection 的免费边界、Copilot 已为自己的提交签名……）。这一章是全书时效性最脆的一章，必须加"截至 X 年 X 月"的书写规范。

**一句话判断：结构可以定稿，技术事实与术语口径需要一轮专项修订。** 建议按本报告第 6 节的三轮顺序执行，预计修订后可净减约 1 万字，篇幅与质量同向改善。

## 2. P0：会误导读者的问题（必须先修，不是文字问题）

每条都给了实测/官方依据。表格说明：**实测**=我在临时仓库跑过；**文档**=`man` 页或官方手册原文。

### 2.1 `--force-with-lease`：三处口径互相否定（最高优先级）

| 位置 | 原文 | 问题 |
|---|---|---|
| `ch05:313` | "前提是远端还是我上次 fetch 时看到的那个样子……请拒绝我" | **定义正确** |
| `ch05:320` | "用 `--force-with-lease` 之前先 `git fetch`——这样你的本地缓存反映的是刚刚的远端状态，**最能挡住**'我离开的这几分钟里同事推了东西'的意外" | **与上面 7 行前的定义自相矛盾**：缓存一旦等于远端现状，lease 检查必然通过，保护归零 |
| `ch05:328` | 流程第 2 步"`git fetch origin` 确认远端此刻确实是你 rebase 之前那 8 个 commit" | 同上：这一步之后 `--force-with-lease` 等价于裸 `--force` |
| `ch04:432` | "只在远端没在你**上次 fetch** 之后变过才允许" | **正确**，与 ch05 冲突 |
| `ch10:383` | "立刻在群里喊住小李和小王——**不要 pull，不要 fetch**" | 把 `fetch` 也禁掉是过度了：`fetch` 只更新 `origin/*`，不动本地分支 |
| `ch10:397` | "小李，你现在**先不要 fetch**——直接在你当前分支上 `git push --force-with-lease origin feature/checkout-v2`" | **实测该命令会被拒绝**（见下） |
| `ch10:419` | "如果同事上周就推过而你没 fetch，lease 完全无能为力" | **因果讲反**，见下 |

**实测（两个克隆 + 一个 bare 远端）**：

```
A 未 fetch，直接 push --force-with-lease
  → ! [rejected]  main -> main (stale info)      ← 被挡住了，保护生效
A 先 git fetch，再 push --force-with-lease
  → + ca48c7e...80e8f82 main -> main (forced update)   ← 成功覆盖，同事的 b1 从分支上消失
```

即：**"先 fetch"不是加强保护，是把保护归零**。而 `ch10:397` 让小李在缓存陈旧的状态下推送，恰好落进实测的第一行——**书里最关键的一个救援动作，按原文照抄会被 Git 拒绝**。

`ch10:419` 的因果也需要翻转。lease 真正的盲区是：

- lease 只回答**"远端此刻的 SHA 等于我缓存里的 SHA 吗"**。
- 它**拦不住**的情形是：你缓存里**已经看到**别人的提交（你 fetch 过），然后把它们从分支上抹掉——检查通过，因为缓存就等于远端。**这正是第 10 章这场事故本身的成因**：你 rebase 前 fetch 过，所以 `--force-with-lease` 没有阻止你删掉小李的两颗珠子。
- 反过来，"同事上周推过而你没 fetch"→ 缓存陈旧 → lease **会**拒绝你（实测第一行）。

**统一改法（四处一起改）**：

1. `ch05:320` 那句删掉，改成一句判据：
   > **不要为了 push 去 fetch。** `--force-with-lease` 的价值恰恰来自你的缓存是"旧"的——旧缓存会让 Git 在远端变过时拦住你。想同时具备"保护"和"对齐预期"，用带期望值的形式：`git push --force-with-lease=<branch>:<你期望远端仍是的那颗 SHA>`（官方文档中唯一非实验性的写法），或用 `--force-if-includes` 兜住"后台自动 fetch 把缓存刷掉"的情形（IDE / 编辑器插件自动 fetch 很常见）。
2. `ch10:383` 的禁令收窄为"**不要 pull**（以及 merge / rebase）"。
3. `ch10` 的救援序列改为（顺序很重要）：
   ```
   ① 小李先钉住黄金状态（这一步让他敢 fetch）
      git branch rescue/golden feature/checkout-v2
   ② 再 fetch —— 只更新 origin/* 缓存，不碰任何本地分支
      git fetch origin
   ③ 再把黄金状态推回去
      git push --force-with-lease origin feature/checkout-v2
   ```
   比原文多两步，但**能跑通**，且黄金 SHA 在本地有分支兜着，比"千万别 fetch"的紧张感更让人安心。
4. `ch10:419` 按上面的"盲区"重写。

### 2.2 第 10 章的兜底三件套：三条都不完全成立

| # | 位置 | 原文（摘要） | 实测/文档结论 | 建议改法 |

| P0-3 | `ch10:74` | "只要一个对象被 Git 造过一次（`git add` 或 `git commit`），它就获得了 **30-90 天**的托管期" | **错**。30/90 天是 **reflog 条目**的保留期，不是对象的。`git add` 不写 reflog | 拆成两句：commit 级孤儿（有 reflog 记录）30 天；`add` 出来但从未 commit 的 blob 只受 `gc.pruneExpire` 保护 |

| P0-4 | `ch10:803` | "用 `git fsck --lost-found` 列出……**只读、不改任何东西**" | **错**。实测：`--lost-found` 会在 `.git/lost-found/commit/`（及 `other/`）下**写出文件**。这是它在 8 个剧本里唯一"看起来只读实则写盘"的命令 | ① 诊断统一用 `git fsck --dangling`；② 反过来把 `--lost-found` 讲成**正向功能**："它会把捞到的内容按 SHA 落成文件——`.git/lost-found/other/<sha>` 里就是你要找回的 `.env` 原文，比 `git show > path` 省事" |

## 8. 需要作者拍板的三个决策

1. **体量口径**：接受"正文 12.1 万 + 附录 2.6 万 = 14.7 万"，还是压到 13 万以内？我的建议是**接受**（正文本就在原规划内），但把 README 的字数口径与附录单列写清楚。
2. **颜色分级按什么定**：按"是否需要人确认"（附录 B 口径），还是按"是否不可逆"（附录 A 口径）？我建议**按可逆性 + 影响范围**，因为读者真正需要的是"这个动作能不能撤回"。
3. **"标签"是否改"名牌"**：这是一次全局替换，会影响全书的比喻手感和附录 C。但从"标签有三义"这个隐患看，**不改的代价更大**。
