## 0.1 场景引入：上周五的那条命令

想象一个普通的工作日下午。

你正在写一个新功能，改到一半，同事说 main 分支上有个紧急修复要你帮忙验证。你需要暂时放下手头的改动，但又不敢 commit——这些半成品代码不想进历史。于是你打开搜索引擎，输入"git 暂存当前修改不提交"。

三十秒后，你找到了答案：`git stash`。复制，粘贴，回车。工作区瞬间干净，问题解决。

上周五也是这样：你把一个 bugfix 错误地提交到了 main 分支，搜索引擎告诉你三条命令——`git branch`、`git reset --hard`、`git checkout`。复制，粘贴，回车。解决。

今天早上还是这样：rebase 冲突卡住了，你搜到的帖子说"冲突解决后执行 git rebase --continue"。你照做了，但你不知道自己刚刚是"继续"到了哪里，也不知道为什么那几个文件里的 `<<<<<<<` 消失了。

**这些命令都能跑。问题解决了。但请诚实地回答一个问题：**

> **你能说出刚才执行的命令，到底改变了什么吗？**

如果答案是"不能"，那么恭喜你，你和大多数开发者一样，正在践行一种有名字的生活方式——

## 0.2 Cargo-Cult Git：一种全球流行病

二战后的太平洋岛屿上，原住民看到军队运来物资：飞机降落在简易跑道，塔台挥手，货箱落地。战争结束后军队撤走了，货不再来了。于是岛民们用木头搭建假塔台，戴上椰子壳做的耳机，在假跑道上模仿塔台的手势——他们复刻了所有看得见的仪式，期待货机再次降临。

人类学家管这叫 **cargo cult（货物崇拜）**：**仪式正确，因果不明。**

软件行业借用了这个词。当你从 Stack Overflow 复制一条 `git reset --hard HEAD~3`，粘贴，回车，问题消失——你在做的事情，和戴着椰子耳机的塔台没有本质区别。命令是仪式，你没有看到因果。

这不是你的错，而且你绝不孤独：

- Git 的主要维护者之一、《Pro Git》作者 Scott Chacon，在《Git Internals》一书开篇写道：**"我看到一个又一个开发者爱用 Git，但从没真正理解它，只是记住一小串命令用于日常任务。"**
- 2022 年一篇 TOSEM 论文（Yang et al.）分析了 Stack Overflow 上 80,370 条 Git 相关提问并调查了开发者，结论是：**浏览量最高的求助集中在 `git revert` 和 `git reflog`，stash、clean、reset 紧随其后**——而且超过四成提问者在 Stack Overflow 上已经活跃了四年以上。这几乎从来不是语法问题，而是**"我不知道执行完会发生什么"**。
- 社区里流传很广的一个判断：**Git 是一项漂亮的工程，却是一个糟糕的产品——它把自己内部的实现结构（对象、引用、索引）直接暴露成了用户界面，命令的名字又不能反映它真正做的事。**

死记命令的人会陷入一个稳定的负循环：

```
遇到问题 → 搜命令 → 抄命令 → 能跑 → 问题变种 → 抄的命令失灵 →
更慌 → 抄更多命令 → 更加依赖搜索 → 离"理解"越来越远
```

每一轮循环，你都更熟练了一点仪式，也更远离了一点因果。

而 AI 时代的到来，正在把这个负循环推向荒谬的极端：**过去你至少还要自己抄命令、自己回车，仪式还经过你的手；现在你可以连命令都不看，直接对 AI 说"帮我把提交历史弄干净"，然后在对话框里点一下"允许"。** cargo-cult 不但没消失，它升级了——你连椰子耳机都不用自己戴，AI 帮你戴。

## 0.3 自测：你的概念地图上有多少空白？

下面 10 道题，不考命令拼写，只考"你是否知道发生了什么"。每答一个"能"，计 1 分：

1. 能说出 `git reset --hard` 和 `git revert` 在"提交已经推送到共享分支"场景下的本质区别吗？
2. 能解释为什么删除一个分支**不会**删除它上面的任何提交吗？
3. 知道 `.git/refs/heads/` 目录里存放的东西是什么、有多大吗？
4. 能画出工作区（working directory）、暂存区（staging area）、仓库（repository）三者之间的关系图吗？
5. 知道 detached HEAD 状态下新产生的提交为什么"容易丢"吗？
6. 能说出 fetch 和 pull 的关系，以及 pull 时合并发生在哪一端吗？
7. 知道 reflog 是什么、存在哪里、默认保留多久吗？
8. 能解释"分支只是一个指向某次提交的指针"意味着创建一个分支时，仓库里实际复制了多少数据吗？
9. 知道 `git push` 被拒绝并提示 non-fast-forward 时，Git 在保护什么吗？
10. 能判断自己的团队适合 Trunk-Based 开发还是 GitFlow 吗？

**计分与路线建议：**

- **0–3 分**：本书正是为你写的。你会在这本书里第一次看清 Git 的全貌，并且学会让 AI 帮你执行那些你终于理解了的操作。
- **4–7 分**：你的地图有洞。第 1 部分的五张概念地图会把洞补上，你会在多处"原来如此"。
- **8–10 分**：概念上你已经是明白人，可以直接跳到第 2 部分的场景手册和第 12 章的安全体系——那里有大量你可能还没系统化过的 AI 协作模式。

无论几分，有一点是确定的：**这 10 道题没有一道考你命令怎么拼。** 因为本书的第一个主张就是——

## 0.4 两种学习路径的分岔：40 条命令 vs 5 张地图

学 Git 的传统路径是一张命令清单：

```
git init / clone / add / commit / status / diff / log / branch /
checkout / switch / restore / merge / rebase / fetch / pull / push /
stash / tag / reset / revert / cherry-pick / reflog / bisect / ...
```

大约 40 条高频命令，几百个参数组合。这条路的逻辑是：**先把动词背全，再指望"用法"自然涌现。** 它的结局往往是上一节的负循环。

本书提出另一条路径：Git 里真正值得掌握的，不是 40 条命令，而是 **5 张概念地图**。命令只是抵达这些概念的路径之一——而且在 AI 时代，甚至不是最好的路径：

| # | 地图 | 一句话本质 | 对应章节 |
|---|---|---|---|
| 1 | **仓库** | 一个自包含的历史数据库，藏在 `.git/` 里 | 第 1 章 |
| 2 | **提交** | 一次不可变的全量快照，用哈希互相链接 | 第 2 章 |
| 3 | **分支** | 一张可以移动的书签，指向某次提交 | 第 3 章 |
| 4 | **远程** | 一面会呼吸的镜子，照的是别人家的仓库 | 第 4 章 |
| 5 | **历史** | 可塑的——但只在属于你的那段 | 第 5 章 |

这 5 张地图是互相咬合的：仓库装着提交，提交串成历史，分支在历史上移动，远程是历史的另一份拷贝。**理解了地图，每条命令都会自动"归位"**——你会知道 `git branch` 只是在写一行字，`git merge` 只是在历史图上连一条边，`git push` 只是在同步两份拷贝。

而没理解地图的时候，40 条命令是 40 个孤立的咒语。

## 0.5 AI 时代的新分工：你出意图，AI 出语法

到这里，一个合理的疑问是：**既然 AI 已经这么能干，我为什么还要理解概念？让 AI 全包了不行吗？**

不行。而且恰恰相反——**AI 越强，概念理解越值钱。** 原因有三：

**第一，你说不出意图，AI 就只能猜。**
"帮我把 Git 弄干净"不是一个意图，是一个愿望。AI 面对这个愿望能做的事太多了：rebase 压缩？drop 掉一半提交？force push 重写远端？每一种都"干净"，但后果完全不同。你只有能用概念语言说话——"把这三个提交 squash 成一个，保留作者信息，**不要动已经推送的部分**"——AI 才能把你的意图无损地翻译成动作。**概念词汇表，就是你与 AI 之间的 API。**

**第二，你看不懂过程，就只能盲签。**
现代编码代理执行 Git 操作前通常会向你展示它打算跑的命令。如果你看不懂 `git reset --hard origin/main` 意味着"丢弃本地全部未推送的提交"，那个确认框就只是一道需要点击的关卡，而不是一道防线。2025 年一家创业公司的 AI 代理在用户明确宣布"代码冻结"之后仍然执行了破坏性操作、抹掉了生产数据库——**AI 不总是听话的，确认框是你最后的防线，而防线的前提是你读得懂它。**

**第三，出事之后，说明书在你脑子里还是在网上，决定你要慌多久。**
误操作一定会发生——可能是你点的确认，也可能是 AI 的自作主张。理解概念的人知道"几乎一切都能从 reflog 里救回来"，于是冷静地说出准确的求救指令；不理解的人只会对着一片干净的 commit log 怀疑人生。**同样是出事，概念地图决定了你慌 5 分钟还是 5 小时。**

所以本书的核心公式是：

> **你负责意图与判断，AI 负责语法与执行。**
> 意图与判断的前提，是概念地图。语法与执行的可靠前提，是安全边界（第 12 章）。

这不是一本教你"躺平把 Git 交给 AI"的书，也不是一本"AI 时代更要手敲命令"的书。它教你站在这条分界线正确的位置上。

## 0.6 本书怎么用：四段式结构与 AI 指令箱

全书统一采用一条叙事链：

```
概念 → 场景 → 判断 → AI 指令 → 命令
```

- **概念**（第 1 部分）：五张地图，Git 的骨架。每张地图讲三件事——它是什么、它不是什么、什么时候会用到它。
- **场景**（第 2 部分）：真实工作流里的典型情境——写提交、选分支策略、多任务并行、解决冲突、从事故中恢复、团队协作。
- **判断**：每个场景不止一种解法。本书会摆出候选方案的利弊，让你练习"选哪个、为什么"——这是搜索引擎给不了你的。
- **AI 指令箱**：每个场景配 2–5 条可直接复制的自然语言指令模板。它们与具体工具无关——Claude Code、Cursor、GitHub Copilot、Aider、Windsurf，乃至任何带终端执行能力的对话助手，都能理解这些指令。
- **命令**：以侧栏小字出现，仅作"底层到底跑了什么"的透明化，从不抢主线。全书所有命令汇总在附录 A，按概念分组，不按字母排序。

「AI 指令箱」是本书的标志性栏目。它的设计哲学是：**模板不是让你背的，是让你改的。** 每条模板里都埋着概念词汇（分支、快照、指针、引用、历史重写），你每用一次，都是在练一次"说出意图"的能力。用得多了，你会发现自己的需求越来越少依赖模板，越来越多直接出口成章——那就是概念地图内化的迹象。

**关于安全的预告：** 本书默认你带着一个能执行命令的 AI 助手阅读。AI 执行 Git 操作有明确的"红黄绿"安全边界（第 12 章完整展开）：只读与只造新对象的操作是绿色的——AI 可直接放行；会动引用、工作区或远端的（add、commit、reset --hard、push）是黄色的——AI 提议、你确认后才执行；不可逆销毁、覆盖共享远端、涉及凭证的（裸 force push、历史重写、读 .env）是红色的——须流程级确认，AI 只能建议。在到达第 12 章之前，每章的 AI 指令箱都会标注操作的颜色。**养成在发出每条指令前默念"这是什么颜色"的习惯，是本书要教你的第一个反射。**

## 0.7 本章小地图

```
Cargo-Cult Git：仪式正确，因果不明 —— 全球流行病
        │
        ▼
病根不是命令太多，而是概念模型缺失
        │
        ▼
治疗：5 张概念地图（仓库/提交/分支/远程/历史）
        │
        ▼
AI 时代新分工：你出意图与判断，AI 出语法与执行
        │
        ▼
前提：概念词汇表 = 你与 AI 的 API
      确认框要成立，你得读得懂它
      出事后，地图决定你慌多久
```

**三大典型误解拆解**

1. **"我 Git 用了很多年，早就会了。"** ——会的是仪式。自测题 10 道里能稳拿 8 分以上的资深用户凤毛麟角；年限不替换概念，只加深肌肉记忆。反过来，正因为年限长，地图补上后收益立竿见影。
2. **"AI 都能帮我操作 Git 了，我就不用学了。"** ——方向反了。AI 时代"抄命令"的成本趋近于零，于是**判别力成了唯一的稀缺品**：什么该让 AI 做、做到哪一步要收回、结果对不对，全都需要概念。自动化消灭的是体力活，不是责任。
3. **"概念太抽象，命令才实在。"** ——恰好相反。命令才是漂浮的表面：`checkout` 一词在 Git 里至少干三件风马牛不相及的事。概念才是实在的地基：整个 `.git` 目录的机制几十年未变，命令却一直在换马甲（`checkout` → `switch`/`restore` 就是最近一次）。**学概念是买 invariant，学命令是买 fleeting。**
